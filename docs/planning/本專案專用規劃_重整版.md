## 一、專案重新定位

**Island Fitness AI 不是健身計次工具，而是「AI 品質判定 × 島嶼養成」的遊戲化健身產品**：用一支家用鏡頭做到準教練級的即時動作矯正——只有「完整週期＋達標深度＋無代償」的動作才算有效、才產生金幣——再把金幣投入一座看得見、能累積的 3D 島嶼，形成 **「正確訓練 → AI 判定有效 → 獲得金幣 → 島嶼成長 → 想再訓練」** 的正向循環。健身系統回答「怎麼做才對」，島嶼回答「為什麼要持續做」；評審第一眼要看到的不是四個功能按鈕，而是**這條循環在眼前跑一圈**（練一組 → 金幣飛入島 → 蓋起一棟建築）。

## 二、目前專案狀態總結（引自現況盤點）

- **能跑且驗證過**：34/34 引擎測試綠；示範模式端到端（倒數→計次→HUD→結算入帳→圖表）；相機被拒的安全網；金幣經濟／建設／成就；設定的真欄位；手機 RWD；0 console error。
- **狀態定性**：核心功能=企劃書等級；產品體驗=工程 Demo 等級。四個分頁各自成立，但互不說話。
- **主要缺口**：無「今日/任務」層、結算獎勵無儀式、分頁零引流、單組 60 秒 vs 簡介「3 組×12」矛盾、四個假設定（難度/三色/每日/週目標存而不用）、OAuth 佔位。
- **風險區**：`workout.js` async 時序（run-token 剛修穩）、store schema 淺合併雷、真相機良率依賴環境（macOS 人物置中）。

## 三、與企劃書的落差重點（引自落差分析）

企劃循環五步 `選任務 → AI 辨識 → 結算 → 獎勵轉換 → 島嶼建設`，現況：

```
✗ 無任務   ✓ 辨識強   ✓ 有結算   ✗ 獎勵只有 toast   ✓ 可建設   ✗ 無拉回循環
```

- 斷點 1（第 1 步）：沒有每日任務/週目標（企劃 B.2 明文承諾，含「週目標解鎖島嶼區域」）。
- 斷點 2（第 4 步）：獎勵轉換零儀式——這是企劃把「數字」變「情感連結的視覺成就」的樞紐。
- 斷點 3（第 6 步）：島與訓練互不引流，循環靠使用者腦補。
- 其他：分級語音缺「低」級（結算總評可補）、10.3「後台」需改口徑為「本機優先＋可匯出」、組數流程與簡介數字矛盾。

## 四、重整總方向（引自重整策略）

**保留核心引擎與功能，重做「產品體驗層」**（策略選項 B 為主、局部 A 為輔）。不做新架構搬遷、不砍掉重練、不只做美化。執行紀律：**先打通一條黃金路徑，再擴散廣度**——`打開 App → 今日任務 → 取景全綠 → 訓練一組 → 結算儀式 → 金幣入島 → 蓋房 → 回到今日打勾`。

### 六-補、關鍵設計決策：運動終止邏輯（S4 的前提，先定案避免實作時打架）

**問題**：舊發想是「時間導向」（60 秒倒數環，時間到強制結束）；企劃書是「次數導向」（組×次，狀態機判定完整週期才計次）。兩者同時存在會造成「時間到了但只做 8/12 下被砍」或「12 下做完還乾等 20 秒」的錯亂。且 `UI_REDESIGN_BRIEF` 與 `SPEC §3.1` 都把「倒數邊框」列入保留契約——不能單純刪掉。

**決策：次數為主、時間為安全網、倒數環改語意。**

1. **組的完成條件＝達到目標有效次數 N**（次數導向，符合企劃書「品質確認」定位）。達到 N → 立即進入組間休息，不乾等。
2. **時間只當安全上限**：單組上限（建議 90 秒）到仍未達 N → 該組以實際次數收束、照常結算（不懲罰、教練語音鼓勵），防止使用者卡死在一組裡產生挫折。
3. **倒數環改語意、不刪除**（契約保留）：
   - 組內 → 環＝**有效次數進度環**（8/12 亮 2/3），顏色沿用三色回饋；
   - 組間休息 → 環＝**休息倒數環**（30 秒遞減）；
   - 安全上限剩 10 秒才以顏色/閃爍提示時間壓力。
   - 此語意同時滿足 SPEC「隨時間/**組數**遞減的光線環」的原文。
4. **示範模式沿用同一套語意**（合成序列照樣走 組→休息→組），Demo 與真機行為一致。
5. HUD 的「倒數」欄位改為「本組 X/N 下＋休息倒數」雙態顯示；簡介頁的「3 組 × 12 下、休 30 秒」自此與實際流程一致。

> S4 實作計畫必須以本決策為規格；若實作中發現需偏離（如某動作以時間計更合理，e.g. 平板支撐類），先回這裡改決策再動工。

## 七、目前不要做的事情

1. **不要砍掉重練**——會丟掉 34 測試守護的防作弊引擎（最難被抄的競賽資產）。
2. **不要重寫核心 AI 引擎**——加動作用加檔案、調難度用 opts 注入，判定式不動。
3. **不要修改 tests 的舊斷言**——只增不改；改舊斷言＝掩蓋回歸。
4. **不要更換 vendor 版本**——three/mediapipe 升版會同時牽動島嶼、公仔、偵測三系統。
5. **不要另起全新 Design System**——歷史教訓：Liquid Glass 整層做完被整層退回；只收斂 Lumina。
6. **不要一次重構整個專案**——一次一條 Slice，做完任一條都停在可交付狀態。
7. **不要做後端／真帳號系統**——SPEC §1.3 明定 Demo 邊界；簡報口徑改「本機優先＋可匯出」。
8. **不要在未過互審前動高風險區**——`workout.js` 時序區與 store schema 的改動，實作計畫先過 cross-model review 再動手。

## 九、黃金路徑驗收（整體 Definition of Done）

重整完成的判準不是「做完幾條 Slice」，而是這條路徑**一鏡到底、零破圖、0 console error**：

1. 打開 App → 看到今日任務與目標環（3 秒內理解「我今天要幹嘛」）
2. 點「開始訓練」→ 今日推薦動作 → 取景檢查全綠 → 自動倒數
3. 完成一組（含組間休息）→ 結算成績單 → 金幣飛入島嶼演出
4. 「去蓋房子」→ 島上蓋起新建築 → 看到「下一個解鎖目標」
5. 回到今日 → 任務打勾、週目標進度前進
6. 全程：34 測試綠、防刷鐵則不變、離線可跑、手機/筆電皆可展示

## 十、AI 協作規則（交給 Codex / Cursor / Claude Code 必須遵守）

1. **每次只處理一條 Slice**——不順手修隔壁。
2. **每次修改前先提出計畫**——列出目標/檔案/驗收/風險，過目（高風險 Slice 需 cross-model 互審）後才動工。
3. **不要修改不相關檔案**——diff 超出 Slice 宣告範圍即退回。
4. **不要動 `app/core/`**——引擎/規格/幾何/合成器一律唯讀；需要參數化走建構 opts。
5. **不要動 `tests/` 舊斷言**——只允許新增測試。
6. **不要改 `CONTRACTS.md` 既有簽名**——新介面用附加條目；改簽名＝重大事件需先互審。
7. **UI 改動必須對齊 Lumina tokens**——禁止新增硬編碼色票、禁止另起設計系統。
8. **完成後必須回報**：修改檔案清單＋測試方式（`node tests/run.js` 結果＋瀏覽器實測步驟與截圖）＋已知未盡事項。
9. （補充）store 新欄位一律「新增＋深合併預設」，不改既有欄位語義；動 `workout.js` 時序區必附「載入中退出／暫停恢復／再一次／組間退出」實測清單。
