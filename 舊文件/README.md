## 前提有誤_勿參考/

### `健身系統與遊戲連動技術方案評估報告.md` / `.docx`

**⚠️ 這份文件的根本前提是錯的，不得再作為任何架構決策的依據。**

它的第一句就寫：

> 「本系統（AI 健身動作判定系統）與島嶼遊戲 App **為兩個獨立開發之應用程式**」

這個前提**從未經過雙方確認，而且與初衷直接衝突**。《初步發想計劃》寫的是「我想要做**一個軟體**，它有四大功能⋯用下方四個按鈕來切換」。

這份報告在那個錯誤前提上評估了八種「跨應用同步方案」，然後這個前提被 v2 企劃書繼承（§4.1「兩個介面」），又被 QA 回覆繼承。**專案的架構方向就是從這裡開始跑偏的。**

另有一處實質技術錯誤：方案 E 的 Firestore Security Rules 範例宣稱能防止金幣竄改，但該規則只檢查「金幣不為負」，使用者仍可將餘額直接設為任意大數。真正的防線必須是伺服器端函式作為唯一寫入閘門。

**替代文件**：`企劃文件/AI健身系統_育秀盃企劃書_v2_整合版.md` §4.1（產品形態）、§4.8（整合架構）。
