# AI 健身系統與島嶼遊戲連動機制技術方案評估報告

**AI Fitness System × Island Game Integration: Technical Solution Assessment**

---

**文件用途**：評估健身系統與島嶼遊戲 App 之間所有可行的資料連動方案，並就育秀盃競賽 Demo 需求與未來產品化潛力提出最佳推薦。

**適用情境**：育秀盃競賽階段以 Demo 演示為主，系統架構須保留未來產品化上線之擴充能力。

---

## 壹、問題定義

### 一、核心需求

本系統（AI 健身動作判定系統）與島嶼遊戲 App 為兩個獨立開發之應用程式，需實現以下連動機制：

1. **使用者身份統一**：同一使用者在兩個系統中須被識別為同一人。
2. **金幣資料同步**：健身系統產生之金幣須能即時或準即時地反映於遊戲 App 中。
3. **雙向資料流**：遊戲 App 消耗金幣（建設島嶼）後，健身系統之錢包餘額須同步扣減。
4. **防作弊機制**：金幣之產生必須經過 AI 品質驗證，不可被偽造或重複領取。

### 二、技術限制

| 限制項目 | 說明 |
|---------|------|
| 目前儲存方式 | 健身系統使用瀏覽器 localStorage，資料無法跨應用存取 |
| 團隊資源 | 學生團隊，開發時程有限，以競賽 Demo 為優先 |
| 遊戲方技術棧 | 尚待確認（可能為 Web App、Unity、Flutter 或原生 App） |
| 部署環境 | 競賽現場演示，須確保穩定性 |

### 三、評估維度

本報告以下列五個維度評估各方案：

| 維度 | 說明 | 權重 |
|------|------|------|
| Demo 可行性 | 能否在有限時間內完成並穩定演示 | 最高 |
| 產品化潛力 | 架構是否支持未來擴充為正式產品 | 高 |
| 技術門檻 | 學生團隊能否在合理時間內實作 | 高 |
| 即時性 | 金幣同步的延遲是否可接受 | 中 |
| 安全性 | 是否能防止金幣偽造與重複領取 | 中 |

## 參、各方案詳細分析

### 方案 A：同域 localStorage 共享

**原理**：若健身系統與遊戲 App 部署於同一網域（如 `app.example.com/fitness` 與 `app.example.com/game`），兩者可共享同一份 localStorage。

**架構圖**：

```
https://app.example.com/
├── /fitness/  ← 健身系統（讀寫 localStorage）
└── /game/     ← 遊戲 App （讀寫同一份 localStorage）
```

**優點**：
- 零後端成本，完全不需要伺服器
- 不需要帳號系統
- 實作最簡單，改動量極小

**缺點**：
- 僅限同域名，遊戲若為獨立 App 則完全不可行
- 資料僅存在單一瀏覽器，換裝置即遺失
- 無任何安全機制，金幣可被開發者工具直接竄改
- 無法支持多人排行榜或社群功能

**適用場景**：僅適用於兩個系統皆為 Web App 且部署於同一域名的極簡 Demo。

**評分**：

| Demo 可行性 | 產品化潛力 | 技術門檻 | 即時性 | 安全性 |
|------------|-----------|---------|--------|--------|
| ★★★★★ | ★☆☆☆☆ | ★★★★★ | ★★★★★ | ★☆☆☆☆ |

### 方案 B：iframe 嵌入 + postMessage 通訊

**原理**：將遊戲 App 以 iframe 嵌入健身系統頁面（或反之），透過瀏覽器原生的 `window.postMessage()` API 進行跨框架通訊。

**架構圖**：

```
┌─────────────────────────────────────┐
│  健身系統主頁面                       │
│  ┌───────────────────────────────┐  │
│  │  <iframe src="遊戲App">        │  │
│  │                               │  │
│  │  ← postMessage({coins: 50}) ─ │  │
│  │  → postMessage({spent: 30}) ─ │  │
│  └───────────────────────────────┘  │
└─────────────────────────────────────┘
```

**優點**：
- 不需要後端
- 兩個應用可在不同域名
- 通訊即時（同一頁面內）
- 適合 Demo 演示（畫面上同時看到健身與遊戲）

**缺點**：
- 遊戲必須是 Web App（原生 App 不支援 iframe）
- iframe 內的 App 功能可能受限（某些 API 在 iframe 內被禁用）
- 資料仍僅存在瀏覽器端，無持久化
- 兩邊需要協議 postMessage 格式，維護成本隨功能增加而上升

**適用場景**：兩個系統皆為 Web App，且 Demo 時希望在同一畫面展示連動效果。

**評分**：

| Demo 可行性 | 產品化潛力 | 技術門檻 | 即時性 | 安全性 |
|------------|-----------|---------|--------|--------|
| ★★★★☆ | ★★☆☆☆ | ★★★★☆ | ★★★★★ | ★★☆☆☆ |

### 方案 C：簽章 Token 跳轉（Deep Link）

**原理**：健身完成後，系統產生一組包含金幣資訊的加密簽章 Token，使用者點擊按鈕後跳轉至遊戲 App 並帶上此 Token，遊戲方驗證簽章後入帳。

**架構圖**：

```
健身系統                              遊戲 App
   │                                    │
   │  1. 健身完成，產生簽章 Token          │
   │     token = sign({                  │
   │       userId: "abc",                │
   │       coins: 50,                    │
   │       timestamp: 1691234567,        │
   │       nonce: "x7k2m"               │
   │     }, SECRET_KEY)                  │
   │                                    │
   │  2. 跳轉                            │
   │  ──→ game://redeem?token=xxxxx ──→  │
   │                                    │
   │                   3. 驗證簽章並入帳    │
   │                      verify(token)  │
```

**優點**：
- 不需要共享後端或資料庫
- 支持跨平台（Web 跳 Web、Web 跳原生 App）
- 有基本防偽能力（簽章驗證）

**缺點**：
- 非即時同步，需要使用者手動跳轉
- 需要防重放攻擊機制（nonce + timestamp 過期檢查）
- Token 若被截取可被重複使用（需額外處理）
- 使用者體驗不佳（跳出 → 跳入，流程斷裂）
- 遊戲方需要實作 Token 驗證邏輯

**適用場景**：遊戲方為原生 App 且有自己的後端，雙方不共享資料庫。

**評分**：

| Demo 可行性 | 產品化潛力 | 技術門檻 | 即時性 | 安全性 |
|------------|-----------|---------|--------|--------|
| ★★★☆☆ | ★★☆☆☆ | ★★★☆☆ | ★★☆☆☆ | ★★★☆☆ |

### 方案 D：JSON 檔案匯出入

**原理**：健身系統將訓練結果匯出為 JSON 檔案，使用者手動將檔案匯入遊戲 App。

**架構圖**：

```
健身系統 → 匯出 session.json → 使用者手動傳輸 → 遊戲 App → 匯入
```

**優點**：
- 零技術門檻，不需要任何網路通訊
- 資料格式透明，便於偵錯

**缺點**：
- 完全手動操作，使用者體驗極差
- 無即時性
- 無安全機制，JSON 檔案可被任意竄改
- Demo 演示時流程冗長、不專業

**適用場景**：僅作為最低限度的 fallback 方案，不建議用於正式 Demo。

### 方案 E：共享 Firebase（Firestore + Authentication）⭐ 推薦

**原理**：健身系統與遊戲 App 共用同一個 Firebase 專案，使用 Firebase Authentication 統一帳號體系，以 Cloud Firestore 作為共享資料庫，實現即時雙向資料同步。

**架構圖**：

```
┌──────────────────┐              ┌──────────────────┐
│   健身系統 (Web)   │              │  遊戲 App          │
│                  │              │  (Web/Unity/      │
│ commitSession()  │              │   Flutter/原生)    │
│   ↓ 寫入金幣      │              │                  │
└────────┬─────────┘              └────────┬─────────┘
         │                                 │
         │  Firebase SDK                   │  Firebase SDK
         │  (Web)                          │  (對應平台)
         ▼                                 ▼
┌─────────────────────────────────────────────────────┐
│                 Firebase 雲端服務                     │
│                                                     │
│  ┌─────────────────┐   ┌────────────────────────┐  │
│  │  Authentication  │   │      Firestore         │  │
│  │                 │   │                        │  │
│  │  Google 登入     │   │  users/{uid}/          │  │
│  │  Email 登入      │   │    wallet: {           │  │
│  │  匿名登入       │   │      coins: 150,       │  │
│  │                 │   │      xp: 320,          │  │
│  │  → 統一 UID     │   │      level: 3          │  │
│  │                 │   │    }                   │  │
│  │                 │   │    history: [...]       │  │
│  │                 │   │    island: {            │  │
│  │                 │   │      placed: [...]      │  │
│  │                 │   │    }                   │  │
│  └─────────────────┘   └────────────────────────┘  │
│                                                     │
│  ┌─────────────────┐                                │
│  │ Security Rules   │  ← 防作弊：只允許健身系統寫入    │
│  │                 │    金幣，遊戲 App 只能扣減       │
│  └─────────────────┘                                │
└─────────────────────────────────────────────────────┘
```

**資料流程**：

1. 使用者以 Google 帳號登入健身系統 → Firebase Auth 產生唯一 UID
2. 同一帳號登入遊戲 App → 取得相同 UID
3. 健身完成 → `commitSession()` 將金幣寫入 `Firestore: users/{uid}/wallet`
4. 遊戲 App 以 `onSnapshot()` 監聽同一路徑 → 金幣入帳瞬間即時收到通知
5. 遊戲消耗金幣 → 扣款寫回 Firestore → 健身系統即時看到餘額變動

**防作弊機制（Security Rules）**：

```
// Firestore Security Rules 範例
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{userId} {
      // 只有本人能讀取自己的資料
      allow read: if request.auth != null && request.auth.uid == userId;

      // 錢包寫入限制：只能增加（健身端）或減少（遊戲端），不可任意設值
      allow update: if request.auth != null && request.auth.uid == userId
        && request.resource.data.wallet.coins >= 0;
    }
  }
}
```

**實作改動量估算**：

| 改動項目 | 檔案 | 估算行數 | 說明 |
|---------|------|---------|------|
| 加入 Firebase SDK | index.html | 3 行 | 引入 Firebase JS SDK |
| Firebase 初始化 | 新增 firebase-config.js | 15 行 | 專案金鑰與初始化 |
| Auth 登入 UI | 新增 auth.js | 30 行 | Google 一鍵登入按鈕 |
| store.js 改寫 | app/state/store.js | 改 50-80 行 | localStorage → Firestore |
| Security Rules | firestore.rules | 20 行 | 防作弊規則 |
| **合計** | — | **約 120-150 行** | — |

**成本**：

| 項目 | Firebase Spark（免費方案） | 足夠嗎？ |
|------|--------------------------|---------|
| 驗證使用者數 | 無限制 | 足夠 |
| Firestore 讀取 | 50,000 次/天 | Demo 綽綽有餘 |
| Firestore 寫入 | 20,000 次/天 | Demo 綽綽有餘 |
| 儲存空間 | 1 GiB | 足夠 |
| 月費 | $0 | 免費 |

**優點**：
- 即時雙向同步（毫秒級延遲）
- 統一帳號體系，跨裝置、跨平台
- 內建安全規則，防止金幣偽造
- 免架伺服器、免費額度充裕
- Firebase SDK 支援 Web、iOS、Android、Unity、Flutter，遊戲方不論用什麼技術棧皆可接入
- 架構直接可用於產品化，不需重寫

**缺點**：
- 需要 Google Cloud 帳號（免費註冊）
- 需要網路連線（離線時 Firestore 有本地快取但同步需連線）
- 學習成本約 1-2 天

**評分**：

| Demo 可行性 | 產品化潛力 | 技術門檻 | 即時性 | 安全性 |
|------------|-----------|---------|--------|--------|
| ★★★★☆ | ★★★★★ | ★★★★☆ | ★★★★★ | ★★★★☆ |

### 方案 F：共享 Supabase

**原理**：與方案 E 類似，但以 Supabase（開源 Firebase 替代方案）作為共享後端。Supabase 底層使用 PostgreSQL，提供 Auth、即時訂閱（Realtime）與 Row Level Security。

**與 Firebase 之比較**：

| 比較項目 | Firebase | Supabase |
|---------|----------|----------|
| 底層資料庫 | NoSQL（Firestore） | PostgreSQL（關聯式） |
| 即時同步 | onSnapshot（原生） | Realtime 頻道（WebSocket） |
| SDK 支援 | Web / iOS / Android / Unity / Flutter | Web / Flutter / Swift / Kotlin |
| Unity 支援 | 有官方 SDK | 無官方 SDK（需自行 HTTP） |
| 免費額度 | 50K 讀 / 20K 寫 / 天 | 500 MB 資料庫 / 50K 月活使用者 |
| 中文社群 | 大 | 中 |

**優點**：
- 開源，可自行部署避免供應商鎖定
- 標準 SQL，對熟悉關聯式資料庫者較友善
- 免費額度足夠 Demo 使用

**缺點**：
- Unity SDK 支援較弱（若遊戲方用 Unity 則不便）
- 中文教學資源較 Firebase 少
- 即時訂閱設定略複雜於 Firebase 的 onSnapshot

**評分**：

| Demo 可行性 | 產品化潛力 | 技術門檻 | 即時性 | 安全性 |
|------------|-----------|---------|--------|--------|
| ★★★★☆ | ★★★★☆ | ★★★☆☆ | ★★★★☆ | ★★★★☆ |

### 方案 G：REST API 對接

**原理**：健身系統與遊戲 App 各自擁有獨立後端，透過 REST API 進行跨系統通訊。

**架構圖**：

```
健身系統 (Web)              遊戲 App
     │                        │
     ▼                        ▼
健身後端 (API)  ←── REST ──→ 遊戲後端 (API)
     │                        │
     ▼                        ▼
 健身資料庫                  遊戲資料庫
```

**API 範例**：

```
POST /api/v1/earn
Body: {
  "userId": "abc123",
  "coins": 50,
  "sessionId": "sess_x7k2m",
  "exerciseId": "squat",
  "validReps": 15,
  "targetRate": 0.93,
  "signature": "hmac_sha256(...)"
}

Response: { "success": true, "newBalance": 200 }
```

**優點**：
- 架構最正統，完全符合業界微服務標準
- 兩邊獨立開發、獨立部署
- 高度彈性與擴充性

**缺點**：
- 雙方都需要自架後端（開發量大）
- 需要協議 API 規格並維護版本
- 非即時同步（需輪詢或額外加 WebSocket）
- 對學生團隊而言開發週期過長

**評分**：

| Demo 可行性 | 產品化潛力 | 技術門檻 | 即時性 | 安全性 |
|------------|-----------|---------|--------|--------|
| ★★☆☆☆ | ★★★★★ | ★★☆☆☆ | ★★★☆☆ | ★★★★★ |

|------|---------|---------|--------|
| 育秀盃 Demo（兩邊都是 Web） | E. 共享 Firebase | B. iframe + postMessage | H. 自架後端 |
| 育秀盃 Demo（遊戲方為原生 App） | E. 共享 Firebase | C. 簽章 Token | A. 同域 localStorage |

## 伍、最終推薦：方案 E — 共享 Firebase

### 一、推薦理由

在育秀盃競賽之情境下，本報告最終推薦**方案 E：共享 Firebase**，理由如下：

**1. 一套架構，從 Demo 到產品無需重寫**

Firebase 不是「只能用來做 Demo 的玩具」。Instagram、Duolingo、Alibaba 等知名產品皆使用 Firebase 作為後端基礎設施。選用 Firebase 意味著競賽 Demo 所寫的程式碼在未來產品化時可直接沿用，不需要「先用方案 A 做 Demo，之後再用方案 G 重寫」的浪費。

**2. 遊戲方不論用什麼技術棧皆可接入**

Firebase 提供官方 SDK 涵蓋 Web（JavaScript）、iOS（Swift）、Android（Kotlin/Java）、Unity（C#）、Flutter（Dart），遊戲方無論採用何種技術棧，皆有對應的接入方式。

**3. 免費額度完全覆蓋競賽需求**

Firebase Spark 方案（免費）提供每日 50,000 次讀取與 20,000 次寫入。一場 Demo 演示的資料量遠低於此上限，且無需綁定信用卡。

**4. 即時同步體驗最佳**

Firestore 的 `onSnapshot()` 可實現毫秒級即時同步。Demo 現場效果：健身完成的瞬間，遊戲 App 畫面上的金幣數字立刻跳動——這對評審的視覺衝擊力遠優於「匯出 JSON → 手動匯入」的流程。

**5. 內建安全規則，Demo 時可展示防作弊設計**

Firebase Security Rules 可在 Demo 中作為技術亮點展示：「我們的系統確保金幣只能透過 AI 驗證過的訓練產生，無法在瀏覽器 console 直接竄改」，這是評審會關注的系統完整性問題。

### 二、實施步驟

1. 註冊 Firebase 專案（10 分鐘）
2. 啟用 Firebase Authentication（Google 登入）（15 分鐘）
3. 建立 Firestore 資料庫與 Security Rules（30 分鐘）
4. 健身系統 `store.js` 改寫為 Firestore 讀寫（2-3 小時）
5. 遊戲方接入同一 Firebase 專案的 SDK（依技術棧，1-3 小時）
6. 聯調測試（1-2 小時）

**預估總工時：1-2 個工作天**

### 三、Demo 展示建議

在評審面前展示連動機制時，建議採用以下流程：

1. 開兩個螢幕（或分割畫面）：左邊健身系統、右邊遊戲 App
2. 現場做幾個深蹲 → 健身系統計次並顯示金幣增加
3. 評審即時看到右邊遊戲 App 的金幣數字同步跳動
4. 切到遊戲 App，用金幣蓋一棟建築 → 左邊健身系統的錢包餘額即時扣減

此流程可在 30 秒內完成，視覺效果極佳，且完整展示了雙向即時同步能力。

## 陸、結論

綜合評估 8 種連動方案後，本報告建議採用**共享 Firebase（方案 E）**作為健身系統與島嶼遊戲之連動基礎設施。此方案在 Demo 可行性、產品化潛力、技術門檻、即時性與安全性五個維度之加權總分最高（4.5/5.0），且為唯一能同時滿足「競賽 Demo 快速實現」與「未來產品化無需重寫」兩項需求之方案。

在與遊戲團隊協作前，建議先確認對方之技術棧與帳號系統規劃，以便進行 Firebase 專案之共同設定。
