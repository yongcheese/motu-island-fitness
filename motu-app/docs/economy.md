# 經濟系統 — 稀有度、貨幣、獎勵

2026-08-25。這份文件描述的是「商品稀有度 + 貨幣 + 獎勵」這一整套架構，不是單一功能。
程式碼是規格的實作，這裡寫的是**為什麼**長成這樣，以及哪些決定不要重新討論。

---

## 一句話版本

```
        健身
          ↓
        金幣  ──────→  一般商品購買
          │               ↑
          │               │  價格（price）
          └→ 抽獎券 ┐     │
   多出來的碎片 ────┤     │
                    ↓     │
                 幸運轉盤 │
   每日簽到 ┐        │    │
   幸運轉盤 ├→  碎片 ←────┘
   活動/任務┘        └──→ 未來的特殊兌換
   島上互動 ┘
                          │
      所有商品 ──→ 稀有度（rarity）
                        普通／稀有／史詩／神話
```

金幣 → 抽獎券 → 轉盤 → 碎片 這條路 2026-08-31 才被打開，而且是被定價擋著而不是被規則擋著 ——
理由見下面第二節末尾那一段。

**金幣與碎片是兩種資源，不是同一種資源的兩個名字。**
**價格與稀有度是商品的兩個獨立屬性，不是同一件事的兩種說法。**

## 一、稀有度

### 每件商品都有稀有度，而且是必填

`ItemDefinition.rarity` 是**必填欄位**，不是選填、也不是有預設值。少寫一個是編譯錯誤。

以前不是這樣：稀有度是選填的，目錄裡約 93% 的商品沒有這個欄位，而且有一條
「已標記商品不得超過目錄 15%（後來 18%）」的天花板。那套模型有一個天花板只能延後、
無法解決的問題——**階梯只有在相鄰兩階同時可見時才讀得出來**，所以分級必須「整層貨架一起做」，
於是每次新增貨架都變成「天花板還放得下嗎」而不是「這些商品該是什麼階」。

全部分級之後，那個相鄰性條件自動成立，天花板也就不需要了。

### 全部分級 ≠ 全部發光

| 階級 | 顏色 | 佔比 | 畫幾層 |
|---|---|---|---|
| 普通 | 白 | ~73% | 一塊琺瑯板 + 一圈細框。沒有放射紋、沒有閃光、沒有掃光 |
| 稀有 | 綠 | ~19% | 完整放射紋 + 2 顆閃光 + 掃光 |
| 史詩 | 紫 | ~8% | 4 顆閃光 + 框上的緩慢金屬反光 |
| 神話 | 紅 | 1 件（鳳凰） | 6 顆閃光 + 全遊戲唯一會漂移的色相 |

（2026-08-28 從六階收成四階：優秀併入普通、傳說併入史詩。兩次都往下併，因為往上併會讓
稀有變成全遊戲最大的一階、或讓神話多出三件——見 constants/rarity.ts。）

普通那一階看起來幾乎就是它取代掉的「沒有稀有度」卡片。**目錄沒有變吵，只是多了一個底。**

### 稀有度不從價格推導

這是硬規則。價格與稀有度是兩個獨立屬性，目錄刻意排成可以**直接讀出**這條規則：

- 部落面具 400 金幣 → 史詩
- 火把 1,050 金幣 → 普通
- 金絲雀 850 → 稀有，橘貓 900 → 普通
- 熱帶草裙 50 金幣（全遊戲最便宜）→ 普通

`npm run audit:catalog` 會在目錄不再包含「便宜但更稀有」的反例時失敗——
一個完全按價格排序的階梯，看起來就跟推導出來的一模一樣。

### 稀有度會影響獎勵，不只是卡片外觀

`constants/rewardPools.ts` 用稀有度篩選（上限、下限、排除清單）。
所以**重新分級一件商品，會連帶改變每日簽到／輪盤／健身獎勵可能發出什麼**。
這是刻意的單一來源設計，也是為什麼稀有度已經不再只是一層油漆。

## 二、貨幣

### 兩種，用途完全不同

| | 金幣 | 碎片 |
|---|---|---|
| 唯一來源 | **健身** | 每日簽到、輪盤、活動、任務、島上互動 |
| 用途 | 購買一般商品 | 長期收集資源；未來的特殊兌換 |
| 存在哪 | `profile.balanceGold` | `profile.wallet.fragments` |
| UI 顏色 | `island-gold` | `island-teal` |
| UI 圖示 | 錢幣（`Coins` / 自繪金幣） | 碎晶（`Gem` / 自繪 `FragmentShard`） |

### 為什麼存放方式不一樣

金幣留在最上層的 `balanceGold`，其他所有貨幣放進一個巢狀的 `wallet` map。看起來不對稱，理由很實際：

- `balanceGold` 是**承重欄位**。`firestore.rules` 的 `isValidUser` 無條件要求它、
  每日簽到伺服器在 transaction 裡直接 increment 它、而且世界上每一份既有存檔都帶著它。
  把它搬進 map 是一次「玩家會注意到數字不見了」的資料遷移，換不到任何玩家看得到的好處。
- `wallet` 是一個 map，所以它是 `firestore.rules` 裡的**一個** clause、
  update whitelist 裡的**一個**條目。第三種貨幣是 `CURRENCY_SPECS` 裡的一列，
  不是一次 schema 變更加一次 rules 部署。（`islandState` 與 `workoutRewards` 是同樣的理由。）

這個不對稱只存在於 `constants/currency.ts`。**所有呼叫端都只說 `getBalance(profile, 'coins')`。**

### 金幣可以買到抽獎券（2026-08-31）

上面那張表寫著碎片的來源不包含金幣，而轉盤發碎片 —— 所以商店賣抽獎券，等於開了
**健身 → 金幣 → 抽獎券 → 轉盤 → 碎片**。這條路以前是關著的（`RaffleTickets` 那一櫃是空的，
`categoryUtils.ts` 上還留著當時寫的理由）。現在它開著，是一個被推翻的決定，不是有人沒看到那道牆。

**牆換成了匯率。** 這跟每日簽到的補簽是同一種處理（第五節）：那是全遊戲第一處兩種貨幣接觸的
地方，被接受的理由是「換算很差、而且永遠嚴格劣於免費的那條路」。抽獎券套用同一組理由：

- 一張券 300 金幣，期望值約 13.8 個碎片（權重見 `constants/luckyWheel.ts`）＋ 12% 抽中稀有／
  史詩造型；換算下來大約 22 金幣換 1 個碎片。
- 免費的那條路一直都在：多出來的碎片每 20 個自動換一張券，一次健身最多發 40 個碎片。
- 所以「買券換碎片」永遠比「去健身」差。它買到的是**方便**（想現在就轉一次），不是效率。

要收回這個決定，只需要把 `card-raffle-ticket` 從 `constants/items.ts` 拿掉：購買路徑本身
（`grantsTickets`）是資料驅動的，沒有任何地方寫死那個 id。

### 沒有人可以自己改貨幣

不要在任何元件裡寫 `balanceGold: increment(n)`。
發放走 `grantReward()`；需要與其他欄位一起原子寫入時走 `buildCurrencyUpdate()`；
扣款走 `buildSpendUpdate()`。三者都在 `context/useEconomyActions.ts`。

## 三、獎勵

### 來源→貨幣政策：這條規則有牙齒

```ts
// constants/rewards.ts
export const SOURCE_CURRENCY_POLICY: Record<RewardSource, readonly CurrencyId[]> = {
  workout:              ['coins'],
  'daily-login':        ['fragments'],
  wheel:                ['fragments'],
  newbie:               ['fragments'],
  event:                ['fragments'],
  quest:                ['fragments'],
  'island-interaction': ['fragments'],
  'admin-test':         ['coins', 'fragments'],
};
```

每一筆獎勵都帶著它的 `RewardSource`，而 `checkGrant()` 在**任何寫入之前**執行。
所以「每日簽到不小心發了金幣」不是一個會上線然後一個月後才被發現的 bug——
那筆發放根本不會發生，而且 console 會指名是哪個來源試圖這麼做。

`wheel` 與 `quest` 目前**沒有任何程式碼**，但仍然被宣告。這是刻意的：
政策必須能在輪盤存在之前就說出「輪盤不得發金幣」。
沒有規則支撐的來源發不出任何東西；它只是無法在有人動手做的那天被用來鑄造金幣。

### 為什麼獎勵要帶來源

一筆憑空出現在錢包裡、沒有任何紀錄說明原因的資源，是無法除錯、無法做平衡、也無法稽核重複發放的。
來源跟著獎勵一路從「導致它的那件事」走到寫入為止，所以
「玩家為什麼得到這些資源」永遠有答案。成本是一個欄位。

### 獎勵池是規則，不是清單

獎勵池從目錄**推導**出來，永遠不列舉 id。加一件 180 金幣的帽子到商店，
它自動進入新手池；把某件既有帽子改成 2,000，它自動離開。這邊不用改任何東西。

任何獎勵系統都不得寫 `if (itemId === '...')`。

順序永遠是 **Filter → Select**，不是 Select → Check：
抽獎之前池子就已經只剩合格的商品，所以不存在「抽到了才發現要退回」的路徑——
那種形狀最後一定會發出它本來要排除的東西，因為那個「檢查」是某人在第三條路徑上忘記寫的一個 `if`。

## 四、健身 → 金幣：為什麼繞這麼一圈

目前的健身畫面是**拋棄式原型**，真正的健身系統會透過 API 串接。所以：

```
目前：  FitnessView ──→ reportWorkoutCompletion() ─┐
                                                    ├→ [bus] → useWorkoutRewards → 金幣 / XP / 紀錄 / 物品
未來：  Fitness API → Adapter ─────────────────────┘
```

`FitnessView` 的**全部**貢獻是一次 `reportWorkoutCompletion()` 呼叫。
沒有給付、沒有 XP、沒有寫紀錄、沒有獎勵邏輯、沒有物品 id、沒有彈窗。

### 這裡以前不是這樣，而且錯得很具體

2026-08-25 之前，`FitnessView.finishWorkout` 自己算 `Math.floor(reps * 0.8)` 金幣、
`reps * 5` XP，直接寫進存檔，再寫 workout_logs，**然後才**發出完成事件。三個問題：

1. **一個拋棄式原型畫面是遊戲經濟的權威。** 換成真 API 時，要嘛在 adapter 裡重新推導經濟，
   要嘛留一個沒人用的 UI 檔案在樹裡只為了保管那些數字。
2. **貨幣從元件裡被寫入，而且沒有記錄來源。**
3. **它在構造上就不可能冪等。** 給付發生在事件發布之前，所以沒有任何東西能分辨
   「重送的完成事件」和「新的完成事件」。

現在給付與 replay guard（`processedIds`）在**同一次 `updateDoc`** 裡，
所以重送的完成事件不可能付第二次錢。公式在 `WORKOUT_PAYOUT`，是資料。

### 換成真 API 要做什麼

刪掉 `FitnessView` 裡那一次呼叫，加一個 adapter 做三件事：驗證、把廠商的 payload
翻譯成 `WorkoutCompletion`、呼叫 `reportWorkoutCompletion()`。
**獎勵系統、貨幣系統、存檔、規則表都不會被動到。**

## 五、每日簽到

改發碎片（4 / 6 / 10 / 16 / 24 / 36 / 60，一輪 156）。

**這些數字不是把金幣階梯搬過來。** 舊的是 100 / 150 / 250 / 400 / 600 / 900 / 1500；
直接沿用會讓碎片讀起來就是「另一個名字的金幣」——一樣的量級、一樣的節奏。
除以 25 之後重新排成一個好讀的階梯，讓碎片看起來就是自己的東西：
以「週」為單位、以「十」為量級來數的資源。**形狀完整保留**（一樣的倍增、一樣在第 7 天跳一階），
因為形狀才是讓一輪值得走完的原因。

### 補簽仍然收金幣，這是刻意的取捨

這是全遊戲**唯一**兩種貨幣接觸的地方，也就是說有金幣餘裕的玩家可以透過補簽把金幣換成碎片。
這個匯率是被接受的，不是被忽略的：

- 一輪最多補 6 天，換算很差（500 金幣換 4～60 碎片）
- 補簽永遠**嚴格劣於**準時登入（準時是免費的）
- 若改成收碎片，等於讓從沒健身過的玩家用這一輪自己的產出買通這一輪
- 若完全拿掉補簽，只要漏一天，第 7 天大獎就永遠拿不到（它要求前六天全滿）

因此 `MAKEUP_SURCHARGE` 現在是一個**固定價格**而不是附加費，`makeupCostForDay()` 也不再隨天數變動。

## 六、幸運轉盤

2026-08-28 做出來了。前一版這一節寫著「目前不存在」，而它列出的三件事就是這次的地基：
`RewardSource` 已經有 `'wheel'`、`SOURCE_CURRENCY_POLICY.wheel` 是 `['fragments']`、
`RewardPool` 已經支援稀有度上下限。**輪盤沒有動到其中任何一條，只是用了它們。**

| 檔案 | 負責什麼 |
|---|---|
| `src/constants/luckyWheel.ts` | 十格獎品、權重、兩個造型獎池 |
| `src/context/useWheelActions.ts` | 扣券 + 發獎，**同一次 `updateDoc`** |
| `src/components/UI/LuckyWheel.tsx` | 畫面：島上右下角的入口圖示，以及它打開的轉盤面板 |

### 券從哪裡來（2026-08-31 補齊）

轉盤 2026-08-28 就能轉了，但那時候券只有一個來源：碎片滿出來。也就是說一個還沒把任何一支
碎片堆疊填滿的新玩家，打開轉盤只會看到 0 張券和一個按不下去的按鈕 —— 功能在，但沒有人玩得到。
現在有三條路：

| 來源 | 數量 | 在哪 |
|---|---|---|
| 開局 | 1 張 | `WELCOME_RAFFLE_TICKETS`（`constants/fragments.ts`）。新存檔直接帶著，舊存檔在載入時補發一次 |
| 多出來的碎片 | 每 20 個 1 張 | `settleFragmentGain`，一直都在 |
| 商店 | 300 金幣 1 張 | `card-raffle-ticket`（`constants/items.ts`），見第二節末尾的匯率說明 |
| 轉盤自己 | ×1，8.5% | 第 7 格 |

開局那一張是「讓玩家知道轉盤是什麼」，不是一段免費的遊玩：轉完那一次會看到整個獎品階梯，
然後下一張要自己來。補發的條件是**存檔裡沒有 `raffleTickets` 這個欄位**，不是「等於 0」——
0 是一個真的餘額（剛轉完最後一張的人就是 0），拿它當條件會變成每次登入送一張。

管理員測試模式裡有一整列抽獎券（`UI/AdminValueControls.tsx`：+1 / +5 / +20 與直接指定數值），
理由跟金幣、碎片那兩列一樣 —— 測轉盤需要券，而且測「券不夠」的那個狀態需要能歸零。

### 十格

| # | 獎品 | 機率 |
|---|---|---|
| 0 / 2 / 4 / 6 / 8 | 碎片 ×10 / ×20 / ×15 / ×30 / ×50 | 25.5 / 15.5 / 19.5 / 9.5 / 4.5 % |
| 1 / 9 | 稀有造型（隨機） | 各 6 % |
| 3 | 功能卡（雙倍金幣券 ×1；背包滿時退券） | 3 % |
| 5 | 史詩造型（隨機） | 2 % |
| 7 | 抽獎券 ×1 | 8.5 % |

碎片放在偶數格，五個特別獎才不會擠在一起；兩個稀有格隔了大半圈，否則看起來就是一塊胖的稀有格。

### 版面大小不是機率

十格都是 36°，**包含 1% 的史詩格**。理由是轉盤唯一勝過「抽獎按鈕」的地方就是玩家可以先看到獎品，
把史詩格照機率削成一條線等於把它從轉盤上拿掉。真正的機率在 `weight`，
而且 `wheelSlotChance()` 會直接印在那一格的 tooltip 上——不靠版面暗示，也不騙人。

### 扣券與發獎是同一次寫入

轉盤是遊戲裡第一個**同時扣款與發放**的動作。兩邊分開寫的話，扣了沒發＝玩家白花，
發了沒扣＝轉盤免費。所以 `useWheelActions` 自己組一次 `updateDoc`，而不是叫兩個現成的服務。
**規則沒有被重寫**：200 上限、多餘碎片轉抽獎券、抽獎券進位，全部還是 `constants/fragments.ts`
裡那幾個純函式。

### 功能卡那一格發真的卡（2026-09-13 改）

2026-08-31 時 repo 裡還沒有功能卡系統，那一格只能退還抽獎券。之後 雙倍金幣券
（`constants/utilityCards.ts`）上線，而且卡片自己的 `channels` 就寫著 `'wheel'`，
所以這一格改成照 `cardId` 發一張真的卡，走限時小攤同一個 `grantCards`、同一個 `maxOwned` 上限。
發卡和扣券是同一次寫入；`firestore.rules` 限時商店那一條本來就允許 `utilityCards` + `raffleTickets`，不需要部署規則。

只有卡已經帶滿時才退券（`FUNCTION_CARD_REFUND`，等於轉一次的成本）。權重維持 3%。

### 史詩 1% → 2%（2026-09-13 改）

史詩池只有 7 件，而且沒收齊前不會重複；1% 時要收齊平均約 700 轉，稀有（8 件、12%）只要約 67 轉，
差十倍，史詩格等於裝飾。2% 砍半，仍然是最稀有的結果；多出的 1% 從碎片 ×10 扣。

### 造型獎池

`wheel-outfit-rare` / `wheel-outfit-epic`：上下限都鎖在同一階，
分類是六個穿戴貨架加上 `SpecialFx`（稀有與史詩的化妝品大多在那裡）。
目前解析出稀有 8 件、史詩 7 件。**沒有價格上限**——轉盤看的是稀有度，
價格是商品的另一個屬性，加價格門檻等於把「貴的就是稀有的」偷渡回來。

那一階全部收齊時，`preferUnowned` 會退回已擁有的商品，而重複的穿戴品進背包是 no-op，
所以改折抽獎券（稀有 2 張、史詩 5 張，見 `DUPLICATE_OUTFIT_TICKETS`）。
折抽獎券而不是折碎片：碎片綁定單一商品，而它抽到的正好是那個碎片再也用不到的商品。

## 七、碎片可以買什麼

**目前什麼都不能買。** 這也是刻意的。

需求明確說了：如果碎片的最終用途還沒決定，先把 Currency / Inventory 的支援建完整，
不要自行大量新增尚未決定的消費系統。所以這次做的是貨幣、它的存放、它的發放、
它的政策、它的 UI 與它的管理員工具——不是一間憑空發明的碎片商店。

這個階梯固定下來的是**速率**：認真簽到的玩家大約一週 156 碎片。
那就是未來的兌換系統要拿來設計的數字。

未來如果要做「用碎片兌換指定稀有度的商品」，需要的東西都已經在了：
稀有度是資料、獎勵池吃稀有度、碎片是一種正式貨幣。

## 八、部署提醒

`firestore.rules` **改了不部署等於沒改**，而且失敗方式不是「一次寫入被拒絕」，
是整份存檔載入垮掉變成新手空白檔。`wallet` 是最新加的欄位。

```bash
npx firebase-tools deploy --only firestore:rules --dry-run   # 先在伺服器端編譯，不釋出
npx firebase-tools deploy --only firestore:rules             # 釋出
```

詳見 `docs/FIRESTORE_RULES.md`。
