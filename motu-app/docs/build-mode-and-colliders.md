# 建造模式 × 佈置模式，與擺放物的碰撞箱

這份文件記錄兩件一起做的事：

1. **UX**：屋外【建造模式】與屋內【佈置模式】原本是同一件事的兩套介面。這裡先寫評估，
   再寫重新設計後的樣子，以及哪些地方**刻意保持不同**。
2. **Collision**：所有擺放物的碰撞箱原本都是「整個模型的一個軸對齊方框」。這裡寫它為什麼
   會造成「明明沒碰到卻不能放」與「被看不見的東西卡住」，以及取代它的規則。

兩者是同一個問題的兩面：介面告訴玩家「這裡可以放」，碰撞判定卻說不行，兩邊講的不是同
一件事。

---

## 一、UX 評估：兩個模式差在哪裡

### 1. 玩家的目標不同

| | 屋內【佈置模式】 | 屋外【建造模式】 |
|---|---|---|
| 世界大小 | 一個房間，一眼看得完 | 一整座島，會被房子擋住 |
| 物件種類 | 家具、擺飾、**地板／牆面**（套用，不是擺放） | 裝飾、平台、主題建築、**房屋本體**、**寵物窩** |
| 主要動作 | 加一件家具、換個地板 | 加一件裝飾、**搬動已經放好的東西** |
| 空間本身 | 房間擴建（加一格房間） | 島嶼領土（整座島變大變小） |
| 找東西 | 轉個身就看到了 | 火把在手機上只有十幾個像素，還可能在房子後面 |

### 2. 原本兩邊的做法（改版前）

| | 屋內 | 屋外 |
|---|---|---|
| 選分類 | 右側抽屜，分類**圖磚**，每格寫「已擁有 N 款」 | 底部一排**分類 chip** |
| 看物品 | **直式清單**，分成「已擁有／尚未擁有」兩區，有名稱、說明、庫存 | **橫向卡片列**，左右箭頭翻頁，擁有與未擁有混在一起，只用「庫存不足」半透明遮罩區分 |
| 購買 | 同一張卡上的「購買」 | 同一張卡上的「購買」（這點原本就一致） |
| 擺放中的控制列 | **畫面下方**的 DockPanel | **畫面最上方**的浮動列 |
| 選取已擺放的物件 | 點模型 | 點模型（**只有這個方法**） |
| 進來先看到什麼 | 兩個對等的工具卡：家具／房間擴建 | **領土規劃**分頁（最少用的功能）被預設選中 |

### 3. 根本問題

* **同一件事有兩套操作**。挑東西、擺東西、確認，在兩個模式裡的位置、形狀、資訊量都不同。
  玩家在屋內學會的，走到屋外要重學一次 —— 而且沒有任何一項差異是「因為在戶外」才必要的。
* **「確認擺放」在螢幕的兩端**。屋內在下面，屋外在上面。這是最傷的一點：擺放是一個要反覆
  做很多次的動作。
* **屋外沒有辦法知道自己放了什麼**。要移動或收回，只能在 3D 世界裡找到那個模型並點它。
  沒有任何 UI 說過「模型可以點」。
* **橫向卡片列撐不住一個型錄**。三十件物品在一條會左右捲的窄帶裡，沒有擁有與否的分組，
  卡片小到只能放一張圖和一個名字。
* **預設分頁選錯了**。進建造模式最常做的事是擺東西，不是把島變大。

## 二、重新設計：一致的骨架，不同的工具

### 共用的部分（`UI/PlacementCatalog.tsx`、`UI/PlacementDock.tsx`）

兩個模式現在跑同樣的三拍 —— **挑一個主體 → 調整 → 確認或取消** —— 而且是同一份程式碼。

* **`CatalogDrawer`**：右側抽屜。第一層是分類圖磚（附「已擁有 N 款」），第二層是直式清單，
  分成「已擁有／尚未擁有」兩區。**擺放中會縮成右上角半高、背景不擋點擊**，所以可以連續
  擺好幾個而不用重開清單。
* **`PlacementItemRow`**：清單裡的一列。已擁有和未擁有是同一種卡片，只有動作區不同
  （擺放／套用 vs 購買）。
* **`PlacementDock`**：畫面**下方**的擺放控制列。左邊是主體，中間是**即時判定**，右邊是
  旋轉（附 `R` 鍵帽）／收回／確認擺放／取消。危險色只給收回，取消放在確認的另一側。
* 分類永遠來自 `utils/categoryUtils.ts` 的同一份分類表，用 `placementScope` 過濾 —— 所以
  「我在哪裡看過這個」永遠只有一個答案。

### 屋外獨有：【島上物件】

刻意不一致，而且原因在世界而不在介面：島很大，東西會找不到。

* 列出島上所有已擺放的物件，依分類分組，**「我的家」排在最上面**。
* 每一列有「移動」與「收回」。移動交棒給同一個編輯 session（跟點模型完全一樣），
  收回走同一個 `retrieveDraftTarget`，所以庫存退回、存檔、失敗回報都只寫一次。
* 點模型仍然可用，而且仍然是看得到東西時最快的方法 —— 這個工具是為了看不到的時候。
* **「我的家」那一列是唯一不是動詞的一列**：它開啟【我的家】而不是把房子拿起來。原因見第五節。

### 屋外獨有：【我的家】

見第五節。房子有三個動詞，那是一個「目的地」，不是別人清單裡的一列。

### 屋外獨有：【島嶼領土】

改成 modal。它編輯的是**島本身**而不是島上的任何東西，這一點讓它變成屋內「房間擴建」的
對應物，而不是型錄的對等分頁。它也不再是預設分頁。

### 版面配置

| 位置 | 內容 |
|---|---|
| 上方置中 | 說明（叫小天使）／退出編輯 |
| 下方置中 | 工具列（我的家／建築與裝飾／島上物件／島嶼領土），擺放中換成 `PlacementDock` |
| 右側 | 抽屜（我的家／型錄／島上物件），一次只會有一個 |

擺放中 `NavBar` 會退場（`App.tsx`）—— 手上拿著東西的時候，螢幕下緣是拿來放下它的，
不是拿來離開的。

## 三、Collider：碰撞箱為什麼太大，以及新規則

### 1. 原本的做法

`lib/furniturePlacement.ts` 的 `measureFootprint` 會把模型底下每個 mesh 的
`geometry.boundingBox` 聯集起來，得到**一個軸對齊方框**。這個方框同時負責：擺放重疊判定、
走路碰撞、平台邊緣判定、地板高度查詢。

它對沙發是準的，對其他形狀一律**往外多算**：

| 形狀 | 方框多算了什麼 |
|---|---|
| **圓形**（噴泉、陶甕、貓窩、鳥籠） | 對角線多 41.4%。噴泉半徑 1.60，方框角落卻伸到 2.26 |
| **細長／斜放**（樹枝鳥架、木板、衝浪板） | 整個外接矩形，而不是那條斜的東西 |
| **上寬下窄**（許願井的屋頂、鳥籠的罩子、陽傘） | 最寬的那一層一路算到地面 |
| **會轉的圓形物** | 方框跟著轉，所以「轉一下就放得下了」 |

而且方框是軸對齊的，`geometry.boundingBox` 分不出圓柱和方塊 —— 兩者給出一模一樣的正方形。

### 2. 新規則（`lib/collisionShape.ts` + `lib/furniturePlacement.ts`）

> **一個碰撞箱 = 模型實際畫出來的實體幾何，投影到 XZ 平面的凸包，簡化到最多 12 個頂點，
> 並且依高度切成最多 6 層。**

沒有任何一件物品有自己的數字，沒有任何一行程式碼是 `if (itemId === …)`。

* **量頂點，不量 bounding box。** 直接讀 `geometry.attributes.position`（每種物品只做一次，
  之後所有副本共用）。這是圓形物品能變回圓形的原因。
* **凸包簡化只會往外長。** 移掉一個頂點 = 把它左右兩條邊延長到交點，所以簡化後的多邊形
  一定**包含**原本的。碰撞箱寧可大一點點，不能小 —— 小了兩個模型就會互穿。
  全型錄最大外凸 6.3%（木製鳥籠），上限寫在 `MAX_SIMPLIFY_BULGE = 0.08`。
* **高度分層**是「上寬下窄」的解法。兩個擺放物只有在**同時存在於同一個高度**時才會相撞，
  所以一朵花可以放進許願井的屋簷下，但一根跟屋頂一樣高的柱子放同一個位置仍然會被擋。
* **走路碰撞**是同一套形狀，但只取走路高度帶（0.25–1.75）那一層。椰子樹的樹葉在四公尺
  高，所以只有樹幹擋人。
* **Padding 不做進多邊形裡。** 小物件的最小可讀尺寸與兩件物品之間的間隙都是 `pad`，
  判定時當成「多邊形 ⊕ 半徑 pad 的圓」處理 —— 角落是圓的，不是把方框整個放大。
* **效能有上限。** 每種物品最多 6 層 × 12 頂點，只量一次。走路判定新增了外接圓的粗篩
  （原本完全沒有），所以擺滿東西的島**比改版前更省**。

### 3. 順手修掉的

* **房子的無建造圈**。`placementSurfaces.ts` 原本註冊的是「牆 + 玩家半徑 0.35」的實心框
  當作擺放障礙物 —— 那是擋**身體**的框，不是擋**物件**的框。多出來的 35 公分是玩家看得穿
  的空地卻放不了東西。改成房子本身的 footprint；擋身體的邊界仍然在 `resolveHomeCollision`。
* **鬼影輪廓**（`PlacementGhost` 的 `FootprintOutline`）與**小地圖**現在畫的是同一個凸包。
  玩家看到的圈就是判定用的圈 —— 噴泉畫的是圓圈，木板畫的是細條。

### 4. 實測（`npm run audit:colliders`，以及在跑起來的遊戲裡量的）

```
噴泉：碰撞多邊形 12 邊、外接半徑 1.644（方框角落是 2.257）
      走路停止距離：各個方向都是 1.93–1.99
      改版前：正面 1.95、對角線 2.61 —— 對角線有 66 公分的隱形牆
      把噴泉轉 45°：停止距離不變（方框會跟著轉）
```

全型錄最大的幾個改善（小物件貼著放時的最短距離）：

| 物品 | 改版前 | 改版後 |
|---|---|---|
| 噴泉 | 2.45 | 1.82 |
| 戶外陶甕 | 1.19 | 0.75 |
| 大型陶甕 | 1.06 | 0.73 |
| 風動雕塑 | 1.12 | 0.82 |
| 木製鳥籠 | 0.84 | 0.56 |

### 5. 守門的稽核

`npm run audit:colliders` 用**出貨用的模型**餵給**出貨用的 `measureFootprint`**
（`scripts/lib/measureFurnitureModel.ts` 的 `buildModelObject3D` 會建出真的 three.js
scene graph），所以通過等於是在講玩家實際拿到的碰撞箱，而不是這個檔案裡另外算一遍的算術。

它檢查五件事：

1. 碰撞箱不會超出模型（容許 `MAX_SIMPLIFY_BULGE`）
2. 模型的**每一個頂點**都在自己的碰撞箱裡（這個方向錯了會讓模型互穿）
3. 粗篩半徑 `reach` 涵蓋每一層（不然真的重疊會在進到分層判定前就被丟掉）
4. 走路碰撞箱也不超出模型
5. 頂點數與層數都有上限

加一件新物品不需要動這裡的任何一行。

## 四、移動精度、選取鎖與堆疊

前三節把**介面**與**碰撞箱**統一了，但「拿起一個東西把它移到想要的位置」這件事本身，兩個
模式仍然各寫各的。這一節是那一層。

### 1. 「移動跨度過大」的兩個真正原因

回報是「滑鼠移動很久，物品完全不動，然後突然跳一大格」。這是**兩個獨立的原因疊在一起**，
而且大家最先懷疑的格線只是其中一個。

#### (a) 拖曳只在「指標還壓在模型上」的時候取樣

兩個模式都把拖曳掛在**鬼影自己**的 R3F `onPointerMove` 上。R3F 是靠 raycast 派送這個事件
的：只有當射線仍然打中那個物件自己的幾何時才會觸發。所以整個手勢實際上長這樣 ——

```
指標在花瓶上      → 取樣 → 花瓶跟著游標
指標滑出花瓶      → 完全沒有事件 → 花瓶凍住，滑鼠走多遠都一樣
指標剛好又掃過它  → 一次取樣 → 花瓶一口氣跳完累積的距離
```

—— 這就是回報的「沒反應，然後一大跳」，而且**物件越小越嚴重**：檯燈、書本、小盆栽，剪影
只有幾十個像素。屋內完全沒有備援，物品就停住；屋外有一個備援，但那是一個固定在
`y = 0.34` 的隱形圓環，而鬼影自己的處理器是拿**物件當下的高度**去交平面的 —— 兩個不同的
平面，所以游標每次跨過模型輪廓，物件就在兩個答案之間跳一次。

**修法**：不要再問場景。拖曳是**指標**的手勢，不是任何幾何的手勢。按下之後，
`Three/usePlacementDrag.ts` 直接從 **window** 讀 `pointermove`，用相機和游標自己的螢幕座標
重建射線，之後再也不做任何 hit test。每一個 pointer 事件都會移動物件，不管底下有什麼 ——
這同時也是「正在移動的物品不會被自己的 Raycast 干擾」的答案：拖曳已經沒有 raycast 可以被
干擾了。

#### (b) 0.5 的地板格線（只有屋內）

`interiorPlacement.ts` 的 `FLOOR_GRID = 0.5`，從這個模式寫出來就在。一個房間
`ROOM_GRID_SIZE` 是 12，所以整層地板是一塊 24 × 24 的棋盤，家具只能站在交點上。桌子往左推
一點：不動、不動、不動，然後跳半公尺 —— 那是它自己寬度的四分之一。

**修法**：步進改由共用的 `lib/placementSession.ts` 決定，預設 **2 公分**。格線沒有被刪掉，
而是**從機制降級成工具**：按住 `Shift` 對齊 0.25 的格線（比原本的 0.5 還細一半），擺放列上
有一個常駐的「自由微調 / 對齊格線」小標籤說明現在是哪一種。

#### (c) 順手修掉的第三個：每一次拖曳都以一次跳動開始

兩個模式都沒有**抓取點**，所以物件的**原點**會直接跑到游標下。抓住桌子的一角，滑鼠都還沒
動，桌子已經彈開一公尺。抓取點是用**平移射線**的方式套用的（`translateRayXZ`）：對任何水平
面，把射線原點在 XZ 平移，交點就位移同樣的向量，所以在地板、在桌面、在平台上都對，不需要
分情況。

> **實測**（跑起來的遊戲裡，建造模式）：1 px 的滑鼠位移 ≈ 0.015 世界單位，量化後是一格。
> 一次按住不放、游標走 253 px 且**完全離開模型剪影**的拖曳，物件全程跟著走到島的邊界為止。

### 2. 為什麼還要量化

因為位置會被存進 Firestore、讀回來、再被當成下一次拖曳的起點。在一次拖曳之內誤差不會累積
（位置是每個事件從射線重算的，不是把 delta 加起來），但那個 存→讀→拖→存 的迴圈會讓同一個
位置長出十五位數。`quantize` 把乘回去的結果再收到小數第六位，所以一個位置只是它格子編號的
函數 —— 這也是 `BuildingInteriorView` 那個「transform 沒變就不要寫」的短路能成立的前提。

### 3. Hover / Selected / Active

移動 A 卻選到 B，根因不是碰撞箱，是**選取狀態每一個 pointer 事件都被重新推導一次**：

* 屋內每一件擺放物都掛著 `onClick={() => onItemClick(p.instanceId)}`，**完全沒有守衛**。所以
  把書本拖到桌子上的那一刻，放開的那個 release 就選中了**桌子**，玩家突然開始搬家具。堆疊
  做不到，不是因為 collider，是因為手勢的對象在中途被換掉了。
* 屋外則是整個 session 期間把這個 handler 關掉（`isEditable = BUILD_MODE && !islandDraft`）。
  沒有東西能搶，因為沒有東西能選 —— 反方向的過度修正，而且玩家也沒辦法主動換一件。

`lib/placementSession.ts` 把三件事分開講：**Hovered**（這一格游標剛好指到什麼，只影響游標
外觀，從不儲存）、**Selected**（玩家點過的）、**Active**（手勢當下擁有的）。狀態機是
`idle → selected → moving → selected → idle`，`moving` 是**上鎖**的相位。

有一個容易漏掉的細節值得寫下來：**光靠相位鎖抓不到最後一個事件**。click 是在產生它的
pointerup 之後才送出的，而 pointerup 正是結束手勢的那個事件 —— 所以等 R3F 把 release 派給
底下的模型時，相位已經回到 `selected`，鎖已經開了。因此「有實際移動過的拖曳」會**認領它
自己的 release（只有真的跨過拖曳門檻的手勢才算，見下一節）**（`guardNextClick`），下一次按下時清掉。同一個旗標也擋住兩個模式的「點地面 =
把東西放到這裡」，否則放開拖曳的瞬間物品會丟掉抓取點跳一下。

沒有 `rotating` 相位，這是刻意的：旋轉是 45° 的離散步進（R 或擺放列的按鈕），不是有起點和
終點的手勢。一個停不住的相位就是一把握不住的鎖。

### 3.5 點擊 vs 拖曳：屋外「滑鼠移到哪、物品就跳到哪」

上面第 1 節修掉的是「拖曳中途取樣不到」。這一節修的是更前面的一件事：**屋外根本不需要按住
就會移動**。

`usePlacementDrag` 原本有一個 `followWhenIdle` 選項，屋外開著它：**沒有按下任何按鍵**的
`pointermove` 也會被採樣，物件就直接跑到游標下。所以

* 想看看某個位置好不好 → 看的當下東西已經搬過去了，沒有「先看再決定」這個動作；
* 伸手去按 HUD 上的按鈕 → 噴泉跟著飛過去；
* **手機上更糟**：「沒有按住」在觸控上不是一個存在的狀態，所以在建造模式裡拖動鏡頭的那一
  指，同一個 handler 也把**物件**一起拖走了。

那個選項已經整個刪掉。現在兩個模式的手勢完全一樣：

```
pointerdown 在物件上        → ARMED。什麼都不動，但相機已經被鎖住（見下）
指標位移 < 門檻             → 還是 ARMED。在這裡放開就是一次「點擊」＝選取
指標位移 ≥ 門檻             → DRAGGING。beginMove 上鎖，物件從這一個取樣開始跟著指標
pointerup                   → 位置定案，onEnd 把它寫回 draft（要按「確認」才會存檔）
Esc / 右鍵                  → 取消，物件回到按下去時的位置，但**東西還在手上**
```

**門檻**（`lib/placementSession.ts` 的 `DRAG_THRESHOLD_PX`）：滑鼠與觸控筆 4 px，手指 10 px。
兩個數字不同是必須的 —— 指尖蓋住 40 px 的玻璃，玩家感覺完全沒動的一次點按，實際上常常報告
5–8 px 的位移；用滑鼠的門檻去量，手機上每一次「點一下看看」都會變成一次小搬動，而觸控沒有
hover，點一下是**唯一**能看某個東西的方法。

門檻在真的要拖的人身上是隱形的，因為**抓取點是在按下的那一刻量的**，不是在跨過門檻的時候。
所以拖曳一開始，物件就正好落在「指標自己走了多遠」該在的位置，沒有補跳、也沒有要先掙脫的
死區。

**相機是在 pointerdown 就鎖住的，不是等跨過門檻。** `CameraController` 每一影格讀一次
`playerBus.isDraggingPlacement` 並消化累積的指標位移；如果按下當時不鎖，門檻前的那幾個像素
會把鏡頭轉掉，接下來玩家就是在一個已經轉過的鏡頭底下拖東西。沒跨過門檻就放開的話清掉即可 ——
照定義指標幾乎沒動，本來就沒有鏡頭該轉。

**Esc 有兩個意思，靠一個一次性旗標分開。** 拖曳中按 Esc 是「取消這次搬動」（物件回到原位、
東西還在手上），沒在拖的時候按 Esc 是「放下這個東西」（整個 session 結束）。兩個模式都把 Esc
掛在 window 上，所以拖曳的那一個用**捕獲階段**先接走並 `stopPropagation`。這對真的按鍵夠了
（按鍵的 target 是焦點元素，停在 window 捕獲就再也下不去），但**對「直接 dispatch 到 window
的事件」不夠** —— 那種事件的路徑只有一個節點，同一個節點上的每一個 listener 都會跑，
`stopPropagation` 管不到。所以拖曳同時舉起 `guardCancelKey()`，模式層的 handler 用
`consumeCancelKeyGuard()` 消化掉；誰先跑都不影響結果。旗標會在下一個 macrotask 自己清掉，
不然沒被讀到的那一次會吃掉玩家的**下一個** Esc。

右鍵也是取消：它是唯一絕不會是擺放手勢的鍵（那是鏡頭的視角旋轉），而且原生選單早就被
`lib/inputManager.ts` 全域擋掉了。

**「點一下地面」現在兩邊都是「把東西放到這裡」，不是「確認擺放」。** 屋外原本點地面就直接
存檔，那在跟著游標跑的年代是合理的（東西本來就在游標下，「點地面」和「放這裡」是同一件事）；
一旦物件會留在原地，同樣那一下就會把東西存到玩家根本沒有指著的地方。確認一律是擺放列上的
「確認」，跟屋內一直以來一樣。地面**雙擊**仍然是確認，那個快捷沒有動。

### 4. 堆疊：`surface` 掛載點原本沒有任何物品搆得到

屋內的 `surface` 掛載點是**完整實作**的 —— 會 hit test、會夾到桌面上、會把支撐物排除在重疊
判定外 —— 但 `DEFAULT_PLACEMENT` 是 `{ mounts: ['floor'] }`，而**全部 194 件物品沒有一件宣告
過 `surface`**。所以「把書放到桌上」背後的機制全都在，卻一次都跑不到。

修法必須是一條**規則**，不能是一張「小東西」的清單 —— 用 id 當 key 的表格正是
`footprintRadius`、`getCollisionBounds`、`ITEM_LAYERS` 各自被移除的理由。規則是：

> **任何東西都可以放在任何宣告了頂面的東西上，只要放得下。**

兩半都已經是量出來的：`tabletop`（constants/items.ts）說一件家具提供頂面，
`clampOntoSupport`（lib/furniturePlacement.ts）從兩個 footprint 回答「放不放得下」。所以衣櫃
會被床頭櫃拒絕，不需要任何人打一個尺寸；新增一件擺飾第一天就能疊。

放不下的頂面**不是**拒絕，而是**穿透過去**找後面的下一個面：拿沙發掃過小茶几時，沙發會落在
茶几後面的地板上，而不是整格變紅。「太大放不上那張桌子」不是錯誤，只是那不是你正在指的桌子。

屋外原本連這個概念都沒有：只有 `standable` 的木製平台算支撐，所以拖過戶外木桌的提燈不是
「在桌上」而是「重疊」。`getSupportAt` 把這件事補上，而且**刻意跟走路用的 `getSurfaceAt`
分開**——桌子不可以是玩家（以及寵物、NPC、腳步聲）踩得上去的地面。

### 5. 接觸 vs. 碰撞

這一段原本就是對的，值得寫下來是因為它常被誤會成問題所在：`placementsCollide` 先比**高度
帶**（`VERTICAL_EPSILON`），所以「剛好放在上面」讀作淨空而不是零厚度重疊；而 `finish` /
`evaluateIslandPlacement` 會把**支撐物本身**排除在障礙物之外 —— 玩家特意放上去的那張桌子，
對桌上的花瓶而言不是障礙。

順手修掉一個訊息錯誤：屋外的角點測試只在物件**確實站在某個東西上**時才報 `offEdge`。對一個
把椅子擺在桌子旁邊、角落稍微碰到的玩家說「有一半懸在平台外」是沒有意義的 —— 那裡沒有東西
懸空，只是有張桌子擋著，而重疊那條規則講得比較清楚。

### 6. 三種 Raycast 現在各自負責什麼

| | 誰做 | 何時 |
|---|---|---|
| **Selection Raycast** | 擺放物自己的 `onClick`，先問 `canSelect` | 只有玩家點擊時 |
| **Placement Raycast** | `usePlacementDrag` 從 window 重建的射線 → `resolveInteriorPlacement` / `evaluateIslandPlacement` | 拖曳中的每一個 pointer 事件 |
| **Collision Check** | `findPlacementConflict`（分層凸包） | 位置決定之後 |

三者不再共用同一次 hit test，這是「物品重疊後選取錯誤」在架構上的解法。

### 7. 守門的測試

`npm run test:placement`（`scripts/test-placement-precision.ts`，55 項）。它跑的是**出貨用的
模組**，不是這裡另外算一遍的算術。最值得留意的一項是原始 bug 的迴歸測試：把指標以 1 公分
為單位走過一個房間，斷言**沒有任何一步的位移超過一格**、物件**不會長時間凍住**、而且拖曳
方向永遠單調。在舊的 0.5 格線下，這一段會是 49 次完全不動加上一次跳半公尺。

## 五、【我的家】：選取不等於編輯

### 1. 「點一下我的家就開始搬房子」為什麼是個問題

改版前，房子的**唯一**入口是【島上物件】抽屜最上面的一列，而點它會直接
`selectHome()` → 寫進 `islandDraft` → 進入擺放模式。同一個動作一次做了四件事：

* 房子本體隱藏（`PlayerHomeView` 在 `kind === 'home'` 時回傳 null），改由鬼影繪製；
* 玩家正在看的抽屜關掉；
* 底部換成 `PlacementDock`；
* 玩家欠下一個他從來沒要求過的「確認／取消」。

於是**每一個**跟房子有關的意圖都被折進「移動」這一個動作裡：

| 玩家想做的事 | 改版前實際發生的事 |
|---|---|
| 看看我的家現在長怎樣 | 房子消失，變成一個鬼影，還要按「取消」才能退出 |
| 換一個外觀 | 先進入移動模式，才在擺放列上找得到「外觀」鍵 |
| 把大門轉個方向 | 先進入移動模式，而且在按下 R 之前不知道有這個功能 |

三個更深的毛病：

1. **入口藏在承諾錯誤的清單裡。**【島上物件】的副標寫的是「移動或收回已擺放的東西」，
   但房子不在 `islandPlacements` 裡、不能被收回 —— 那張清單的三欄有兩欄對它沒有意義。
2. **「更換外觀」被關在移動模式裡面，而且兩種「確認」混在同一塊面板上。**
   `applyHouseStyle` 是**立刻寫入**的，位移卻還是草稿；所以先換外觀再按「取消」，
   位移被取消、油漆卻留下來了。
3. **旋轉在進入之前完全不可見。** 「大門朝哪邊」是房子的一個屬性，
   但畫面上任何地方都沒有寫過它。

### 2. 重新設計：入口 → 房屋管理 → 具體動作

```
【我的家】（工具列第一格／島上物件那一列／直接點島上的房子）
   ↓  selectHome() —— 世界完全沒有變化
房屋總覽：目前外觀的預覽＋說明、大門朝向羅盤、可用款式數
   ↓  玩家明確選擇
[更換外觀] → 款式清單（已擁有／尚未擁有），點「套用」就換好，不進擺放模式
[移動與轉向] → startHomeTransform() → 唯一會寫 `islandDraft` 的路徑
```

對照使用者提出的七條原則：

| 原則 | 做法 |
|---|---|
| 1. 點【我的家】不該直接移動房子 | `selectHome()` 只開面板；只有 `startHomeTransform()` 會寫草稿 |
| 2. 「選取」與「移動」要分開 | `useIslandEditor` 現在有兩個狀態：`homeMenuOpen` 與 `islandDraft.kind === 'home'`，永不同時成立 |
| 3. 玩家要知道正在編輯什麼 | 面板底部固定一條「編輯中：我的家 · 海景小屋」；擺放列的主體區也一樣寫著「我的家」 |
| 4. 更換外觀不該觸發移動 | 款式清單在面板裡，`applyHouseStyle` 只寫 `home.currentStyle`；擺放列上的「外觀」鍵已移除 |
| 5. 只有移動時才進 Transform Mode | 同 1 |
| 6. 旋轉要清楚直覺 | 大門朝向變成一個**看得到的事實**：面板上的羅盤盤面＋擺放列上的即時方位 chip，兩者共用 `facingLabel()` |
| 7. 功能集中，不要藏在小按鈕裡 | 從抽屜裡的一列升格為工具列第一格，並且三個入口（工具列／清單／點房子）都到同一個地方 |

### 3. 為什麼「旋轉」沒有變成第三個入口

使用者提的方案是【更換外觀】／【移動位置】／【旋轉】三個對等按鈕。這裡合併成兩個，
理由不是版面，而是**驗證**：

* 房子轉了以後蓋住的地面就不一樣了。一個繞過草稿的「原地旋轉」等於繞過
  `isDraftBlocked`，可以無聲地把房子的一角轉進柵欄裡或轉出地形外。
* 拖曳與旋轉在 3D 世界裡本來就是同一個連續操作，`PlacementDock` 也早就同時提供兩者
  （旋轉鍵＋`R` 鍵帽）。

所以那一列叫**「移動與轉向」**而不是「移動位置」，副標直接寫出兩個動作與 `R` 鍵；
而旋轉真正缺的東西 —— 「現在朝哪邊」—— 被補上了。

### 4. RWD

工具列從三格變四格，原本的 `sm:w-52 lg:w-56` 固定寬在 640px 就已經溢出，四格會溢出約
250px。改成 `DOCK_LAYOUT`：

| 寬度 | 版面 | 量到的結果 |
|---|---|---|
| < 640 | 一列四格（`grid-cols-4`），標籤用四個字的 `shortLabel` | 320px 下每格 67×88，工具列 304px 不溢出 |
| 640–1023 | 2×2（`sm:grid-cols-2`），完整標籤＋副標 | 820px 下寬鬆 |
| ≥ 1024 | 一列四格（`lg:flex` + `flex-[1_1_13rem]`，可壓縮），上限 `calc(100vw-2rem)` | 1024px 下每格 195.8px，工具列 844.8px，副標不截斷 |

面板本身沿用 `CatalogDrawer` 的外殼（`w-full max-w-md`、`p-4 md:p-8`），所以手機是滿版、
平板以上是 448px 的右側抽屜。

### 5. 守門

沒有稽核腳本 —— 這一節改的是資訊架構而不是幾何。真正的不變量寫在型別裡：
`IslandDraftKind` 沒有「已選取」這個值，而 `homeMenuOpen` 與 `kind === 'home'` 的草稿
由 `startHomeTransform()` / `cancelDraft()` 兩支函式互斥地維護 —— 兩者都只在
`useIslandEditor.ts` 裡出現一次。
