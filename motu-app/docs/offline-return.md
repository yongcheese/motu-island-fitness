# 離線回歸／環境變化系統 (Offline Return)

> 「幾天沒回來，再次登入時感覺 —— 我的島好像真的自己生活了一段時間。」

不是懲罰機制。這套系統的每一個產物都是**可以整理掉的裝飾**，以及**寵物的一個心情**。
沒有任何一條路徑會扣金幣、扣家具、刪道具、降等級、破壞房屋，或讓寵物死亡。

判斷一個新想法能不能加進來，只問一句：**玩家如果永遠不整理，他有損失任何東西嗎？**
只要答案是「有」，那就不屬於這套系統。

## 2. 重複使用了哪些既有系統

這套系統沒有另外建立第二套登入／存檔／時間判定。

- **登入與存檔**：`src/auth/` + `src/save/`，完全沒動。狀態就存在 `UserProfile` 上。
- **時間判定**：`islandState.lastSeenAt`，一個 ISO 字串。沒有另外一套時鐘。
- **生成位置**：`utils/placementRules.ts` 的 `findRandomValidPlacement` —— 島上的花和石頭
  本來就是用它決定位置的，房屋本體與門前通道的迴避規則因此自動沿用。
- **互動**：`Three/InteractionPromptTracker.tsx` + `UI/InteractionPrompt.tsx`，
  整理只是多一個候選目標，不是第二顆按鈕。E 鍵的分派也走 `Avatar.tsx` 既有的 `handleAction`。
- **彈窗排序**：`lib/onboardingQueue.ts`，多一個成員 `islandReturn`。
- **畫面色調**：`Three/Scene.tsx` 的 `SceneLighting`。它本來就每幀把三盞燈朝天氣的目標值
  lerp，離線環境只是再乘一組係數上去 —— 沒有新的 `useFrame`、沒有 post-processing、
  沒有第二套光。
- **彈窗先後**：`lib/onboardingQueue.ts` 的 `useOnboardingActive` —— 恢復演示等它讓開才開始，
  所以不會在「歡迎回到島上」後面自己跑完。沒有為了這件事再做一套「畫面被擋住了嗎」的判斷。
- **管理員測試**：`hooks/useAdminMode.ts` / `AdminOnly` / `constants/adminFeatures.ts`，
  和其他測試功能同一套開關。
- **寵物**：`Three/IslandPet.tsx` 的既有跟隨邏輯，心情只是**乘數**，不是第二套 AI。

## 3. 資料形狀

```ts
// UserProfile.islandState — 一個 nested map，不是五個 top-level 欄位
{
  lastSeenAt?: string          // 量離線時間的錨點
  sprouts?: OvergrowthSprout[] // 目前站在島上、還沒被整理掉的東西
  pet?: { mood, vitality, lastGreetedAt? }
  lastReturnAt?, lastReturnStage?, lastReturnHours?   // 最近一次「有打招呼」的回歸
}
```

收成一個 map 是刻意的：`firestore.rules` 只需要一條 `hasOnly(['islandState', 'lastUpdated'])`，
以後要加飢餓／心情／親密度也不必再動規則。
見 `docs/FIRESTORE_RULES.md` 第 5 節 —— **規則必須部署，否則整套功能會安靜地不存在。**

`sprouts` 存的是**實際物件的清單**，不是一個種子。
種子 + 重新推導會把玩家剛剛整理掉的東西再長回來，那正是 §11／§12 要防的事。

## 4. 時間怎麼算

```
lastSeenAt ──(離線)──> 現在
```

`lastSeenAt` 在兩個時機被寫：**登入時**，以及遊玩中每 5 分鐘一次的心跳
（`SEEN_HEARTBEAT_MS`，分頁在背景時不寫）。
只在登入時寫是不夠的 —— 那樣「玩了三小時再離開」會被算成從進來的那一刻開始離線。

**沒有 `lastSeenAt` = 第一次看到，永遠不是長時間離線。**
新玩家如此，這個功能出現以前的舊存檔也是如此：兩者都沒有「離開過」。

## 5. 成長是一條曲線，不是階梯

```
overgrowthBudget(hours)   // 這是「島上總共該有幾個」，不是「這次要加幾個」
  1 天  →  2
  3 天  →  6
  7 天  → 12
 14 天  → 21
 19 天+ → 26（上限 OVERGROWTH_MAX）
```

寫成總量而不是增量，是「重複登入不會無限增加」的**結構性**保證：
`growOvergrowth` 只補差額，補到目標就停。

登入後 `lastSeenAt` 被重設，所以下一次登入的目標是 0 —— 玩家整理過的成果不會被推翻。
不是靠「已整理」旗標記住的，是靠時鐘。

種類按時間解鎖，各自有上限：

| 時間 | 開始出現 |
|---|---|
| 12 小時 | 落葉 |
| 2 天 | 雜草 |
| 3 天 | 小花 |
| 4 天 | 枯枝、小石 |
| 5 天 | 藤蔓（上限 5 條） |
| 12 天 | 蜘蛛網（上限 3 張） |

上限是「藤蔓是細節、不是外套」這句話的實作。房屋有 12 個掛點，
藤蔓 5 + 蜘蛛網 3 永遠填不滿，所以最誇張的情況也還看得到牆。

藤蔓還會**繼續長**：一條藤蔓最終有多長是它自己的 seed 決定的（所以五條不會長得一樣），
但它現在長到哪裡是 `ambience.vineGrowth` 決定的。第五天冒出來的是短短一截，
兩個星期後才會垂到牆面下方 —— 不是每次登入就直接生成完整藤蔓。

## 6. 環境狀態：一個值，所有系統都讀它

`resolveIslandAmbience(sprouts)` → `IslandAmbience`。這是整套功能唯一的環境計算。

```
sprouts.length ──> wildness (0..1) ──┬──> saturation   畫面飽和度
                                     ├──> brightness   燈光強度
                                     ├──> exposure     toneMappingExposure
                                     ├──> shade        偏陰影的程度
                                     ├──> vineGrowth   藤蔓長到哪裡
                                     └──> grade        給管理員看的名字
```

三個使用端各自只讀一個欄位，**沒有任何一個自己去算離線天數**：

| 讀它的地方 | 拿走什麼 |
|---|---|
| `Three/Scene.tsx` | saturation / brightness / exposure / shade |
| `Three/IslandOvergrowth.tsx` | vineGrowth |
| `UI/AdminIslandControls.tsx` | wildness / grade |

### 為什麼是從「島上現在有什麼」算，而不是從時鐘算

這是整份設計最重要、而且最不直覺的一個決定。

直覺的寫法是 `hours → ambience`：玩家離開 12 天，就把畫面按 12 天的量調暗。
但那樣**玩家整理完島之後，畫面還是暗的** —— 因為時鐘還是說他離開了 12 天，
而他在遊戲裡做的任何事都改變不了那個數字。島只會在下一次登入時才變亮，
理由還是玩家在遊戲裡看不到的。

改成從**現在真的站在島上的東西**去算，「整理」和「恢復」就變成同一件事：
拔掉雜草，光就跟著回來，同一個動作、連續地。不需要恢復計時器、
不需要第二份狀態、不需要「已整理」旗標。

它也不可能和畫面說的不一樣：色調是從渲染器正在畫的那份清單算出來的，
所以一座偏暗的島上，一定看得到讓它偏暗的東西。

時鐘沒有消失 —— `overgrowthBudget(hours)` 仍然只由離線時間決定**長出多少**。
它只是不再被看第二次。

## 7. 畫面色調怎麼變

四個係數，全部走島上**原本就有的**系統：

| 係數 | 套在哪 | 最深的時候 |
|---|---|---|
| brightness | 三盞燈的 intensity | ×0.86 |
| saturation | 燈光顏色的 HSL 飽和度 | ×0.72 |
| shade | 燈光顏色混入柔和的灰綠 `#b9c4c1` | 22% |
| exposure | `gl.toneMappingExposure` | ×0.90 |

### 為什麼不是 post-processing

「畫面稍微變暗、飽和度降低」聽起來就是 colour grading pass 該做的事。
但這個專案沒有 EffectComposer：加一個等於多一個相依套件、一張全螢幕 render target，
以及每幀至少一次額外的全螢幕繪製 —— 為了一層很淡的色調，這個帳單太貴了。

**改成把光本身去飽和**，畫面幾乎一樣，成本是零。島上每一樣東西都被那三盞燈照著，
所以抽掉燈光顏色的飽和度，就等於抽掉每一個受光表面的飽和度：
沒有新的 pass、沒有新的材質、沒有 per-object shader、沒有多一個 draw call。

它和真正的 post-process 只差在自發光／不受光的表面（天空、螢火蟲）。
那些留著反而更對：長滿草的院子是**有陰影**，不是**陰天**。

> 燈光顏色在混入灰綠之後會把亮度還原回天氣原本的值。
> 變暗是 intensity 和 exposure 的工作 —— 如果色調也一起壓暗，
> 三者會無聲地相乘，「稍微變暗」就會悄悄變成「變黑」。

### 過渡是免費的（§15）

`SceneLighting` 本來就每幀把燈朝目標值 lerp（0.03）。離線環境只是換了目標值，
所以玩家回來的頭幾秒，是燈和曝光從原本的位置慢慢滑向這次離線該有的樣子 ——
「數秒內逐漸套用」，而不是第一幀就變暗。

**這套功能裡沒有任何一個過渡計時器**，因為燈光系統本來就是一個平滑濾波器，
離線只是餵給它的另一個輸入。

草的部分同理：`SwayingTufts` 本來就每幀在寫矩陣（為了搖曳），
所以「從地裡長出來」只是在那個迴圈裡多乘一個 0→1 的係數，同樣是零成本。
它用 sprout 的 id 記住誰已經長好了，所以**整理之後剩下的草不會重新長一次**。

## 8. 離線褪色與回歸恢復

> 「世界會隨著玩家離開而失去色彩，而玩家回來後，世界重新恢復。」

第 6、7 節那套是**永久的、由島上的東西決定的**，而且刻意很淡（飽和度最低 0.72）。
這一節是另一半：**由時鐘決定的、會自己消失的**，而且可以一路走到完全黑白。

兩半回答的是兩個不同的問題，所以不會打架：

```
resolveIslandAmbience(sprouts)   →  你在玩的時候，島長什麼樣    永久 / 很淡 / 整理就恢復 / 套在「燈」上
resolveIslandColour(hours, t)    →  你「剛回來」的那一刻長什麼樣  暫時 / 可到全黑白 / 自己恢復 / 套在「畫面」上
```

### 為什麼這一半可以看時鐘，第 6 節那一半不行

第 6 節那段長篇論證（「畫面會和玩家的行為脫節」）成立的前提是**那個色調是永久的**：
玩家整理完島，時鐘還是說他離開了 12 天，於是他站在乾淨的院子裡看著一個變暗的畫面，
而且他做什麼都改變不了。

褪色沒有這個問題，因為它**不是永久的**。它是玩家「走進來的那一瞬間」世界的樣子，
然後用幾秒鐘把自己收掉。時鐘決定顏色掉了多少，「回來」這件事本身把它帶回來 ——
這正是需求 §6～§8 描述的東西。玩家能看到它的唯一時機，就是回歸演示的那幾秒。

所以規則沒有變，只是被講清楚了：**畫面上任何會停留的東西，都不准由時鐘決定。**

### 飽和度怎麼算

```
colourDrainForHours(hours)   // 0 = 正常彩色，1 = 完全黑白
  ≤ 1 天  →  0        （完全沒有效果，連元素都不會掛上去）
    2 天  →  0.13
    3 天  →  0.20
    7 天  →  0.38
   10 天  →  0.49
   14 天  →  0.61
   21 天  →  0.78
   30 天  →  0.98
   31 天+ →  1.00     （完全黑白）
```

一條連續曲線（`drain = (days / 30) ^ 0.6`），不是階梯。
`COLOUR_STAGES` 那五個名字（正常彩色／輕微／明顯／接近灰階／完全黑白）**只有管理員面板在用**，
程式裡沒有任何一個地方 `if` 它 —— 和 `ISLAND_GRADES` 同一條規矩。

指數 0.6 < 1，和成長曲線（0.72，但那條是壓在總量上）方向相反是刻意的：
雜草必須永遠「一個下午整理得完」，所以它的曲線要壓平；顏色沒有這個包袱，
可以早一點就說話 —— 三天回來就看得出來安靜了一點，那才值得看。

`COLOUR_QUIET_HOURS` 是 **24 小時**，比長草的 `QUIET_HOURS`（12）晚。
再加上 `COLOUR_MIN_DRAIN = 0.12` 這道門檻（約兩天），
**每天上線的玩家永遠看不到這個系統，連那個 DOM 元素都不會被掛上去。**

### 恢復演示

```
玩家回到島上（且沒有任何彈窗擋著）
   ↓  停 0.8 秒 —— 讓玩家真的看到「咦，沒有顏色」
   ↓
島中央先出現一小塊顏色
   ↓  色彩往外擴散（bloom），同時整體飽和度也在往上抬
   ↓  5.5 秒
完全恢復，元素卸載
```

兩條 easing 是分開調的，而且 **bloom 一路領先** uniform 的那一條：
在動畫進行到 30% 時，中央那圈已經清出來了，但畫面其餘部分還幾乎是灰的。
如果兩條一起走，看起來會像有人在拉亮度滑桿，而不是「顏色從島上長回來」。
兩條在終點會合，所以最後一幀是**真正的無作用**，卸載元素時不會閃。

### 為什麼這裡用了 post-processing 而第 7 節沒有

第 7 節拒絕 EffectComposer 的理由（多一個相依、一張 render target、每幀多一次全螢幕繪製）
在那裡是對的，因為那是一層**永久**的淡色調。

這裡不一樣，有兩個理由：

1. **它必須碰到燈碰不到的東西。** 天空、螢火蟲、海水自己的色調都是不受光的，
   把三盞燈抽掉飽和度它們完全不會變。「完全黑白」但天空還是藍的，那不叫黑白。
2. **它可以被拆掉。** 恢復一結束元素就卸載，而且短離線根本不會掛上去 ——
   一般的一次登入付的成本是 0。EffectComposer 一旦加進去，就是每一場遊戲的每一幀都在付。

實作是一層 `backdrop-filter: saturate()` 的透明 div，加上一張 radial-gradient 的 mask
（mask 中間透明的那個洞就是 bloom）。這是瀏覽器合成器的工作，在 GPU 上，
沒有 render target、沒有第二次繪製場景、沒有 shader、沒有相依套件。

> mask 字串每改一次，瀏覽器就要重畫一張全螢幕漸層。所以兩個值都做了量化
> （飽和度 0.5%、半徑 0.25%），沒動到就完全不寫 style —— 整段動畫大概只重畫幾十次，
> 而漸層自己的柔邊把每一階都藏起來了。

### 它碰不到任何遊戲功能

- `pointer-events: none`，而且它是一個 DOM 元素，和 R3F 的樹完全沒有關係 ——
  從它到 raycast、collider、相機、輸入處理器之間**沒有路徑**。
- 掛在 `Three/Scene.tsx` 那個 `z-background` 容器裡面，所以它去飽和的只有島。
  所有 HUD 都在 `z-game-view` 以上：**UI、商店、設定、每一個彈窗都維持全彩。**
  這是故意的 —— 一顆灰掉的按鈕看起來像是被停用了。
- 恢復期間不鎖任何東西。玩家可以走路、互動、進屋、蓋東西、開商店。

### 和其他畫面效果的先後（§13）

演示有幾秒，值得看，所以它**不會在還沒人看得到的時候就開始跑**：
要等玩家人在島上（不在商店／屋內／換裝間），而且沒有任何 onboarding 彈窗在畫面上
（`lib/onboardingQueue.ts` 的 `useOnboardingActive`）。

實務上就是：玩家按下「歡迎回到島上」的〈去看看〉，世界才開始上色。
沒有這道門，整段演示會在那個視窗後面跑完，玩家一眼都看不到。
Loading Screen 也自動被涵蓋 —— 它是 `z-loading`，蓋在上面，而且那時 `islandRecovery` 還沒被設。

**開始之後就不再停**。如果因為玩家開了選單就暫停，玩家就有辦法把世界卡在灰色。

### 中途離開（§12）

存檔裡**沒有**「正在播放恢復動畫」這個欄位，而且永遠不該有。
整個恢復是兩個只活在記憶體裡的數字（離線幾小時、這次什麼時候進來的），
分頁一關就沒了。

玩家演到一半離開 → 下次登入量到的是一段**更短**的離線 → 拿到一個**更淺**的褪色。
這就是正確答案，而且是靠「沒有東西要對帳」得到的，不是靠一段還原邏輯。
（分頁被切到背景時 rAF 會被瀏覽器停掉；十分鐘後切回來，`performance.now()` 的差值
早就超過整段長度，於是 `progress` 直接是 1 —— 不會卡在灰色。）

### 為什麼雜草沒有跟著自動消失

需求 §9 說「可以」讓環境狀態一起恢復。這裡刻意只做了顏色和光，沒有自動清掉雜草。

因為那會把玩家回來要做的事拿走。整理本來就是這套系統唯一的互動，
而且整理**已經**就是恢復 —— 拔掉草，光就跟著回來（第 6、7 節）。
自動清掉等於「你不在的時候島荒了，你回來的時候島自己好了」，中間那個玩家不見了。

所以回歸時環境確實在恢復，只是恢復的是**顏色與光**，
而雜草留給玩家 —— 那不是待辦清單，是這座島還在等他的證據。

## 9. 不會長在哪裡

`lib/islandOvergrowth.ts` 的 keep-out：

- 玩家出生點（世界原點）半徑 2.2
- 石板路的每一顆石頭（`PATHWAY_BASE_POINTS`，已移到 `constants/terrain.ts` 共用）
- 玩家放置的每一件物品，半徑 1.35
- 草地以外（沙灘、海）
- 房屋本體與門前通道 —— 由 `findRandomValidPlacement` 既有的規則負責
- 彼此之間至少 0.7

### 區域差異（§14）

島上沒有區域系統，這次也沒有為了這個功能建一套。它不需要 ——
島上唯一重要的分區不是一張地圖，而是**玩家待過的地方**。

草長在牆角、長椅後面、花圃邊上，那些耙子掃不到的角落；草坪正中央是空的。
所以「角落」是從房屋和玩家自己擺的東西推出來的（`SHELTER_RADIUS`），
不是宣告出來的 —— 房子搬家，雜草偏好的位置就跟著搬。

它是**偏好，不是限制**：只有前 5 次嘗試會挑剔，之後就有什麼收什麼。
這個順序很重要 —— 島上角落被佔滿時，草還是找得到地方站，
而不是安靜地長不出來、把成長曲線核准的數量偷偷少掉一截。
（少掉的話畫面也會跟著不夠暗，因為色調是從這份清單算的。
`npm run test:offline-return` 兩件事都有釘。）

開闊的草坪仍然會有零星幾株（`EXPOSED_ODDS`）。
完全乾淨的草坪看起來像關卡設計，不像沒人整理。

> 為什麼用固定半徑而不是量測到的 walk box？因為這段程式跑在**登入時**，
> 場景還沒 mount，`lib/furniturePlacement.ts` 的量測框還不存在。
> 固定半徑會多留一點空間，而在「不要擋住互動物件」這條規則上，多留是對的方向。

## 10. 效能

- 同時最多 26 個物件。
- 五種地面物件共用 **4 個 InstancedMesh**。
- 落葉／枯枝／小石的矩陣**只在清單改變時寫一次**，沒有每幀工作。
- 只有一個 `useFrame`，處理最多 13 株草的搖曳，和島上原本的花共用
  `getWeatherSwayFactors`。
- 藤蔓／蜘蛛網是掛在房屋 transform 底下的幾個普通 mesh，每幀零成本，
  房屋移動／旋轉／換外觀時自動跟著走。
- 沒有 collider、沒有 walk box、沒有 pointer handler、沒有粒子。
- 色調沒有 post-processing、沒有 render target、沒有多的 draw call：
  四個係數餵進島上原本那一個 `useFrame`。
- 環境狀態只在清單改變時算一次（`resolveIslandAmbience` 是純函式，
  乾淨的島直接回傳共用常數，連配置都不做），不是每幀。
- 登入時的生成：最壞情況（26 株、從空島開始）實測約 **0.1 ms**，一次登入一次。
- 離線褪色一樣沒有 EffectComposer、沒有 render target、沒有第二次繪製場景：
  一層 `backdrop-filter` 的透明 div，由瀏覽器合成器在 GPU 上做。
  **短離線根本不會掛上那個元素**（`COLOUR_MIN_DRAIN`），恢復一結束就卸載 ——
  所以一般的一次登入付的成本是 0，而不是「很小」。
- 恢復演示只有**一個** `requestAnimationFrame`，而且只在演的那幾秒存在。
  它寫的是同一個元素上的兩個 CSS 值，兩個都做了量化（沒動就不寫），
  所以那張全螢幕 mask 漸層整段動畫只重畫幾十次，不是每幀一次。
- 離線時數**不是每幀重算**：它在登入時算一次，之後就是一個放在記憶體裡的數字。

## 11. 和建造系統完全分離

雜草不是家具。具體來說：

- 不在 `islandPlacements`、不在 `inventory`、沒有 catalog id、商店買不到；
- `resolvePlayerAgainstFurniture` 看不見它，所以不影響移動與碰撞；
- 建造模式選不到它（`IslandOvergrowth.tsx` 完全沒有 `onClick`）；
- 唯一能移除它的是「整理」互動。

> 維護提醒：如果哪天在 `IslandOvergrowth.tsx` 加了 `onClick`，
> 就等於把環境物件放進了家具的互動空間。那是這個檔案唯一一條不能跨的線。

## 12. 寵物

`PetMoodId` = `lively` / `calm` / `waiting` / `reunion`。

心情是一組**乘數**（`nestPull` / `pace` / `liveliness` / `showsNest`），
餵給 `IslandPet.tsx` 原本就在跑的跟隨邏輯。沒有第二套 AI。

- `nestPull > 0` → 主人離窩超過 `PET_NOTICE_RADIUS`（6.5）時，寵物待在自己的窩附近晃；
  主人一走近，覆寫解除，寵物就自己過來了 —— 「主動靠近」不需要額外程式碼，
  它就是覆寫停止作用的樣子。
- `reunion` 是唯一的暫態：回歸時設上，寵物跑到主人身邊（`PET_GREET_RADIUS`）時
  借用既有的 `playerBus.dogIsHappy` 撒嬌 1.8 秒，然後寫回 `lively`。
  **在寵物真的走到你旁邊時結算，不是在關掉視窗時。**
- 小窩／空食盆／散落的玩具只在安靜的心情下出現。它不是玩家擁有的家具，
  是「你不在的那段時間」的痕跡；痕跡不成立了，它就該消失。
- **島上的流浪狗（`PetDog.tsx`）沒有心情。** 牠是島的動物，不是玩家的，
  給牠一個因玩家離開而變化的狀態等於說玩家的缺席影響了不屬於他的東西。

### 12.1 跟 寵物照護 的關係（2026-08-31）

上面預留的「飢餓／活力」那條路已經被走過了，但走法跟這裡原本設想的不同，值得寫下來：

**照護狀態沒有變成新的 mood id，也沒有變成 `resolvePetMood` 的新輸入。**
它是 `PetLifeState` 上的一個**巢狀物件** `care`（`constants/petCare.ts`），跟 `mood` 並排，
因為兩者回答的是不同的問題：`mood` 是「你離開了多久」，`care` 是「你有沒有在餵牠」。
一個玩家可能天天上線但從不餵食，也可能餵得很好卻消失兩週——把兩者塞進同一條 mood 階梯，
就沒有辦法分辨是哪一個讓寵物安靜下來。

兩套系統的乘數用 `combinePetMotion()` **相乘**，誰也不覆蓋誰。`nestPull` 取兩者的較大值
（兩邊都是「牠想待在窩裡」，相乘會讓「又餓又被丟很久」的動物比「只是餓」的更少回窩）。

`applyDwell()` 已經被 `usePetBehaviour()` / `applyBehaviorSlot()` 取代（`Three/IslandPet.tsx`），
但這一節說的原則完全沒變：行為層仍然只是把心情變成**一個座標**，每一幀的跟隨、碰撞、
步態、提示都跟以前一樣。`PET_NOTICE_RADIUS` 現在是行為決策的 `ownerNearRest` 輸入，
「主人一走近就自己過來」依然是「覆寫停止作用的樣子」，只是覆寫換成了權重歸零。

窩也不再一定是屋旁那個痕跡：玩家買了「戶外寵物窩」擺下去，`lib/petRestingSpots.ts`
就會用那一個，而這裡的小窩／空食盆／玩具會讓位（見 `IslandOvergrowth.tsx` 的 `showNest`）。
完整說明在 `docs/pet-care.md`。

要再擴充心情／親密度／玩耍需求：如果它跟「離開多久」有關，加在 `PetLifeState` 上並讓
`resolvePetMood` 納入判斷；如果它跟「照顧得好不好」有關，加在 `PetCareState` 上。
**兩種情況都不要加新的 mood id，也不要在呼叫點加分支。**

## 13. 管理員測試

帳號中心 →「離線回歸測試」（需開啟 `管理員測試模式`）。
按鈕：12 小時／1／3／7／14／30 天／最大，以及重置。

兩端各有一個是刻意放的：**12 小時**正好是 `QUIET_HOURS`，它必須什麼都不長 ——
哪天改壞了變成過一夜就長草，除非有這顆按鈕，否則要等玩家回報才會發現。
**最大**（60 天）越過成長曲線的天花板，所以它顯示的就是這座島最糟的樣子；
如果那看起來像廢墟而不是「一個下午可以整理完的院子」，那就是數值調錯了。

面板上的讀數（荒廢程度／藤蔓生長／畫面色調）直接來自 `resolveIslandAmbience` ——
和畫面正在用的是同一個值，不是另外算一份。

### 第二排：畫面飽和（離線褪色）

按鈕：正常彩色／輕微褪色／明顯褪色／接近灰階／完全黑白／播放恢復／恢復完成。

和上面那排是**不同性質**的東西，所以分成兩排：上面那排會倒退 `lastSeenAt` 並真的寫存檔，
這排**什麼都不寫**。褪色是離線時數的純函式，而且從來不進存檔，
所以預覽只是把一個時數交給畫面層；按「恢復完成」或重新整理就結束，帳號不留任何痕跡。

五段的時數是用**正式曲線自己的反函數**（`hoursForColourDrain`）算出來的，
不是為了面板另外定義的假階段 —— 所以每一級都真的是某段離線時間會長的樣子。
（`ColourStageDef.previewDrain` 取的是該段的**中間**而不是邊界：邊界是最不適合示範一段區間的值，
而且「輕微褪色」的邊界在 `COLOUR_MIN_DRAIN` 以下，停在那裡會什麼都看不到。）

「播放恢復」是從**目前畫面上的程度**開始播，所以「先停在接近灰階、再看它恢復」是兩次點擊、
講的是同一段離線。演示期間可以照常走動、開 UI、進商店 —— 它不鎖任何操作。

按鈕做的是**把 `lastSeenAt` 倒退，然後跑正式的 `resolveIslandArrival`**，
不是另外畫一份結果。差別很重要：直接產生結果的捷徑是第二套實作，
正式那套壞掉的時候它還是會通過。

## 14. 測試

```
npm run test:offline-return
```

釘住的是需求本身：第一次進遊戲不算離線、成長單調且不跳崖、上限有效、
重複登入不會再長、整理過的不會被推翻、每一樣長出來的都清得掉、
每個心情都還會走路。

環境狀態的部分另外釘了四件事：

- **最糟的島仍然是亮的、有顏色的**（brightness ≥ 0.8、saturation ≥ 0.7）。
  這是「不要做成黑暗恐怖風格」寫成數字的版本 —— 以後不管誰重調，這條線都還在。
- **多一株草永遠不是一個看得見的事件**（單步 < 5%），也就是不會有硬切換。
- **整理完就完全恢復**：清空之後拿到的是同一個 `NEUTRAL_AMBIENCE` 常數本身。
- **偏好不會變成限制**：長時間離線真的會把島填滿，同時大多數還是長在角落。

離線褪色與恢復演示另外釘了：

- **沒有硬切換**：以「小時」為解析度掃過整條曲線，**畫得出來的**範圍裡沒有任何一小時
  的變化超過 1%。（門檻以下那段不計入 —— 冪次曲線在原點的斜率是無限大，
  第一個小時值 2%，但那整段都在 `COLOUR_MIN_DRAIN` 以下、根本沒有掛元素。
  把量不到的東西也釘住，只會逼著曲線為了一個沒人看得見的數字被調平。）
- **真的到得了全黑白**，而且到了就停在那裡（不是無限逼近、也不會反過來）。
- **一天內回來完全沒有效果**，兩天才開始 —— 每天上線的玩家看不到這套東西。
- **恢復從全灰開始、在正中間結束於 1.0**：最後一幀是真正的無作用，卸載時不會閃。
- **bloom 領先**：動畫 30% 時中央已經有顏色而其餘部分還是灰的，
  否則「色彩擴散」會退化成「亮度滑桿」。
- **中途離開是合法狀態**：沒有東西要對帳，下一次一定更淺。
- **管理員的每一級都 round-trip 回真曲線**，所以面板不會示範一個不存在的世界。
