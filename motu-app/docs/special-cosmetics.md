# 特殊效果飾品 — Special Cosmetic Effects

「有生命感的特殊飾品」，而不是「身上掛著大量 Particle 的飾品」。

這份文件說明系統怎麼組成、加一件新飾品要動哪兩個檔案，以及為什麼有些看起來多餘的限制其實
是刻意的。程式碼裡的註解寫的是「為什麼」，這裡寫的是「在哪裡」。

---

## 一、系統長什麼樣

```
constants/cosmeticEffects.ts    目錄（DATA）：有哪些飾品、掛在哪、怎麼動、放什麼
constants/petRig.ts             寵物的掛點（等同 characterRig.ts 之於玩家）

components/Three/effects/
  particleShapes.ts             十五種粒子外形 + 每種的池子大小、透明度、要不要旋轉
  cosmeticRuntime.ts            粒子池、生物池、唯一的 update；沒有 React
  EffectField.tsx               每個 Canvas 掛一個：池子的 mesh + 唯一的 useFrame
  CosmeticModels.tsx            二十二件飾品本體（低模）
  CreatureMeshes.tsx            蜜蜂與蝴蝶
  SpecialCosmetic.tsx           掛點 + 模型 + 註冊，給身體部位 render 的東西
```

整個系統對外只有兩個接觸點：

- **身體部位** render `<CosmeticSlot socket="…" …/>`（角色的頭、身體，寵物的頭、脖子、背）
- **每個 Canvas** 包一層 `<CosmeticEffectField>`

其他檔案一行都不用改。

### 2026-08-20 的「精緻化」改版

需求是「特殊飾品看起來太樸素，跟價格不匹配」，而且明講了**不要只把粒子數量乘十**。所以這次動的是
四層，粒子只是最後一層：

| 層 | 做了什麼 | 在哪 |
|---|---|---|
| 飾品本體 | 每件玩家飾品從 3～13 個 mesh 長到 12～28：多層結構、小寶石、緞帶、葉片、藤蔓、齒輪、翅脈、邊緣細節 | `CosmeticModels.tsx` |
| 材質 | 半透明膜、emissive 小件、金屬感杯口、玻璃泡泡的折射高光 | 同上 |
| 動態 | **`motion.parts`**：模型標記子 group，catalog 說它怎麼動。軌道、齒輪、花朵各自搖、四片翅膀差半拍 | `cosmeticEffects.ts` + `cosmeticRuntime.ts` |
| 粒子 | 四種新外形（`crystal`/`snow`/`drop`/`wisp`）＋四個新欄位（`gravity`/`wobble`/`rare`/`cadence`） | `particleShapes.ts` + 上面兩個 |

**一件飾品的 mesh 數量可以這麼大方，是因為 `SpecialFx` 只有一格。** 畫面上最多同時出現「玩家一件
＋寵物一件」，不是十四件。所以幾何細節的預算可以花在模型上，而**會隨穿戴人數增加的粒子**仍然照舊
池化、照舊兩層上限。實測整個角色連飾品是 **17～61 個 draw call**，最重的是花環足跡的 75——那件是
一整圈花。

**四層裡最關鍵的是第三層，不是第四層。** 「更華麗」如果只加粒子，得到的是同一個東西外面沾更多亮
片；讓飾品**自己有會分別動的零件**，才是「一個小型視覺系統」跟「一個模型加特效」的差別。

### 資料怎麼流動

```
profile.equippedItems (string[])
      │  resolveSpecialCosmetics(ids, 'player' | 'pet')   ← 用 item id 查表，不比對名稱
      ▼
SpecialCosmeticDef[]
      │  CharacterOutfit.specials  /  PetDog 的 useMemo
      ▼
<CosmeticSlot socket=…>  →  <Attachment point=…>  →  <group ref>  →  <Model/>
                                                          │
                                                          │ runtime.register(def, group)
                                                          ▼
                                            CosmeticRuntime（一個 useFrame）
                                              ├── 寫 group 的 rotation/position/scale（Mesh Animation）
                                              ├── 到時間就從共用池子拿粒子（世界座標）
                                              ├── 到時間就從三隻的池子放一隻蜜蜂／蝴蝶
                                              └── 每 0.5 秒檢查一次玩家↔寵物同系列 Bonus
```

## 二、加一件新飾品

兩個檔案，沒有第三個：

1. **`constants/items.ts`** — 一筆商品（`shopCategory: 'SpecialFx'` 或 `'PetGear'`）。
2. **`constants/cosmeticEffects.ts`** — 一列 `SpecialCosmeticDef`：id、系列、掛點、模型 key、
   `effect`。

如果要新的外觀，再加：

3. **`components/Three/effects/CosmeticModels.tsx`** — `COSMETIC_MODELS` 多一個 entry。
4. **`components/SpecialCosmeticIcon.tsx`** — `GLYPHS` 多一個 entry（商店圖示）。

**不需要**：新的 component、新的 useFrame、新的 particle system、新的 socket（除非真的掛在
身上沒有過的地方）、任何 `if (item === …)`。

`cosmeticEffects.ts` 在 module load 時會對照 `items.ts` 檢查兩邊有沒有對上，漏掉會直接丟
Error，而不是安靜地變成「買了看不到」。

**加完跑 `npm run audit:cosmetics`。** 它把這份文件裡寫成數字的預算真的算一遍：每個 emitter 的
穩態存活數（`count × lifetime / interval`，`cadence` 會按工作週期折算）、每顆粒子會長到的最大
半徑、以及每種外形的池子用量。超標就 exit 1。

這個腳本存在的理由本身就是一課：**穩態存活數的公式在文件裡寫了好幾週，而沒有人跑過它**——所以
大多數 emitter 一直待在「不到一顆存活」的狀態出貨。寫得下來的東西就應該跑得起來。

它**不會**告訴你飾品好不好看，這點很重要。這套系統踩過的每一個美術坑——讀成單眼鏡片的環、讀成
蜘蛛腳的三道貝殼紋、夜裡整個變黑的夜用光環——都是**畫出來看**才發現的。腳本管的是對或錯，
`tmp-cosmetic-preview.tsx` 管的是好或不好。

## 三、可以配置什麼

`CosmeticEffect` 有三塊，都是選填。沒有填 = 那件飾品就是普通飾品（這就是「無特殊效果」，
不是特例分支）。

### `motion` — Mesh Animation（優先用這個）

| 欄位 | 效果 |
|---|---|
| `sway` | 單軸鐘擺搖晃 |
| `bob` | 上下浮動 |
| `spin` | 持續旋轉 |
| `pulse` | 整體縮放呼吸 |
| `flap` | 成對翅膀拍動（唯一會驅動模型自己零件、也唯一會看玩家在做什麼的） |

前四種都是「共用時鐘的純函數 + 每件飾品自己的相位」，不是每幀累加。累加會讓幅度跟著螢幕更新率
跑掉，而且會永久漂移 —— 這是 `Fireflies.tsx` 已經踩過一次的坑。

**`flap` 是唯一的例外，而且是刻意的。** 它的速度會隨著玩家起步而改變，`sin(時鐘 × 速度)` 在速度
改變的那一瞬間會跳到曲線上完全不同的位置 —— 翅膀會在每次起步時「卡」一下。所以只有它累加相位。
上面那條規則要防的漂移在這裡不可能發生：相位只餵給一個 sine，輸出永遠有界，而 `delta` 上游已經
夾過了。漂移的「位置」會跑到身體外面去，漂移的「相位」只是停在拍翅的另一個瞬間，看不出來。

#### `parts` — 讓模型自己的零件分別動（2026-08-20）

前面五種動作都寫在飾品的**那一個 group** 上。一個 transform 只能說「這個東西在動」，說不出：

- 三顆小星星以不同半徑繞著髮飾
- 音樂盒裡兩個齒輪反向、不同速轉
- 花冠上四朵花各晃各的
- 一朵大雲旁邊兩朵小雲慢慢飄

以前這些都只能新開一個 component 配一個 useFrame——正是這套系統存在的理由要消滅的東西。現在模型用
`COSMETIC_PART` 標記子 group，catalog 說每個 tag 怎麼動：

```tsx
// 模型
<group userData={{ [COSMETIC_PART]: 'orbit' }} rotation={[Math.PI / 2, 0, 0]}>
  <mesh position={[0.082, 0, 0]}>…</mesh>   {/* 半徑寫在幾何裡 */}
</group>
```
```ts
// catalog
parts: [{ tag: 'orbit', spin: { axis: 'y', speed: 0.5 }, stagger: 0.333 }]
```

三件事值得記：

- **一個 tag 是一個集合，不是一個物件。** 三顆星星共用 `orbit`，`stagger`（單位是**圈**）把相位
  平均散開。所以「三顆等距繞行」是一行 config，不是三行。
- **「軌道」不是一個欄位。** 模型把飾品放在 tagged group 裡的某個半徑上，runtime 轉那個 group，
  就是繞圈。半徑留在幾何裡（它本來就屬於那裡），runtime 一行都不用懂。three 的 Euler 'XYZ' 是
  Rx·Ry·Rz，所以在 group 上先寫一個 `rotation.x`，就會把 runtime 的 Y 旋轉**傾斜**成另一個平面——
  星星髮飾就是靠這個讓衛星在頭的**表面**掠過而不是穿過頭骨。
- **基準姿勢是被記錄下來的，不是被覆蓋的。** 最上層 `MotionSpec` 可以寫絕對值，是因為飾品自己那個
  group 從 identity 開始（socket 的 transform 在上面那層）。子 group 沒有這個保證——花在圈上有自己
  的角度、齒輪在盒子裡有自己的位置——所以這些曲線是**加在**模型畫出來的姿勢上，那個姿勢在 register
  時抓一次。
#### `flap` 要有兩個零件才會動

其他所有動作都寫在飾品的那一個 group 上，而一個 transform 表達不出「拍動」—— 兩片翅膀必須反向
轉，否則就是整個物件在左右搖。所以模型自己用 `userData` 標記兩個子 group：

```tsx
<group userData={{ [COSMETIC_PART]: 'wingL' }}>…</group>
<group userData={{ [COSMETIC_PART]: 'wingR' }}>…</group>
```

runtime 在 register 的時候 traverse 一次找出來、存在 entry 上，之後每幀直接寫。沒有標記的模型
配上 `flap` 就是不會拍 —— 一樣是「沒有 config 就是沒有效果」，不是特例分支。

`flap` 有兩組數字（站著／移動中），runtime 用一個 ~0.35 秒的 `moveBlend` 在兩者之間漸變，所以
起步時翅膀是「張開」而不是「彈開」。而且它同時寫兩軸：**Z 是上下拍、Y 是前後掃，兩者差 90 度相位**，
翅尖畫的是一個 8 字而不是一條斜線。

**為什麼前後掃反而是主角**：這是個大頭角色，0.26 的頭骨罩住整個上背，所以純上下拍的最高點會把
兩片翅膀送到頭後面完全看不見（第一版就是這樣，看起來像沒穿）。往上是背部飾品在這個角色身上唯一
不能用的方向。

**四片翅膀**：`secondaryLag` 會另外驅動 `wingL2` / `wingR2`，相位落後前翅一個指定的弧度。昆蟲的
前後翅本來就不同步，而**那個落差就是「像一隻蟲」的全部**——同相會看起來像一片厚翅膀，反相看起來
像壞掉。四分之一拍（約 1.5 rad）是實際會讀成動物的值。蝴蝶髮夾與昆蟲之翼都用這個。

**扁平的形狀不要用 `spin`。** 星星是壓扁的八面體，繞 Y 軸整圈轉會有兩次側面對著鏡頭，變成一
根細片。星星髮飾與星星項圈都改成 ±20° 的 `sway`，一樣有轉動反光，但正面永遠對得到。

### `emit` — 粒子（配菜，不是主菜）

十五種外形：`star / leaf / petal / bubble / spark / spore / heart / mote / feather / ring / note`
＋ 2026-08-20 加的 `crystal / snow / drop / wisp`。除了 `ring` 與 `drop` 以外每種都會拿到一個隨機
朝向，而且全部都是 4～60 個三角形的實體 mesh，不是 billboard sprite —— 一片從花冠掉下來的葉子是離
鏡頭一公尺的實體物件，糊掉的光點在那個距離只會看起來像鏡頭髒了。

新的四種各自解決一件舊外形做不到的事：

| 外形 | 為什麼不能用既有的 |
|---|---|
| `crystal` | 細長、兩端都是尖的雙錐。`spark`（矮胖的四面體）是「一小塊燒著的東西」，這個是「從晶面長出來的東西」。冰與火在同一個貨架上，兩者的比例必須差得夠遠。 |
| `snow` | 六角雪花，一條輪廓擠出來的。全套裡唯一「一眼就認得出來」的形狀。刻意不用三根交叉的長條——那樣三倍的幾何全堆在最看不見的中心，而且末端是方的。 |
| `drop` | 車製的水滴，**尖端朝上**，而且是第二個 `SHAPE_FLAT`。理由跟漣漪一樣：會翻滾的水滴不是水滴，是種子。原本雨是用 `bubble` 代打的，一整場雨看起來像一串珠子。 |
| `wisp` | 壓扁的軟團，alpha 0.34，通常配 `grow`。全套裡唯一是拿來**看穿**而不是看的——霧、煙、雲氣、霜靄。它是「這個效果需要周圍有空氣」的答案，而那個問題本來只會用「把 count 調高」來回答。 |

重要欄位：

- `interval` 以秒為單位。**能見度調整（2026-08-20）後是 0.75～3.8 秒**，原本是 2～9 秒。

  改的理由是量出來的，不是喜好：穩態存活數 ≈ `count × lifetime / interval`，而原本大多數環境型
  emitter **不到 1** —— 星星髮飾 0.84、森林花冠 0.45、寵物蝴蝶結 0.27。「克制」跟「大部分時間
  什麼都沒有」是兩件事，而出貨的是後者。現在落在 2.5～6 之間。

  **環境型砍最兇（×0.42），移動觸發的軌跡型只放寬到 ×0.7** —— 那些本來就在 1.1～1.8，它們從來
  不是問題，再砍半才真的會變成滿屏粒子。**下限 0.75 秒，應該守住。**
- `maxAlive` **必填**，是這個 emitter 的硬上限。到上限就整個跳過這次，不會排隊、不會補發。
- `trigger`：`always` / `moving`（只有移動中才出）/ `night`（只有天黑才出）/ `swimming`
  （只有玩家在水裡才出）。`swimming` 讀的是 `playerBus.isSwimming`——游泳動畫本來就在發佈這個旗標，
  所以「游泳時加強水元素」的成本是一次屬性讀取。**它不可能影響游泳姿勢**：emitter 只讀身體的世界
  座標，從來不寫身體，所以需求裡的「不要影響游泳動畫」是結構上成立的，不是靠小心。
- `movingScale`：移動時把 `interval` 乘上去，`< 1` 就是走路時多一點（泡泡髮飾用這個）。
- `orbit`：把 `drift` 從直線變成繞圈，數字是「一生繞幾圈」（星星項圈用這個）。
- `settle`：**粒子在生命的第幾成停止移動、留在世界原地**，剩下的生命就只是原地淡出。這是把
  emitter 變成 **trail** 的那個開關 —— 沒有它，粒子消失的那一刻還在動，所以走遠的人身後拖著一
  條會跟著跑的糊影；有了它，羽毛掉完就停在被丟下的地方，那個「靜止」才是玩家讀成「我從那邊走來」
  的東西。成本是既有位置曲線上多一個 clamp，沒有新的池子、沒有新的 draw call。
- `grow`：**生命結束時的大小是出生時的幾倍**。所以 `size` 是「一開始多大」，而這個欄位是讓一顆
  粒子可以是**一道波**而不是一個物件的唯一開關 —— 漣漪就是一個在你看清楚之前已經大三倍並且消失
  的圈。它吃的是原始的生命比例，**刻意不吃 `settle` 壓縮過的行進曲線**：settle 的粒子停止**移動**，
  grow 的粒子在淡出的同時繼續**擴散**，這是「東西落定了」跟「波經過了」的差別。

**2026-08-20 加的四個欄位。** 它們共同的性質是：都不需要新的池子、新的 draw call 或新的迴圈，每一
個都是既有位置曲線上多一項，或生成時多一次 roll。

- `gravity`：**拋物線**，疊在 `rise` 的直線爬升上。兩個一起才是重點——單靠 `rise` 是「一個被往上帶
  的東西」，對泡泡是對的，對任何被**丟出去**的東西都是錯的。火星離開火焰時快、變慢、翻過來、掉回
  去，那個形狀是 `rise: 0.34, gravity: 0.3`，而它**不可能**由 rise 與 drift 的任何組合表達，因為那
  兩個都是單調的。跟 `settle` 吃同一條行進曲線，所以落地的火星會停在原地而不是穿進島裡。
- `wobble`：**橫向擺動**，垂直於粒子自己的行進方向，相位取自它出生時的隨機角度（`orbitPhase`，沒有
  orbit 時本來就沒人讀）。所以一次噴六片雪花會各飄各的，而不是整團一起晃。雪花飄、音符左右搖、泡泡
  不走直線都是它。到 `settle` 點會跟著凍結——停在半空卻還在擺的葉子看起來像吊著線。
- `rare`：**每顆粒子 roll 一次**的「偶爾比較大的那顆」。可以覆寫 size / lifetime / opacity /
  colors / grow / tumble。
  **為什麼不是第二個 emitter**：第一版就是那樣做的，而它比較差——兩個獨立計時器會漂開，大顆的那個會
  落在小顆的**空檔**裡，玩家看到的是兩個無關的效果而不是一個效果裡的重音。per-particle roll 保證大
  的那顆生在一小撮小的**裡面**，那才是「一把星塵，其中一顆是真的星星」。
  `grow` 小於 1 是這裡最有用的一招：結霜光環的大冰晶用 `grow: 0.25`，一邊淡出一邊縮到剩四分之一，
  這就是「慢慢碎裂消失」而完全不需要碎裂的幾何。
- `cadence`：**間歇發射**——開 `on` 秒、停 `off` 秒，兩邊都有 jitter。需求寫的是「偶爾下幾滴小雨然後
  停，不要一直下雨」，而**檔案裡原本沒有任何東西能表達這件事**：其他所有速率控制調的都是「多久發一
  次」，所以無論怎麼設，結果都是某個密度的**持續**毛毛雨。一場雨有開始也有結束。跟 `burst` 刻意不
  同：burst 回應的是玩家造成的一個瞬間，cadence 是天氣，沒有人要求它。

#### `ring` 是第一個「方向有意義」的外形

其他九種從任何角度看都對，所以 runtime 可以放心給每顆粒子一個隨機朝向（八顆星星才不會看起來
像同一張貼圖的八份拷貝）。躺平的圈不行。所以「不會轉」是寫在**外形**上的
（`SHAPE_FLAT`），不是寫在 emitter 上 —— 沒有任何 config 應該有辦法把一道地面漣漪立起來。

注意這跟 `tumble: 0` 是兩件事：沒有 tumble 的粒子**仍然**帶著出生時那個隨機朝向。
- 距離全部是**世界座標的世界單位、沿世界軸**，不是掛點的本地座標。玩家 root 畫在 2.25 倍、
  狗畫在 0.4 倍，用本地座標會讓同一組數字在寵物身上小六倍。

### `burst` — 事件觸發的一次性爆發

其他所有效果都是**環境**的：跑在一個 interval 上，目標是「不用盯著也會注意到」。那是對的預設，
也正是為什麼整組看起來音量一樣 —— 裡面沒有任何一件事情能成為**事件**。

`burst` 是另外一半。它平常完全不吐東西，等玩家做了某件事才發射，而且允許很大聲：一次 10 顆，
是任何 emitter 上限的五倍。克制從「粒子很少」換成「很少發生」，靠的是 `cooldown`。

目前唯一的 `on` 是 `'jump'`，讀的是 `playerBus.playerIsAirborne` 的**上升緣**（跳躍或後空翻都算）。
這個緣在 `tick` 裡整場只算一次，不是每件飾品各存一份上一幀的值 —— 兩份會在變化的那一幀不同意。

刻意**不是**一種 `EffectTrigger`：trigger 是在調節一個速率，而 burst 沒有速率。

### `glow` — 真的光源（唯一會改變場景、而不是加東西到場景裡的效果）

其他每一種效果都是「愈多愈便宜」：粒子共用十個 InstancedMesh、生物共用三個位置，一百個人穿戴
的成本跟一個人一樣。**光源剛好相反**。一盞動態光不是場景裡的一個物件，它是場景裡**每一個被照亮
的 fragment 的著色器裡多出來的一項**，多加一盞就重新對地形、房子、島上每一個人再算一次 —— 不只
是對穿戴者。

所以一件 `glow` 飾品**不會拿到一盞燈**，它只是成為 `GLOW_POOL_SIZE`（**2**）盞燈的**候選人**，
離鏡頭最近的兩個贏。十個發光的玩家跟一個一樣貴，最遠的那些就淡出 —— 反正距離本來也會把它們的
光衰減掉。

交接是三步，順序就是全部的設計：**保留**（還符合條件的擁有者不重新考慮，兩個距離相近的人才不會
讓燈每幀在他們之間閃）→ **釋放**（不再符合條件的先淡到 0，燈是在原地熄掉而不是啪一聲關掉）→
**認領**（只有已經全黑的空位才接受新的擁有者，否則燈會帶著剩下的亮度瞬移過去）。

**強度是量出來的，不是算出來的。** three 0.184 沒有 legacy light 模式，point light 的
intensity 是燭光、irradiance 是 `intensity / d^decay` —— 這個數字在放進它要照的場景之前沒有意義。
精靈光環在島上的午夜環境光（約 0.22）底下實拍過 1.7 / 6 / 14 / 30 / 60：**低於約 6 地面完全沒有
變化，到 30 光池已經過曝**，最後定在 16。房子室內的跟隨燈寫 2.2 卻亮得多，是因為它用 decay 1.3
—— 差別在**指數**不在強度，這兩個數字不能互相抄。

還有一個硬限制：**點光源必須留在頭骨外面**。第一版把燈掛在光環下方 0.5 個世界單位，想說那是臉的
高度會照到臉，結果掛進了半徑 0.585 的頭球裡面，照亮了頭的內側然後什麼都沒有。

### `ground` — 躺在地上（`aura` 掛點靠它才成立）

其他每一件飾品都是「穿在身上」，所以身體的 transform 正好就是它要的：髮夾本來就該跟著頭轉。**畫在
地上的圈剛好相反** —— 它屬於地板，而且有兩個身體解決不了的問題。

**一、它不能繼承身體的方向。** 角色走路會 yaw、匍匐時整個趴平；跟著做的地面圈會變成一個立起來的
輪子。所以 runtime 把這件飾品的 local rotation 寫成
`parentWorld⁻¹ · tilt` —— 把身體正在做的事**抵銷掉**，換成它自己選的世界方向。其他每一件飾品要的
都是相反的，而它們什麼都不用做就有了。

> 因此掛在 `aura` 上的模型必須**畫成平的（XZ 平面）**，而且**不能有正面** —— 它不會跟著角色轉，
> yaw 0 是世界的北方，不是角色面對的方向。

**二、它必須跟著坡度。** 島不是平的。躺在世界 XZ 平面上的圈會切進每一座山的上坡側 —— 這正是做
精靈光環時把 `aura` 往後放的原因：**要做的從來不是加一個掛點，是地形**。runtime 在穿戴者周圍四個
點取地面高度、擬合一個平面、把圈斜到跟它一樣。

```
radius   取樣半徑（世界單位）
lift     離地多高（3 公分，是防 z-fighting 的餘裕，不是高度）
maxTilt  斜度上限；超過就不再跟，讓它平著浮著
```

**它擬合的是一個平面，不是那個表面。** 平滑的坡上會貼齊；跨在台階或大石頭上會有一邊浮起來。這是
刻意停在這裡：逐頂點貼合等於每幀對著高度場變形網格，而它買到的東西（圈沿著石頭彎）在這個尺寸看
不出來。`maxTilt` 就是給近似失敗的那個情況（懸崖邊）用的 —— 誠實的答案是停止傾斜、讓它浮著，而
不是把圈立成一個輪子。

**這個函式絕對不能讀自己寫出去的東西。** 它每幀寫 group 的 position，所以取樣點必須來自
**父物件**（Attachment group，而 aura 的錨點是 root 的 (0,0,0)，也就是腳的接地點），不能來自
group 自己。第一版讀了自己，產生兩個看起來無關的 bug：

- **平地上會往上爬。** 沒有地形取樣器時（屋內、更衣室）fallback 拿 group 自己的 y 當地面高度
  —— 而那個 y 已經是「上次的地面 + lift」了，所以每取樣一次就再加一個 lift。實測 5 秒往上飄
  0.59 個世界單位。
- **游泳後會跑掉。** 游泳會讓角色 root 帶 pitch，而在傾斜的父物件底下，一個世界垂直的位移換算成
  local 會**帶有 x 與 z 分量**。讀回自己就等於在偏移後的點取樣、再寫出更大的偏移，每幀複利 ——
  所以圈會離開穿戴者，上岸之後還留在原地。

改成讀父物件之後兩者都是**精確 0 漂移**（實測：63 度 pitch 加斜坡，5 秒後圓心仍在角色的 (0,0)）。

**兩個踩過的單位陷阱：**
- `radius` 是**世界單位**（跟這個檔案裡其他距離一樣），而模型是畫在 **character-local**（2.25 倍）。
  兩者要手動換算，第一版沒換：模型 local 半徑 0.62 是世界 1.4，而 radius 填 0.62，等於拿不到一半
  大小的一塊地去擬合整個圈。
- 取樣**不是每幀**。一次擬合要五個 lookup，每個都是地形查詢加一輪場上所有擺放物；而且走過台階時
  地面是跳變的，60Hz 追著跑會頓。8Hz 取樣 + 緩動，比認真做還便宜也還平滑。

### `creature` — 低模生物

蜜蜂與蝴蝶。從飾品飛出來、繞主人一圈、淡出離開。全場最多三隻（`CREATURE_POOL_SIZE`）。

`scale` 就是牠的翼展（世界單位）—— mesh 本身是照 1 單位畫的，所以 `1.0` 是一隻一公尺寬的
蝴蝶。目前是蝴蝶 0.13、蜜蜂 0.09。

軌道圓心在**出生的瞬間就固定**，之後不追著主人跑。追著跑的蜜蜂會在狗開始跑時整隻橫移，那不是
蜜蜂會做的事。

## 四、玩家 ↔ 寵物同系列 Bonus

玩家與寵物戴同一個系列、而且靠得夠近時，會有一次短暫的加成。

三個限制各對應需求裡的一句「不要」：

| 常數 | 值 | 擋掉什麼 |
|---|---|---|
| `BOND_RADIUS` | 2.2 世界單位 | 擦身而過不算 |
| `BOND_COOLDOWN` | 9 秒 | 「不要永久觸發」 |
| `SERIES_BONDS[series]` | 中間 1 顆大的 + 各自旁邊 2 顆小的 | 「不要大量生成」 |

檢查本身每 0.5 秒跑一次，不是每幀 —— 兩個人走近彼此不需要 60Hz 的解析度。

只有**同時有玩家飾品也有寵物飾品**的系列才會在 `SERIES_BONDS` 裡；目前是 **starlight、forest、
flower、cloud、ocean、music 六組**，全部實測發射過。沒有登記的系列就是不會 bond，不是壞掉
（bubble、campfire、butterfly、honey 目前都只有單邊，2026-08-20 加的 **frost** 也是——它只有玩家那
一件結霜光環）。注意斷言只擋一個方向：**登記了 bond 卻只有單邊會直接丟 Error；兩邊都有卻還沒設計
bond 是合法的**，否則「幫既有系列加一件寵物飾品」就會變成破壞性改動。

### flower 的那一條一直是死的

這份文件與程式碼原本都寫著「flower（蝴蝶結 ↔ 花朵項圈）」—— 而**那兩件都是寵物飾品**。bond 要的是
一件看得見的玩家飾品加一件看得見的寵物飾品（`CosmeticRuntime.sharedSeries`），所以只有寵物那半邊
的系列永遠湊不出來。它在表裡看起來像做好了，而且**什麼都不會壞**：檢查照跑，只是永遠沒有配對成功，
症狀跟「這兩隻從來沒靠近過」一模一樣。

它是把六個系列一個一個推進 bond、數粒子才發現的。所以現在 `cosmeticEffects.ts` 結尾多了一個
**module load 時的斷言**：登記在 `SERIES_BONDS` 裡的系列，必須同時存在玩家與寵物飾品，否則直接丟
Error。反過來**不檢查** —— 「兩邊都有但還沒設計 bond」是合法狀態，把它變成錯誤會讓「幫既有系列加一
件寵物飾品」變成破壞性改動。

**flower 已經救回來了** —— 缺的那件玩家花系飾品就是 **花環足跡**，所以那一組現在真的能發，六組
到齊。而斷言還在：如果哪天玩家那半邊又被拿掉，它會在 module load 就丟 Error，而不是悄悄變回
「看起來做好了、永遠不會發」。

雙方都必須**看得見**才算數 —— bond 是「你看到兩個角色之間發生了什麼」，第一人稱把角色藏起來
時不該在半空中放一顆星星。

## 五、效能：兩層上限，一個迴圈

- **一個 `useFrame`**（`EffectField`），不管場上有幾件飾品。
- **粒子只配置一次**。「生成」是拿一個死掉的 slot，「死亡」是還回去；執行期不 new、不 destroy。
- **兩層上限**，因為它們擋的是不同的失敗：
  - `maxAlive`（每個 emitter）讓**一件**飾品保持克制；
  - `SHAPE_POOL_SIZE`（每種外形，全場共用）讓**一群人**保持便宜。
  - 超過任何一層的生成都直接**丟掉**，不排隊。
- **看不到就不生成**。`isEffectivelyVisible()` 會往上走 parent chain，所以被第一人稱藏起來的
  角色、或不在畫面上的 view，完全不會發射。
- **沒有東西活著時整組不畫**：`mesh.visible = false`，0 draw call。
- 一種外形一個 InstancedMesh。實測（SwiftShader，空場 24 draw call / 9.4k 三角形為基準）：
  **一個穿戴者 +6 draw call、+8.2k 三角形；六個發光穿戴者只比一個多 5 個 draw call**。
  這就是池化設計的重點 —— 成本跟著**外形種類**走，不跟著人數走。
- **2026-08-20 的精緻化改版把模型加厚了，但沒有動上面那條。** 加的是每件飾品自己的 mesh 數（3～13
  變成 12～28），而那個成本**不跟著人數走也不跟著飾品數走**——`SpecialFx` 是一格，所以畫面上最多是
  「玩家一件＋寵物一件」。實測整個角色連飾品在 17～61 draw call 之間（花環足跡 75，那件是一整圈
  花）。粒子那一半完全沒有放寬：兩層上限還在，最擁擠的外形是 `ring`（13／22）與 `wisp`（12／26），
  而那是**假設每一件飾品同時被穿上**才會到的數字。
- **`motion.parts` 的成本是每個被標記的 group 三次浮點寫入**，在一棵本來就存在的樹上。全目錄最多的
  是花環足跡的三朵蘑菇與精靈光環的四個 tag，都在個位數。- **兩層上限現在是可執行的**：`npm run audit:cosmetics`。它同時擋住三件用眼睛看不出來的事——
  低於 0.75 秒的發射間隔（`cadence` 會先按工作週期折算，否則那個欄位會被自己的下限禁用）、
  超過尺寸天花板的粒子、以及**比自己穩態存活數還低的 `maxAlive`**（那不是上限，那是偽裝成上限
  的速率限制器）。
- **會相乘的欄位必須當成乘積來檢查。** `rare.size` 乘在已經 roll 好的尺寸上，而 `rare.grow`
  **取代** `grow`（不是疊上去）。0.072 × 1.7 × 1.7 是一顆 0.21 世界半徑的泡泡——42 公分，比半顆頭
  還大——而**兩個係數單獨看都沒有問題**。這個腳本第一版自己也弄錯了方向，回報了一個不存在的
  3.3 單位漣漪：**與 runtime 模型不一致的檢查器，回報的假失敗跟真失敗一樣耗注意力。**
- 完全不碰 React state，所以任何飾品都不可能造成 re-render。

### 為什麼是 InstancedMesh + 自訂 alpha

`instanceColor` 可以給每顆粒子自己的顏色，但每顆粒子還要按自己的節奏淡出，而
`material.opacity` 是整個 mesh 共用的。所以 `EffectField` 用 `onBeforeCompile` 塞了一個
`aAlpha` instanced attribute（配 `customProgramCacheKey`，否則 three 會把編好的 program 存到
標準 MeshBasicMaterial 的 key 底下）。

另外三條路都比較差：一顆一個 material（每種外形 32 個 draw call）、用縮到 0 代替淡出（粒子
會「縮走」而不是「化掉」）、整個自寫 ShaderMaterial（就失去跟場景其他東西一致的霧與色彩管理）。

## 六、不能影響操作（需求第五節）

- 粒子池與生物池的 `raycast` 都被覆寫成空函式。所以飄過鏡頭與 NPC 之間的粒子**不可能**擋住
  互動判定、也不可能吃掉點擊 —— 對遊戲裡每一個 raycaster 來說它們根本不存在。
  （驗證：1082 幀、對準每一顆活著的粒子與每一隻生物發射射線，命中數 0。）
- 尺寸上限約 0.09 世界單位、透明度上限約 0.8，都不足以擋住一張臉。
- 沒有 collider、沒有 physics、沒有碰到 camera。飾品本身是掛點底下的子物件，跟著角色走；
  它吐出來的東西在世界座標，不跟著走。

## 七、掛點

### 玩家（`constants/characterRig.ts`，character-local 單位，頭是 0.26 半徑的球）

| socket | 位置 | 說明 |
|---|---|---|
| `hairPin` | `[0.215, 0.075, 0.12]`, yaw 0.9 | 太陽穴上方的頭皮表面。長度 0.257 對 0.26 的球 —— 剛好貼著。 |
| `crown` | `[0, 0, 0]` | 頭骨中心，給環狀的花冠。**故意不共用 `hat`**：帽子跟花冠是可以同時擁有的兩格。 |
| `charm` | 身體 `[0, 0.06, 0.02]` | 領口下方的胸前。**故意不共用 `neck`**：理由同上。 |
| `back` | 身體 `[0, 0.045, -0.132]` | 肩胛骨，給披風與翅膀。掛在**軀幹關節底下**而不是 root，所以會跟著呼吸、走路傾斜與落地下蹲一起動。 |
| `halo` | 頭 `[0, 0.33, 0]` | 頭頂**上方**約 16 公分。唯一一個**刻意不貼著身體**的掛點，也因此是唯一一個帽子不會干涉的。間距是照「離頭頂多遠」給的，不是照絕對高度 —— 頭比較小的模型要保住同樣的視覺間距，而不是把光環戴成帽子。 |
| `ankle` | 腿 `[0, -0.19 - LEG_LENGTHEN, 0]` | 腳踝，鞋子上緣之上。**由「腿」自己 render**，所以一列 config 就是兩隻腳各一個，而且各自跟著自己那條腿擺 —— 兩邊不同步是白拿的，走路週期本來就分開驅動兩個關節。對照星軌之翼：那對翅膀因為掛在背上同一個掛點，得自己造一對、自己驅動。 |
| `aura` | root `[0, 0, 0]` | **地上**。root 原點就是腳的接地點，所以這個掛點是零，剩下的由 runtime 寫 —— 見下面的 `ground`。 |

`back` 是這個角色身上唯一必須**繞著頭去畫**的掛點：0.26 的頭骨罩住整個上背，任何從肩胛往正上方
長的東西都會穿過去。所以掛在這裡的東西要先往**外**、再往上，而且靠整組往後仰 0.3 rad 在**深度**上
取得餘裕 —— 在這個角色身上，高度是沒有餘裕可拿的。

`hairPin` 在 `crown` 的環（y 0.14）**底下**，所以同時戴不會穿模。

### 寵物（`constants/petRig.ts`，**每個品種一組**）

飾品掛在**玩家買的那隻寵物**（`Three/Pets.tsx` 的 `PetModel`）身上，不是島上那隻流浪狗
（`PetDog.tsx`）—— 流浪狗是「你還沒有寵物時陪著你的那隻」，寵物飾品是你打扮**自己**的夥伴。

一條規則讓一個蝴蝶結同時合身於九隻動物：

> **socket 是「那個部位的中心」，它的 `scale` 就是那個部位的半徑。**

所以飾品是畫在 **UNIT-PART 空間**：`y = 1` 就是頭頂，`radius 1.15` 就是比脖子粗 15% 的圈。
臘腸的窄頭骨、紅貴賓的毛球、金絲雀的小頭，同一個模型都對得上，`CosmeticModels.tsx` 裡一個
per-breed 的數字都沒有。

位置本身寫在 UNIT-PET 空間（`Pets.tsx` 畫每隻動物的空間：腳站 y=0、頭頂 y≈1、面向 +Z），
每個品種一組，因為那是量出來的：

| socket | 說明 |
|---|---|
| `petHead` | 頭骨中心。帽子、蝴蝶結。 |
| `petCollar` | 項圈的圈。**不是**脖子中心 —— 這裡每隻都是大頭，柴犬的 0.29 頭骨把整個脖子吞掉了，圈畫在脖子上會 100% 埋進去。所以圈的大小是照**身體斷面**算的，位置往下往後退到頭骨外面。 |
| `petBack` | 背上真正**空的**那一段。不是身體中心（那裡是尾巴），也不是肩膀（那裡是頭）。每個品種的空隙位置不同，臘腸整條背隨便選，紅貴賓只有約 10 公分。 |

寵物飾品是 `PetModel` 內層 group 的子物件，所以會**自動**跟著牠的呼吸、走路彈跳與鳥的傾斜
一起動 —— 需求第三節的「讓寵物與效果產生一些互動」是靠結構拿到的，不是另外做動畫模仿的。

`petRootScale(spec) = spec.height × CHARACTER_ROOT_SCALE` 是效果系統用來換算距離的基準，所以
「rise 0.3」在金絲雀跟柴犬身上都是 30 公分。

這一排是全遊戲第二個**整排上稀有度**的貨架（第一個是寵物）。分級的依據是「這個效果有多像一個
事件」，不是價格 —— 700 元的小火焰跟 620 元的星星髮飾同為普通，而 400 元的部落面具是史詩，這是
刻意排的，因為 `constants/rarity.ts` 明文禁止從價格推導稀有度，而一條只寫在註解裡的規則不如一個
看得出來的貨架。

> 2026-08-28 稀有度從六階收成四階（普通白／稀有綠／史詩紫／神話紅）。這一排的「優秀」併入普通、
> 「傳說」併入史詩，上表已經是新的分級；下面幾段講的是**這三件為什麼站在這一排的頂端**，那個理由
> 跟它們現在叫什麼名字無關，所以原文保留。

三件同為這一排的**最高階**，而且是用三種不同的方式賺到的 —— 這正是讓最高階不等於「最貴的那件」
的關鍵：

- **星軌之翼**改變的是**玩家自己的動作怎麼被看見**（姿勢回應走路、軌跡標記走過的地方、跳躍有峰值）
- **精靈光環**改變的是**世界長什麼樣**（夜裡穿戴者腳下的地面是真的被它照亮的）
- **結霜光環**是**同一個能力的相反用法**：它也帶光，但它的環是六角、有刺、會整體轉，而精靈光環的環
  是平滑的、靜止的、只有東西繞著它跑。兩者共用一個掛點與一半的調色盤，所以它們必須在**結構**上不
  一樣而不只是顏色不一樣——一個是「一圈光，有東西繞著」，一個是「一塊會轉的冰」。

**昆蟲之翼 1450 曾經是史詩、星軌之翼 1600 曾經是傳說，那一階的差距就是重點。** 四階之後兩件都是
史詩，這段話因此變成一段歷史 —— 但它記的事情仍然成立：兩件掛在同一個掛點上，所以貨架必須說得出
誰在上面，而在同一階裡那件事現在得靠**結構**而不是靠邊框顏色去說。兩者也刻意做成相反的東西：
星軌之翼是一把**不透明的羽扇**，響應的是玩家的
**移動**；昆蟲之翼是四片**半透明的膜**，站著不動時最好看。前者在跳起來的那一刻最大聲，後者在被人
盯著看的時候最好看——而那是高階飾品的另一半用途，也是這個貨架原本沒有的那一半。

**星軌之翼是這套系統的旗艦，也是「特殊飾品不夠特別」的答案。** 前五件都是「飾品」：小、在肩膀
以上、環境式、音量一樣，所以沒有任何一件能是「買來被看見」的那一件。它是反過來造的 ——
在背上（第三人稱鏡頭正好看的角度）、大（翼展約 1.5 世界單位）、會回應玩家的動作（姿勢而不只是
速率）、會留下東西（`settle`），而且有一個峰值（起跳時的爆發是全目錄唯一被允許大聲的東西）。

## 九、還沒做的（刻意）

**雲朵、海洋、音樂三個系列已經補上了**（各一件玩家＋一件寵物），而且如同上面說的，系統本身一行都
沒改 —— 六列 config、六個模型、六個圖示，bond 從兩組能發變成五組能發。營火系列的暖暖燈籠仍未進
目錄，但 `glow` 做完之後它也只差一列 config 跟一個模型了。

`burst` 目前只認得 `'jump'` 一個時機。其他明顯的（進門、餵寵物、升級）都只差一個
`playerBus` 上的旗標與 `BurstSpec['on']` 上的一個字串 —— 但每加一個都要先想清楚它會不會變成
「隨時都在爆」，因為 burst 的克制全靠「很少發生」。

**`gravity` 已經做了**（2026-08-20，見第三節），所以「噴上去再落下的火星」現在是一個欄位。小火焰
吊飾的火星、海洋腳環的水花、星軌之翼的跳躍星屑都在用它。

**`glow` 已經做了**（見上面第三節），所以暖暖燈籠現在只差一列 config 跟一個模型。

還沒有的能力，以及各自擋住什麼：

| 缺的 | 擋住 |
|---|---|

| `burst` 的其他時機 | 目前只認得 `'jump'`；進門／餵寵物／升級各差一個 `playerBus` 旗標與一個字串 |
| `'decor'` wearer | 把整套系統延伸到放置型家具（星空投影燈、會落葉的季節樹） |
| 泛化的 proximity 觸發 | 「走近才觸發」的互動家具 —— bond 的「半徑＋冷卻＋每 0.5 秒檢查」仍寫死成玩家↔寵物 |

**`aura` 已經做了**（見第三節的 `ground`），連同它真正的難處：地形貼合。做精靈光環時把它往後放
的判斷仍然成立 —— 難的從來不是加一個掛點 —— 只是那個「另一個問題」現在解掉了。

**逐頂點貼合**仍然沒做，而且短期內不打算做：現在擬合的是一個平面，跨在台階或大石頭上會有一邊浮
起來。要做到圈沿著石頭彎，等於每幀對著高度場變形網格，而它買到的東西在這個尺寸看不出來。

**更衣室的預覽現在兩邊都有**：寵物站在同一個 `CosmeticEffectField` 裡面，所以項圈、蝴蝶結
連同它們的效果在更衣室就看得到，跟島上一模一樣。

**流浪狗（`PetDog.tsx`）身上沒有飾品**，這是刻意的 —— 牠不是你的。要讓牠也能穿的話，
`PET_ANCHORS` 需要多一組給那個方塊身體的掛點，而方塊身體要的是四根方條做的帶子，不是圓環
（任何橢圓都會從長方形的四個角穿出去）。
