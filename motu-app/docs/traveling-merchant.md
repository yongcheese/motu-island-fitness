# 旅行商人 — 把「商店刷新」變成「有人來了」

限時小攤本來是路牌上的一格：按一下就開，什麼時候都開得了。這讓**換檔**變成一件只發生在畫面
上的事——貨架換了一批，島上什麼都沒有改變。

現在那一格不見了。要買本檔的東西，得走到海邊，找到那位搭著小船靠岸的**水獺行商**。

```
新的檔期開始
    ↓
小船從外海滑進來
    ↓
停在島東南的淺灘，攤子朝著沙灘
    ↓
玩家走到岸邊 →「E 與旅行商人交易」
    ↓
限時小攤開啟（還是同一個畫面、同一批商品、同一套購買規則）
    ↓
檔期快結束時他收攤開船，店就開不了了
```

這份文件講四件事：**入口怎麼移走的**、**商人與商店怎麼綁在同一個時鐘上**、**船停在哪裡是誰
決定的**、以及**要加第二位商人時要動哪裡**。

---

## 一句話架構

```
MerchantSpec           這位是誰、什麼時候來、停哪、開哪家店   constants/merchants.ts
      │  shop
      ▼
MerchantShopProvider   那家店的檔期怎麼算                    constants/merchants.ts
      │  currentPeriod(now)   ← 限時商店直接委派給既有的期數算術
      ▼
MerchantVisit          他現在在不在、店開不開得了            constants/merchantVisit.ts
      │                        （純函數，不存檔）
      ├──────────────► 世界裡的船與人                        Three/MerchantVisitor.tsx
      │                        + Three/MerchantBoat.tsx
      │                        + Three/Npcs.tsx（otterTrader）
      │                        停靠點：constants/merchantDocks.ts
      │
      └──────────────► 開店 / 收攤                           UI/MerchantSession.tsx
                               │
                               ▼
                       LimitedShopView（一行都沒改）
```

四層分開，理由跟限時商店自己那四層一樣：它們變動的原因不一樣。

| | 是什麼 | 什麼時候會改 |
|---|---|---|
| `MerchantDock` | 島上這個角落在哪裡 | 想換停靠位置 |
| `MerchantSpec` | 這位訪客是誰、行程是什麼 | 加一位商人 |
| `MerchantVisit` | 他**現在**在不在 | 每一秒（算出來的） |
| `MerchantVisitor` | 那艘船**這一幀**漂到哪 | 每一幀 |

## 一、路牌上那一格是怎麼拿掉的

不是 CSS，不是 `display: none`，也不是留著按鈕加一個 `disabled`。整格連同它會做的事一起消失
了：

- `SideButtons.tsx` 裡那個 `RailButton`（`id="limitedShopBtn"`）刪掉了，連 `Tent` 圖示的
  import 一起；
- 它唯一做的事 `setCurrentView(View.LIMITED_SHOP)` 也跟著沒了；
- `View.LIMITED_SHOP` 這個 enum 成員**留著**——路線還在，只是現在只有一個地方走得到。

**那個地方是 `UI/MerchantSession.tsx`，而且它會先問過。** 這件事有一道實際的守衛，不是一句約
定：

```ts
// 沒有 session 卻停在商店畫面上 —— 熱重載，或任何未來新增的、繞過商人的路。
if (!session && currentView === View.LIMITED_SHOP) setCurrentView(View.HOME);
```

所以「商人不在就開不了店」不是靠每個入口各自記得檢查（那種寫法只要有人加第二個入口就會漏），
而是**只有一個入口，而且畫面本身會把繞過它的狀態退回去**。

`LimitedShopView` 一行都沒改。它照樣只畫 `currentRotation(now)`，也照樣不知道商人存在——一個
會自己判斷「商人還在嗎」的商店畫面，就是關於這件事的第二個答案，而兩個答案遲早會不一致。

## 二、商人怎麼知道現在是哪一檔

**他不知道，也不需要知道。** 他跟貨架讀的是同一個時鐘。

`MerchantShopProvider` 是商人與店之間唯一的接縫，而限時商店那一列整個委派給既有的期數算術：

```ts
// constants/merchants.ts
'limited-shop': {
  view: View.LIMITED_SHOP,
  currentPeriod: (nowMs) => periodForInstant(nowMs),   // ← 就是限時商店自己那一個
  periodLengthMs,
}
```

造訪狀態接著把那一檔切成三段（`constants/merchantVisit.ts`）：

```
├──────────────── 一檔（7 天） ────────────────┤
├──── 造訪（3 天）────┼──── 已離開（4 天）────┤
▲                     ▲
arrivesAt         departsAt
```

（`arrivesAfter` 目前是 0，所以「等待」那一段長度為零 —— 新的一檔開始的那一刻船就靠岸了。三個
相位仍然全部存在，那是設定的事，不是這裡的事。）

因為兩邊都是同一個 `now` 餵進同一個 `currentPeriod` 的兩個投影，「商人賣的是上一檔的東西」在
結構上寫不出來。`scripts/test-merchant-visit.ts` 掃過三檔、每檔取樣 400 個點來驗這件事——它**不
可能**失敗，而把「不可能」寫下來正是那條測試的用途：哪天有人想給商人一套自己的排程，會先撞
到它。

行程本身是**比例**而不是寫死的天數：

```ts
schedule: { arrivesAfter: 0, departsBefore: 4 / 7 }
```

理由跟 `refreshInterval` 是設定同一個：把刷新改成一天一次（測試常這麼做），一組寫死「離開前一
天」的行程會直接變成「這位商人從來不出現」。

**停 3 天、走 4 天、再停 3 天。** 一檔是 7 天，所以「走 4 天」就是 `4/7`。寫成分數而不是
`0.5714`，是因為分母就是一檔的天數、分子就是「走幾天」——規則直接讀得出來。

這一段空窗不是「收攤的幾小時」而是**規則的一半**，而且它比停靠那一段還長：一週裡有四天，限時
小攤是完全打不開的。這是刻意的——沒有它，前一位還沒走下一位就到了，玩家永遠看不到「島上目前
沒有商人」這個狀態，而那個狀態正是「下一位快來了」唯一的訊號。

而一檔的長度反過來是被這個節奏定下來的：每一次靠岸都該是新的一批貨，不是玩家上星期就看過的那
一批。所以 `refreshInterval` 是 7 天（`constants/limitedShop.ts`），而不是巧合。

### 管理員測試模式：船不走

一週裡有四天進不了限時小攤，對玩家是規則，對 QA 是一道濾門。所以管理員測試模式開啟時，商船
**一直停在岸邊**（`components/UI/admin/AdminMerchantDock.tsx`）。

它沒有自己的按鈕：那個元件掛在 `<AdminOnly>` 裡，掛載時打開覆寫、卸載時關掉，而 `<AdminOnly>`
在模式關閉時回傳的是 `null`（真的卸載）——所以「關掉開關」與「歸零覆寫」是同一次卸載，不是兩
件要記得同步的事。面板裡（管理員測試 →「商店與經濟」→「商船行程」）那一區是唯讀的，只說明規
則正在生效。

覆寫是一格**模組層級**的布林值（`constants/merchantVisit.ts` 的 `setMerchantAlwaysDocked`）而
不是一個 context，理由跟 `utils/debugOverrides.ts` 一樣：`Three/MerchantVisitor.tsx` 在
`useFrame` 裡問這個答案，那裡讀不到 React context。差別是那一個自己去拉網址，這一個是 React 推
進來的，所以它仍然完全受管理員測試模式控制。

重點：**釘住的是行程，不是時鐘。** 貨架照樣每 7 天換一批、造訪 id 照樣會換，所以換檔那一刻
（這家店最容易出錯的地方）在這個模式下依然測得到。一艘永遠停著、貨也永遠不換的船，會把輪替變
成測不到的東西。

## 三、船停在哪裡

不是隨機，也**不是一組寫死的座標**。

隨機的問題很明顯（船會擱在陸地上、穿過島、漂到玩家游不到的地方）。寫死座標的問題比較安靜：
**這座島會長大**。領土升級把島的 XZ 乘上 `islandScale`，所以一組在一級領土剛好停在水面的座標，
升到三級就會被長出來的沙灘吃掉——變成一艘停在草地上的船，而且沒有任何東西會壞給你看。

所以停靠點是**相對於島自己的水線**描述的（`constants/merchantDocks.ts`）：

```ts
{
  id: 'east-shallows',
  bearing: 0.81,          // 方位角，atan2(x, z)
  offshore: 2.6,          // 水線往外幾個單位（下限由游泳的身長決定）
  approachOffshore: 20,   // 可游範圍再往外幾個單位（進場點）
  moorHeading: -π/2 + 0.12,
  landing: 1.45,          // 談得到的那塊地從水線往島上延伸多遠
}
```

**這裡沒有 `reach`。** 互動半徑是推出來的，不是第二格資料：

```ts
dockReach(dock) = dock.offshore + dock.landing   // 2.6 + 1.45 = 4.05
```

`resolveDock(dock, islandScale)` 才把它變成這一刻的世界座標。島長大時船自己跟著往外移，永遠在
水上、也永遠離岸邊同樣遠。

幾個數字的來歷：

- **`bearing: 0.81`** 是島自己那條石板路的盡頭（`PATHWAY_BASE_POINTS` 往東南延伸到 `(4, 3.8)`，
  `atan2(4, 3.8) ≈ 0.81`）。玩家沿路走過去就會走到船邊，不必被告知該往哪走——島上早就有一條指
  著那裡的路。它同時落在預設相機的視線方向附近，所以船一停好就看得到。
- **`offshore: 2.6` 已經貼著下限**，而下限是游泳系統定的（見下一節「船停多近」）：實測玩家朝
  著船游過去會停在 `r = 7.2`，也就是水線外 0.4 —— 那 0.4 就是「把船開近一點」全部的空間。所以
  **船不是那個旋鈕**。
- **`landing: 1.45` 才是。** 它 = 乾沙灘寬度（`SHORELINE 6.8 − GRASS 5.7 = 1.1`）+ 玩家半徑
  0.35，意思是「一踏上沙子提示就已經亮著，而且站的是整個身體不是一個點」。前一版把互動半徑寫
  成另一格資料（`reach: 3.4`），於是玩家真正站得到的那塊地是一個沒有人負責的**差值**，只有
  0.8 —— 提示要走到 `r = 5.79` 之外才亮，而水線在 6.8，所以能談生意的只有沙灘最外面那一公尺；
  朝著船再走兩步就過了 7.15 開始游泳。「非得下海才買得到東西」是這麼來的，不是因為船停得遠。
  現在的內緣在 `r = 5.00`（草地上，比沙灘還往內 0.7），沿岸有 5.9 個單位寬。
- **`moorHeading` 的負號不是隨便挑的。** 這個專案裡「local 掛到 world」只有一種寫法：local `+z`
  對到 `(sin yaw, cos yaw)`，local `+x` 對到 `(cos yaw, -sin yaw)`。代進去可以看出 **local `+x`
  是左舷**，而攤子擺在左舷。要讓那一側朝著沙灘，船必須往 −90 度轉；+90 度會把整個攤子轉去面對
  外海，而那個錯誤在螢幕上只會看起來像「商人背對著你」。

`scripts/test-merchant-visit.ts` 對**每一個領土等級（1..11）**各驗一次：停靠點在水線外、離岸距
離不隨島長大而漂移、浮在海平面上、進場點在可游範圍之外、進場航線是一條直線。

## 四、抵達與離開

這裡有**兩個時鐘**，不要弄混：

| | 單位 | 誰算的 | 是不是權威 |
|---|---|---|---|
| 他在不在島上 | 天 | `constants/merchantVisit.ts` | **是** |
| 那艘船這一秒漂到哪 | 秒 | `Three/MerchantVisitor.tsx` | 不是，只是把權威演出來 |

世界那一半是一個每幀推進的狀態機：

```
offshore ──► arriving ──► docked ──► leaving ──► offshore
             (16 秒)                  (19 秒)
```

- **沒有 `setTimeout`，也沒有任何一行 `destroy`。** 每一次轉換都是「這一幀的相位」與「這一幀的
  動畫進度」比對出來的結果。分頁被切走、或整條 Canvas 被 `frameloop='never'` 停掉（玩家進了屋
  子或商店），回來時它只是重新問一次時鐘然後接著演——不會有一個燒在 timer 裡的未來事件在沒人
  看的時候把船刪掉。
- **掉頭是原地掉頭。** 檔期在船還沒靠岸時就結束了？`progress = 1 - progress`，從現在的位置轉回
  去，不是先瞬移到岸邊再開走。反過來也一樣。
- **「消失」是不再被畫出來**，不是 destroy：`leaving` 跑完之後這個實體回到 `offshore`，下一檔
  它會從同一條航線重新滑進來。
- 航線是進場點與停靠點之間的內插，進場 easeOut（滑進來然後慢慢停住）、離港 easeIn（慢慢起步然
  後開走）。**沒有尋路、沒有避障、沒有轉向控制器**——海上沒有東西要閃。

### 進場動畫是給這位玩家看的

商人可能已經停在那裡三天了，但玩家這次進遊戲時，船仍然會從外海滑進來一次。這是刻意的：突然
出現在視野裡的船是最糟的一種；讓它從**可游泳範圍以外**滑進來，玩家只會看到「有東西來了」。

這一段動畫不影響任何資料——店開不開得了看的是相位，不是船在哪。

## 四點五、船是實體

### 接的是既有的那一套，不是新的一套

島上原本只有兩種擋得住玩家的東西，而它們的共通點是**存在存檔裡**：玩家擺的家具（量測出來
的 OBB，`lib/furniturePlacement.ts`）與玩家的家（它自己的 footprint）。船兩者都不是 —— 它因
為「現在是這一檔」而存在，每一幀都在動，而且沒有人擁有它。

所以加的不是碰撞邏輯，是一個**把盒子送進既有流程的入口**：

```
MerchantVisitor（每幀把 local 盒子乘上船的 transform）
      │ publishWorldSolids(sourceId, boxes)     lib/worldSolids.ts
      ▼
getWorldSolids()  ── Avatar 每幀讀 ──►  resolveCollisions
                                              │
                              resolvePlayerAgainstFurniture ─┐
                              resolvePlayerAgainstSolids ────┼─► pushOutOfBox
                                                             ┘
```

最後那個 `pushOutOfBox` 是重點：家具與船**呼叫同一個函數**。沿著面滑開的手感、被擠進去時
從最淺的那一面脫出、玩家半徑 —— 三者不可能在兩種實體之間走鐘，因為它們只寫了一次。

`worldSolids` 是**以來源為鍵的登記表**而不是一個欄位，因為一個欄位只有一個寫入者：同時來兩
位商人（`MERCHANTS` 多一列就會發生）時，第二位會蓋掉第一位，症狀是其中一艘船可以游過去。

### 形狀：階梯，不是一個大方盒

船的平面不是矩形 —— 中後段是 1.6 寬的直身，船頭從 z = 1.0 收到 2.05 的一個尖。一個 3.6 長
的方盒會在船頭兩側多出將近 0.6 的隱形牆。所以船頭用**三格逐漸變窄**的盒子跟著斜度走，每一
格的半寬取自它自己中點上的真實船寬，最大偏差約 0.13 —— 比玩家半徑（0.35）還小。

| 碰撞盒 | 是什麼 |
|---|---|
| `hull-body` | 直身段 + 船尾 |
| `hull-bow-a/b/c` | 船頭的三段階梯 |
| `stall` | 棚架。四根柱子**一格**（Composite）—— 它們是同一個構造物的四隻腳 |
| `cargo` | 三個貨箱**一格**（Composite）—— 它們擠在一起，玩家不可能從中間穿過 |
| `barrel` | 木桶 |
| `mast` | 桅杆。細，但它是從甲板長到 2.7 的實心木頭 |
| `merchant` | 商人本人。跟著船走，所以船轉、船開，他的碰撞都跟著 |

**沒有碰撞的**：帆、棚布、旗、纜繩、燈籠、船板接縫、鬍鬚。布與細物不是實體，給它們碰撞只
會讓玩家被看不見的東西卡住。

要誠實說一件事：**甲板上那四格今天碰不到**。船殼已經把甲板整個圍起來了，玩家游過來會先被
船殼擋下。它們仍然寫著，是因為它們屬於這個**實體**而不是屬於「現在停在哪」—— 哪天船靠上碼
頭或玩家上得了甲板，它們立刻是對的，而不需要有人記得回來補。

### 玩家不上船

目前的設計是**不登船**，而這不是靠一道遠處的隱形牆做到的，是船殼本身：玩家游到船邊就停在
船殼上，甲板沒有可以踏上去的一階。

這也是為什麼碰撞盒**只有平面、沒有高度**。有高度的東西是「可站立表面」
（`lib/placementSurfaces.ts`），而那條路會讓甲板變成地板 —— 一塊在海中央、會隨浪上下、而且
船一開走就把站在上面的人丟下的地板，同時還會讓玩家的游泳狀態在船邊莫名其妙地結束。船是
**擋路的**，不是地面，兩者在程式上是兩條完全不同的路徑。

### 游泳的身體是躺平的

船殼擋得住玩家的**原點**（腳），但游泳時整個人是繞著腳往前傾 71 度躺著的
（Three/swimPose.ts 的 `SWIM_BODY_PITCH`）—— 頭落在原點前方約 1.2。所以只推原點的話，畫面
上會是「腳規規矩矩停在船外，肩膀和頭在船裡面」。

這個專案早就有解法：`resolveProneBody` + `CRAWL_BODY_REACH`，匍匐用的那一套。游泳原本被刻
意排除在外，理由寫在 Avatar.tsx 裡 —— 在岸邊替躺平的身體保留一個身長，會把玩家擋在自己的
沙灘外面。那個理由現在仍然成立，所以新增的 `SWIM_BODY_REACH` **只對 transient world solids
生效**，對房子與家具一律不生效。這不是特例，而是「一個游泳的身體實際上可能躺在什麼東西上」
的完整集合：會漂在水上的只有那艘船。

保留距離乘上**當下的入水姿勢權重**（`playerBus.swimPose`），所以下水時它隨著身體躺下而長
出來、上岸時隨著身體站起來而消失，不會在某個旗標翻面的瞬間憑空出現一個身長的淨空。

### 船能停多近，是幾何算出來的

`offshore` 有一個硬下限，而它不是美感問題：

```
offshore  >  船身半寬 0.80 + 身長 1.20 + 玩家半徑 0.35  =  2.35
```

比這更近的話，朝著船游過去的玩家會被自己的身長推回**沙灘上** → 上岸就不算游泳 → 身體站起
來 → 保留距離消失 → 又能往前游，在水線上來回彈。目前是 **2.6**（餘裕 0.25）。原本的 2.05
正好落在下限以內，所以那個值不能留。

`SWIM_HYSTERESIS` **不在**這條式子裡，而那正是下限沒有更大的原因：`isInWaterZone` 是不對稱
的，已經在水裡的人要退到水線以內才算上岸，乾的人才需要走過 `水線 + margin`。被推回去的是
已經在游泳的人，所以擋著他的是水線那一條。（這條測試的第一版把 margin 也加了進去，於是把
船推到 3.0 —— 比需要的遠了 0.35。）

### 實測

用執行中的模組跑一次真正的 `resolveCollisions`，停泊狀態下：

| | 沒有保留距離 | 有保留距離 |
|---|---|---|
| 原點停在 | r = 8.39，船外 | r = 7.23，船外 |
| 身體中段 | **在 `hull-body` / `stall` / `merchant` 裡面** | 全部在外面 |
| 頭 | **在 `hull-body` / `stall` 裡面** | 全部在外面 |

以及：停下來的地方 r = 7.23 > 水線 6.8，**仍然算在水裡**（不會來回彈）；商人在水線外 2.25，
所以游著的時候離他 1.82、站在乾沙灘上離他 2.25，兩者都在 4.05 的互動距離內；整段水域裡
`isGrounded` 一次都沒有 true —— 游泳判定沒有被影響。

### 碰撞與互動是兩件事

- **碰撞**：`resolvePlayerAgainstSolids`，把玩家推出船身。
- **互動**：`InteractionPromptTracker` 對商人錨點量水平距離，跟碰撞盒無關。

兩者用的是不同的資料、不同的模組、不同的距離。上表最後兩列就是它們分開的證據：玩家能到的
最近位置離商人 0.87，而互動距離是 4.05 —— 玩家**還沒被擋住之前**就已經談得到了。
`scripts/test-merchant-visit.ts` 對每一個領土等級驗這條不等式。

### 移動中的同步

碰撞盒是在寫完 `group.position` / `group.rotation` 的**下一行**、用**同樣那兩個變數**算出來
的，不是回頭讀矩陣、也不是另外算一次航線。所以進場、離港、換檔、升領土時不可能有一個動了
另一個沒動 —— 它們不是兩個要對齊的東西，是同一個 transform 的兩個用途。

船開走時 `publishWorldSolids(id, null)`，元件卸載時也一樣。**沒有這一行的話**，海上會留下一
塊看不見卻游不過去的水。

浮沉的 pitch / roll 刻意不帶進碰撞盒：那是 ±0.03 弧度的搖晃，帶進去只會讓貼著船身的玩家每
幀被推一下。碰撞用的是船的平面位置與艏向。

## 五、玩家怎麼互動

**沿用既有的互動系統，沒有第二套。**

島上那個浮動提示（`Three/InteractionPromptTracker.tsx` + `UI/InteractionPrompt.tsx`）本來就在
「我的家門口 / 一件家具 / 寵物 / 一叢雜草」之間排名，只顯示最近的那一個。商人只是**多一個候選
人**：

```ts
const merchant = playerBus.merchantTarget;
if (merchant && merchantDist < merchant.reach) candidates.push({ key: 'merchant', … });
```

`playerBus.merchantTarget` 由**正在划那艘船的元件**每幀寫入——因為只有它知道船這一幀漂到哪裡、
靠好了沒。它同時是「可不可以互動」的閘門：船還在進場、正在離開、或這一檔根本沒有商人時，這
裡就是 `null`，於是提示不會出現、動作鍵也沒有東西可按。**一個旗標同時關掉兩者**，而不是提示與
按鍵各自判斷一次然後在某個邊界上不同意。

觸發之後走的是這條路：

```
Avatar.handleAction / 提示上的觸控按鈕
        │  window event: merchant-interact { merchantId }
        ▼
MerchantSession  ── 再問一次造訪狀態 ──► 開得了？ 開；開不了？ 什麼都不做
```

Avatar **沒有** `setCurrentView(View.LIMITED_SHOP)`。它知道自己走到了一位商人面前；它不知道、
也不該學會這位商人剛好開的是限時小攤。那個連結是資料（`MerchantSpec.shop`）。

「再問一次」是有意義的：上面那個列表每秒更新一次，而那一秒剛好就是「玩家在商人開船的同一瞬間
按下 E」的那一秒。問一次時鐘的成本是零。

### 手機

**同一顆按鈕，不是第二套互動。** 觸控裝置上那個浮動提示本來就是可點的按鈕（`isTouch` 時它把
`[E]` 鍵帽換成一顆圓形圖示鈕），所以點一下商人頭上那顆 🛍 圖示，跟鍵盤按 E 走的是同一個事件。

這件事之所以不用花力氣，正是因為商人加入了**既有的**提示，而不是帶了自己的一套 UI 來。

## 六、正在逛的時候他收攤了

錢不會出事，而且**不是**因為誰做了什麼補救：`context/useLimitedShop.ts` 的購買在寫入的那一刻
從時鐘重新推導貨架，所以一筆在邊界上送出的購買要嘛照舊檔完成、要嘛被擋下來回一句「這個商品已
經下架」。扣了錢沒拿到東西在那條路上**寫不出來**。

`MerchantSession` 負責的是畫面那一半：

```
造訪結束（open 變 false，或 visitId 換成下一檔）
        ↓
蓋上一層「水獺行商收攤了」——整個貨架被蓋住，所以按不到任何購買按鈕
        ↓
玩家按「回到島上」→ setCurrentView(View.HOME)
```

用 `visitId` 而不是只看 `open`，是因為「上一檔剛結束、下一檔立刻開始」在設定上是可能的
（`departsBefore: 0`），而那種情況下玩家眼前那個貨架已經是舊的了。

**刻意不用計時器把人踢出去**：一個讀到一半被抽走的畫面比一個等著你按的按鈕更糟。也刻意**不是**
逐一停用購買按鈕——一個「還畫著價格但按不下去」的商店，玩家讀到的是壞掉，不是打烊。

## 七、玩家怎麼知道有人來了

- **遠處那艘船本身。** 一根斜桅、一片張開的帆、一頂條紋布棚、一面小旗——那四樣是這片海上唯一有
  直線與尖角的東西（島、浪、珊瑚、雲全是圓的），所以它遠遠看過去就是「有東西來了」。
- **紅色。** 全船只有兩處高飽和（棚布的條紋與桅頂的旗），而且跟商人腰帶是同一個赤陶紅。紅色出
  現的地方就是攤位所在，這是不需要文字的指路。
- **天黑之後那盞燈籠。** 攤子前柱上掛著一盞，是海上唯一亮著的東西。
- **一行字。**「一位旅行商人抵達了島嶼」，右上角，四秒，不擋任何東西，不需要關掉。

最後那一行**一趟造訪只講一次**。存在 `profile.limitedShop.greetedVisitId`（一個字串，鍵是
`${商人id}:${檔期id}`）——不存的話，一檔兩個星期會變成連續十四天每次登入都被通知一次，而一句每
天都出現的到訪通知不是通知，是雜訊。

那一格**住在 `limitedShop` 這個 map 裡面是刻意的**：`firestore.rules` 對它只驗到「它是一個
map」，而 `limitedShop` 本身已經在寫入白名單上——所以多這一格不需要動規則、不需要部署，也就不
可能發生「規則還沒更新，於是整份 profile 讀進來變成新手存檔」那個失敗。寵物照護把狀態塞進
`islandState` 底下是同一個判斷。

只在島上講。在商店裡、屋子裡或健身畫面時不講——那句話是要人抬頭看海的，而那三個地方看不到海。

## 八、要加第二位商人

`MERCHANTS` 多一列。就這樣——世界元件、互動、提示、開店流程一行都不用改。

實際上會用到的清單：

| 想加什麼 | 要改哪裡 |
|---|---|
| 第二位商人，停在島的另一邊，一樣賣限時商店 | `MERCHANT_DOCKS` 一列 + `MERCHANTS` 一列 |
| 一位賣**別家店**的商人（季節家具、活動道具） | 那家店先有一個 `View` 與一個畫面 → `MerchantShopId` 多一個成員 → `MERCHANT_SHOPS` 一列（填它的 `currentPeriod`）→ `MERCHANTS` 一列 |
| 換個長相 | `NpcKind` 多一個成員 + `Three/Npcs.tsx` 一個模型 + `constants/npcs.ts` 一組顏色 |
| 換一種船 | `MerchantSpec` 多一個 `boat` 欄位，`MerchantVisitor` 依它挑元件（目前只有一種，所以還沒有這個欄位——見下） |
| 只在檔期後半出現的活動商人 | 那一列的 `schedule.arrivesAfter` |
| 讓他停久一點／短一點 | `schedule.departsBefore` |

**目前刻意還沒做的**：船是寫死的一種（`MerchantBoat`）。加第二種船的正確時機是**真的有第二種
船**——先宣告一個 `boat: 'skiff' | 'raft'` 欄位而只有一個值，只是把一個 `if` 換成一張只有一列
的表。同一個判斷讓 `MerchantSpec.kind` 現在只有 `'traveling'`：那個欄位存在是因為將來 UI 要分
「商人／使者／表演者」，而不是因為現在需要分。

## 九、這不是伺服器

跟限時商店一樣：沒有全域同步，檔期邊界讀的是裝置上的時鐘，商人的來去是每台裝置各自算出來的
（但因為是純函數，大家算出來的一樣）。

真正的後端會填的形狀已經在這裡了：`MerchantShopProvider.currentPeriod` 就是
`GET /shops/:id/period` 會回的東西，`MerchantVisit` 就是 `GET /merchants` 會回的東西。接上服務
時換的是資料來源，不是重新設計。

## 十一、水獺行商的身體：同一個關節不能有兩個說法

他的雙腳曾經跟軀幹是分開的，而原因值得記下來，因為它是一整類 bug 而不是一個數字寫錯。

**同一個關節被三個獨立的字面值各寫了一次。** 腿的膠囊寫到 y = 0.217、衣襬寫在 0.26、
`Swing` 的支點寫 0.245。三個數字各自都「看起來合理」，但它們描述的是同一件事（髖在哪），而
它們並不同意 —— 中間空了 0.043（乘上身高 1.72 是 0.074 的世界單位），支點懸在那個空隙裡，於
是畫面上是一雙飄在身體下面的腳。

排除掉的其他可能：座標系是同一個（三隻 NPC 都用一套單位高度的模型空間，`Swing` 把 pivot 減
回去所以子物件保持絕對座標）；hierarchy 正確（`NpcModel` 一個 root，`scale` 一次套在整棵樹
上）；沒有第二段程式在生成後改腿的 position；船的 transform 不影響身體內部。**純粹是資料自
己不一致。**

所以修法不是「把腿往上搬」—— 那只會製造第四個字面值。修法是讓那三個地方**讀同一個數字**：

```
constants/npcs.ts  OTTER_RIG { soleY, ankleY, hipY, legTopY, hemBottomY, pelvis… }
        │
        ├─► Swing 的 pivot          （髖）
        ├─► otterLegCapsule()       （腿的中心與長度，從兩端推出來）
        └─► 骨盆那顆球              （包住髖，跨過衣襬）
```

同時補上原本**根本不存在**的骨盆：兩條腿與軀幹共同插進去的那一塊肉。現在的鏈是連續的 ——
軀幹 → 骨盆（跨過衣襬）→ 腿（頂端埋在骨盆裡 0.05）→ 腳（跟腿重疊 0.017）→ 地面。

每一段的「咬住下一段」都是 `scripts/test-merchant-visit.ts` 的一條斷言，包括**未來動畫不會
再把腿甩掉**那一條：腿頂那一小截繞著髖掃出去的距離（`stub × sin(擺幅) + 腿半徑 = 0.063`）
必須小於骨盆的半深（0.122）。所以走路、待機、交易動作都不會讓它露出來 —— 而且那是被測出來
的，不是「目前看起來沒事」。

其餘**關節**查過了，沒有同類問題：手臂在肩球與軀幹圓柱裡都有重疊（不是只靠肩球，那樣在
y = 0.5 會差 0.005）；頭的下緣埋進肩線 0.057；尾巴根部在骨盆球裡面。三處都是重疊而不是接
觸，所以沒有一處是「剛好碰到」。

那次檢查問的是「每一塊都接上了嗎」，而它問漏了另一半 —— 見下。

## 十一點五、褐色圓環：同一件事的上半身版本

### 那個環是什麼

**斜背錢袋的背帶。** 不是 debug object，不是 collider 的視覺化，不是關節或定位輔助物，也不
是重複生成的 mesh —— 它是正式服裝的一部分，只是它從來沒有以「背帶」的樣子出現過。

```jsx
<mesh position={[0, 0.47, 0]} rotation={[0, 0, 0.42]}>
  <torusGeometry args={[0.135, 0.011, 6, 22]} />
```

半徑 0.135 的環，躺在 **XY 平面**上 —— 也就是說，那個環的平面**穿過身體自己的中軸**。軀幹
在那個高度的半徑是 0.1317，於是：

| | |
|---|---|
| 埋在衣服裡 | **86%** 的環面 |
| 露在外面 | 左右兩側各一小段，最多凸出 0.0147（世界單位 0.025） |

從島上那個相機距離看過去，那正好是一個「陷進軀幹裡的褐色圓環」。

旁邊那行 `rotation={[0, 0, 0.42]}` 是作者想把背帶斜過去的意圖 —— 但 `torusGeometry` 本來就
是**繞著 Z 軸旋轉對稱**的，繞 Z 轉它等於沒轉。所以那個意圖從來沒有進到畫面裡，而且**沒有任
何一行程式碼看起來是錯的**。

### 同一個原因埋掉的另外三處

用同一把尺（取樣每個配件的表面，問它有多少在身體的實體外面）量過整隻之後：

| 零件 | 原本露出來的比例 | 原因 |
|---|---|---|
| 斜背帶 | 14% | 環的平面穿過中軸 |
| 米白領口 | **0%** | 寫在 y = 0.60、半徑 0.085；肩線球在那個高度有 0.124 寬 |
| **兩顆眼睛** | **0%** | 寫在 (±0.062, 0.785, 0.115)，那個點在頭的表面**底下 0.026**，而眼球半徑只有 0.021 |
| 四根鬍鬚 | 兩端幾乎都在口鼻球裡 | 同上，加上桿子的軸幾乎是垂直的 |
| 前襟內襯 | 19% | 一塊平板貼在圓錐上，中段整片沉進去 |
| 帽帶 | 最外緣 0.002 | 半徑 0.118 + 管徑 0.009 vs 帽冠在那個高度的 0.125 |

這是十一節那個 bug 的**上半身版本**：一個配件的座標，與它要貼上去的那個身體，各自被寫死了
一次。差別只在下半身的症狀是「散開」（看得出來壞了），上半身的症狀是「不見了」——一件從來
沒出現過的衣服不會有人回報，而一個只露出兩小段的環會被回報成「一個不明的褐色圓環」。

### 修法：讓配件問身體

不是把那幾個數字調大一點（那只會製造下一個字面值），而是加一張描述**側影**的表，並且讓模型
本身也讀它畫軀幹 —— 表跟畫面因此不可能不同意：

```
constants/npcs.ts  OTTER_BODY { torso, hem, sash, sashRim, shoulder, head, muzzle, hatCrown }
        │
        ├─► otterBodyRadiusAt(y)      「他在這個高度有多寬」（取所有部件的最大值）
        │        ├─► otterSatchel()    背帶的半徑、傾角、拉長倍率；袋子掛在環的低點正下方
        │        └─► 前襟那一段殼      上下兩端各問一次
        ├─► otterCollar()             脖子在哪（二分法找頭與肩的交界）+ 那一段最寬處
        ├─► otterHatBand()            帽冠在那一段最寬處
        └─► otterOnHead() / otterOnMuzzle()   把五官貼到臉的表面上，再沉進去指定的深度
```

背帶那一條值得單獨講，因為「把環轉個角度」是不夠的：**一個斜著切過圓柱的平面，切出來的是橢
圓**，照抄身體的圓再斜過去，環一樣會沉進身體（斜角越大沉得越多）。所以它沿著傾斜軸拉長
`1 / cos(tilt)` 倍，代進去可以驗證環上每一點離中軸的水平距離**恰好等於 `radius`**，與角度無
關 —— 整條背帶貼在同一個半徑的圓柱面上，而那個半徑是從 `otterBodyRadiusAt` 拿的。

```
      ↑ y            環上一點 = ( R·cosθ , R·cosθ·tan(tilt) , R·sinθ )
   ┌──┴──┐
   │ 軀幹 │           水平距離 = √(R²cos²θ + R²sin²θ) = R   ∀θ
   └──┬──┘
```

兩端的高度也不是選的：下緣是「腰帶上緣再往上一點」，上緣是「領口底下」。腰帶調寬、領口調
高，背帶自己會讓開。袋子的袋口與環的低點**同高**，所以背帶與袋子是一件東西的兩段。

結果（`npm run test:merchant` 印出來的實測值）：背帶離身體 0.009–0.018，整圈都在外面；領口
的最緊處還有 0.006 餘裕；眼睛露出 0.011 的厚度。每一條都是斷言，不是註解。

## 十二、他在船上做什麼：動畫狀態機

一位站著不動的商人跟一塊立牌沒有差別，但「玩家靠近就轉一下手臂」也不行 —— 第二個動畫出現
的那一天，它就變成兩個 effect 同時在寫同一個 `rotation.x`，而誰贏由掛載順序決定。

### 一個姿勢，一個寫入者

```
   MerchantAnimator（lib/merchantAnimation.ts）
        │  update({ delta, distance, bearing, available, awareness, interaction })
        ▼
   NpcPose（lib/npcPose.ts）—— 一組通道：bodyYaw / lean / roll / twist / rise / swell
        │                        / headYaw / headPitch / left{lift,out} / right{lift,out}
        ▼
   模型（Three/Npcs.tsx）—— 每個關節只讀自己那一格
```

任何時刻只有**一個** pose 物件（就地改寫，每幀零配置），每個關節只從自己那一格讀值。要混合
兩個動畫，唯一的方法是混合兩個 pose —— 而混出來的仍然是一個 pose。**「兩個動畫搶同一隻手
臂」在這個結構裡寫不出來。**

控制器是純 TypeScript：不認識 React，也不認識 three.js。所以整套狀態、優先權、冷卻與待機變
化都能在測試裡用一個 for 迴圈跑完（39 條斷言），而元件裡永遠只剩「量完、寫進去」。

### 狀態與優先權

| 狀態 | 優先權 | 進入條件 | 長度 |
|---|---|---|---|
| `idle` | 0 | 沒事 | 持續 |
| `interacting` | 10 | 玩家在互動半徑裡 | 持續 |
| `greeting` | 20 | 玩家進入感知半徑，且**重新武裝過**、冷卻也過了 | 2.6s |
| `purchase` | 30 | 收到一筆**成交**的買賣 | 1.1s / 1.9s（看金額） |

大的贏，而且交接是 0.26 秒的**混合**而不是切斷：招呼揮到一半買了東西，那隻手是從它當下的位
置移到道謝的位置，沒有任何一個關節跳一下。

### 待機不是一段動畫，是一個小狀態機

`settle`（只有呼吸與極小的晃）、`lookAround`、`shiftWeight`、`checkGoods` 四種，用權重抽
（`settle` 最重，所以那些小動作是**偶爾**發生的，不是輪播的），長度也是抽的。每一段都乘上一
個兩端為 0 的信封，所以每一段自己就會回到基礎姿勢 —— 接縫上不可能有跳動，也不需要第二層混
合。抽籤用控制器自己的偽隨機數（可重現，所以測得動），**沒有一個 `setTimeout`**：每一段都是
被幀時間推進的。

### 為什麼不會一直揮手

§7 講的那種 animation spam（在感知半徑邊界上來回走，商人就揮手、停、揮手、停）被兩道**不同**
的閘門擋著，兩道都要過：

* **遲滯**：進入用 `awareness`，離開用 `awareness + 1.8`。中間那一圈是死區 —— 在邊界上踏步
  不會讓他重新「發現」你。
* **重新武裝 + 冷卻**：玩家必須真的離開過 3 秒，才重新算一位「剛走過來的玩家」；而且兩次招
  呼之間至少隔 24 秒。

測試裡有一條就是拿一分鐘、每半秒跨過邊界一次去跑它：**一次招呼，不是六十次**。

### 購買反應只跟著成交走

反應不是由「按下購買按鈕」觸發的，而是由 `context/useLimitedShop.ts` 在**寫入被接受、餘額與
背包都更新之後**發布的一格 `playerBus.merchantPurchase`（單調遞增的序號，跟
`happyReactionCount` 同一個做法）。那一行放在那裡不是為了整齊：那裡是唯一一條買得到東西的
路，而上面每一道檢查失敗時**沒有任何路徑**走得到它 —— 所以「購買失敗商人卻在慶祝」不是靠記
得不要那樣寫，是根本沒有那條路。

序號是**比對**的、不是消費掉的，因為交易發生在商店畫面上，而那時候島這條 Canvas 是停著的
（`frameloop='never'`）。玩家按下「回到島上」之後的第一幀才會看到那個道謝。

### 動畫碰不到碰撞

* 姿勢**沒有位移通道**。不是「記得不要改 root」，是控制器根本無法表達那件事。
* 呼吸與重心只作用在髖關節以上（`UpperBody`），腳掌與骨盆不是那個 group 的小孩 —— 所以他永
  遠站在甲板上。
* 轉向只寫 `rotation.y`，夾在 ±0.5 弧度，用半衰期平滑（測出來最壞的一幀是 0.0136 弧度，不會
  有瞬間對準）。繞著自己的中軸轉不改變佔地，而他的肩線（0.227）本來就小於他那一格碰撞盒的
  半寬（0.24）—— 這一條也是斷言。
* 他的碰撞盒是船上的一格（`BOAT_COLLIDERS` 的 `merchant`），跟著船的 transform 走，動畫從來
  沒有寫過它。

### 三個半徑（§14）

```
   Awareness   7.49  = reach × 1.85            他發現得了你 → 打招呼
   Interaction 4.05  = offshore + landing      你談得到他 →「與旅行商人交易」
   Collider    0.48  邊長                      你穿不過他
```

由外往內，而且感知半徑是**從互動半徑推出來的** —— 調停靠點時，「先被看到，再談得到」這個順序
不會走鐘。

倍率是 1.85 而不是原本的 2.2，因為互動半徑從 3.4 長到 4.05（船停在下限上，能談生意的地只好往
島上延伸）。等比跟著放大的話感知半徑會變成 8.9，而商人站在 `r ≈ 9.1` —— 島上任何一個角落都會被
他發現，「他看到你走過來了」就不再是一件發生在特定時刻的事。倍率負責的是**順序**，絕對距離才
是手感，所以互動半徑改變時要回頭看的是這一格。
