# Outdoor Asset Quality Standard

> 「屋內家具很精緻，但走到屋外就像另一個品質較低的遊戲。」

這份文件是那句回報的答案。它先講**問題實際上是什麼**（跟直覺不一樣），再把結論寫成一條
跑得起來的檢查：`npm run audit:outdoor`。

---

## 一、評估：問題不是「室外比較差」，是室外**分層**

改版前把每一件可擺放物的模型量過一次（mesh 實例數、相異材質顏色數、模型自己量出來的尺寸），
結果是：

| | 平均 mesh | 中位數 | 最少 | 平均顏色 |
|---|---|---|---|---|
| 室內（124 件） | 12.1 | 10 | 1 | 5.6 |
| 室外（26 件，改版前） | 7.6 | 7 | **2** | 4.1 |
| 室外（26 件，改版後） | 13.3 | 12 | **8** | 6.1 |

（數字由 `npm run audit:outdoor` 量出，計算的是**實際 mesh 實例**而不是原始碼裡的 `<mesh>` 行數 ——
一個 `.map()` 畫六根柵欄柱是六個 draw call，不是一個。火焰粒子、鏡頭反光那類
「畫上去的光」不計入結構。）

平均差距不算災難性。真正的問題在**分佈**：室外那一櫃裡同時放著兩種東西。

- **最近做的**（白色柵欄、十件寵物窩、許願井、手作鳥屋）早就在室內的水準上。
- **目錄裡最早的五件**（`item-16` 到 `item-20`：木製平台、噴泉、椰子樹、吊床、火把）從來沒被
  回頭修過。它們是 2–4 個 primitive、2–4 種顏色：
  - 椰子樹 = 一根直圓柱 + 六片一模一樣的膠囊 + 一顆球
  - 吊床 = 兩根方柱 + 中間一片**平的**板子
  - 木製平台 = 一個 4×0.3×4 的實心方塊 + 四支腳
  - 噴泉 = 一個桶子 + 一片藍色圓盤 + 一根柱子 + 頂上一個小甜甜圈

一櫃裡有兩種品質，比整櫃都樸素**更**難看：玩家會拿他買過最好的那一件當基準，然後覺得其他每一件
都是半成品。所以這個標準的重點不只是「把下限拉高」，而是「不准再分層」。

### 同一次評估抓到的三件事

1. **商店圖片畫了模型上沒有的東西。** 椰子樹的圖有彎曲的樹幹、環紋和掛著的椰子；模型三樣都沒有。
   吊床的圖有下垂的網、交叉織紋和一顆黃色抱枕；模型是一片平板。這正是回報裡
   「商店圖片看起來很精緻，但玩家購買後發現實際物品非常簡略」那一句。
2. **商品說明也寫了模型上沒有的東西。** 許願井的第一句是「爬滿青苔的石造許願井」——
   模型上沒有青苔，而且井身是一根**單一圓柱**，不是砌石。戶外陶甕寫「內壁積了一點雨水。
   青苔從底部爬上來」——兩樣都沒有。溫馨營火寫「圍著石塊堆砌而成」——有六顆一模一樣的灰球排成正圓。
3. **室外的預算花在動畫上，沒有花在結構上。** 鞦韆、營火、望遠鏡、鳥屋、許願井的程式碼都很長，
   但長度幾乎都是 `useFrame` 的動畫；望遠鏡有掃視動畫和閃光，卻沒有目鏡、沒有對焦鈕、
   三隻腳之間沒有任何東西連著。

## 二、標準

### 規則 1：三層結構

每一件都要有：

```
Primary Shape        遠看認得出是什麼
  + Secondary Structure   撐住它的東西：腳架、橫樑、邊框、基座、封邊
  + Small Details         釘子、繩結、封頭、把手、一顆小裝飾
```

**少了第二層的物件就是「基礎 Geometry」**，那正是這次要修掉的東西。提升細節**不等於**提高
polygon count：椰子樹從 3 個 mesh 變成 26 個，但每一個都還是 8 邊的圓柱或膠囊。

### 規則 2：色彩分層

同一種材質至少兩階明暗（受光的面淺、背光的結構件深），而且取自
[`src/constants/outdoorPalette.ts`](../src/constants/outdoorPalette.ts) 的共用色盤。

不是為了寫實，是因為 low poly **沒有貼圖可以分隔相鄰的面**：一整塊同色的木頭，兩個相鄰面只差
一點點光照，遠看會糊成一坨。三階讓「面板」和「撐住面板的東西」在顏色上就分得開 ——
這是「看起來有結構」最便宜的做法，比加幾何便宜得多。

共用色盤還管另一件事：室外的東西是**擺在一起**看的。各自挑色的結果就是改版前的狀況 ——
三種互不相干的木頭色（`#78350f`、`#5C3A1E`、`#EAB676`）、兩種互不相干的石頭色，
每一件單獨看都合理，湊在一起就散了。

### 規則 3：Mesh 預算，依尺寸分級

級距是從**模型自己量出來的水平尺寸**算的，沒有商品可以宣告自己是小東西來躲掉下限。

| 級距 | 尺寸 | 下限 | 上限 | 最少顏色 | 重點 |
|---|---|---|---|---|---|
| Large | ≥ 2.0 | 12 | 34 | 4 | Silhouette + Structure |
| Medium | 0.8–2.0 | 8 | 26 | 3 | Secondary Details |
| Small | < 0.8 | 4 | 16 | 2 | Readability + Distinctive Shape |
| Building（房屋） | — | 40 | — | 6 | 見下 |

**上限跟下限一樣重要。** 一支 30 個 mesh 的火把和一支 3 個 mesh 的火把一樣錯，只是錯在另一邊 ——
小物件堆太多細節會讓畫面變雜，而島上可能同時站著幾十件擺設，每個 mesh 是一個 draw call。

### 規則 4：房屋不能只是換顏色

十二棟房子、十一種屋頂（thatch / slab / gable / hip / gambrel / cottage / pavilion / dormer /
flat / saltbox / gablefront）、九種外牆（plain / timber / masonry / plank / log / bamboo /
batten / panel / shingle）。**沒有兩棟可以共用同一組（屋頂, 外牆）配對。**

這是把「不要只是同一個房屋模型 + 換不同顏色」寫成程式判斷得了的形式：配色不算差異，
屋頂形狀與外牆做法才算。新增一款外觀時，至少要有一邊是這個貨架上還沒出現過的做法。

第三個軸是**開窗量**（`glazing`，見 `HouseModel.tsx` 的 GLAZING 表）：`cottage` 是每一面
一扇小窗（原本七棟都是這個），`wide` 把窗改成橫式並在門的另一側再開一扇，`panoramic` 則是
從腰線拉到門楣的落地窗。它改的是立面而不是輪廓，所以跟上面那組配對是獨立的。

| 房屋 | 屋頂 | 外牆 | 開窗 | 特色 |
|---|---|---|---|---|
| 毛胚屋 | gable | plain | cottage | （刻意沒有） |
| 草本屋 | thatch | timber | cottage | 門邊盆栽、藤蔓 |
| 石磚小屋 | slab | masonry | cottage | 煙囪、窗台花箱、柴堆、門燈 |
| 森林小屋 | gable | plank | cottage | 煙囪、柴堆、藤蔓、百葉窗 |
| 海景小屋 | hip | plank | cottage | 高腳、門邊盆栽、門廊 |
| 木屋 | gambrel | log | cottage | 煙囪、柴堆、雨水桶 |
| 花園小屋 | cottage | plain | cottage | 窗台花箱、盆栽、藤蔓、柵欄、百葉窗 |
| 海島小屋 | pavilion | bamboo | wide | 高腳、小陽台、門燈、門邊盆栽 |
| 鄉村小屋 | dormer | batten | cottage | 煙囪、百葉窗、窗台花箱、柴堆、遮雨棚 |
| 現代海景屋 | flat | panel | panoramic | 小陽台、門燈（屋頂另有露臺欄杆） |
| 林間小屋 | saltbox | shingle | cottage | 藤蔓、盆栽、窗台花箱、遮雨棚、柴堆 |
| 漁村小屋 | gablefront | plank | wide | 浮球與漁網、門燈、雨水桶、遮雨棚 |

**窗戶本身是「框包著玻璃」，不是「實心框裡塞一塊玻璃」。** 原本七棟的窗是一個實心 frame box
加一塊更小、更後面的玻璃 box —— 玻璃被完全包在框裡面，一個像素都畫不出來，所以每一棟的窗
都是一塊純色方塊。「房屋看起來像封閉的方塊」就是這個。現在玻璃先畫、佔滿整個開口，框是圍在
它外面的四根料（`WIN_FRAME`），構造上就不可能再把玻璃吞掉。

### 規則 5：Preview 與模型必須同時改

房屋的商店圖示（`QVersionIcon.tsx` 的 `HouseStyleIcon`）跟 3D 模型讀的是同一份資料，但**各自畫**。
新增一種屋頂而忘了加圖示分支，結果不是壞掉，是悄悄掉進 `default` 分支 —— 木屋的圖示會畫成一般
斜屋頂，玩家看著斜屋頂買回一棟穀倉頂的原木屋。這一輪就發生過兩次，所以現在有檢查。

## 三、這個檔案之外的兩條硬規則

### 不要在靜態模型裡加 `useFrame`

`scripts/lib/measureFurnitureModel.ts` 是靠**直接呼叫元件函式**來量碰撞體積的。元件一旦用了
hook，React 會丟 `Invalid hook call`。

以前這代表那件商品**整件跳過不量** —— 沒有碰撞檢查、沒有互動點檢查、沒有品質檢查。木製鞦韆、
溫馨營火、黃銅望遠鏡、手作鳥屋、許願井 五件（島上 26 件可擺放物的五分之一，含最貴的那一件）
就是這樣長期在稽核網子外面的，而報告只在最後印一行 `items with no measurable model:`，很容易
讀成雜訊而不是漏洞。

**這一輪把洞補起來了**：harness 現在會在呼叫元件的那一瞬間裝一個
[measurement dispatcher](../scripts/lib/measureFurnitureModel.ts)，用最簡單的方式回答每一個
hook（`useRef` 回一個 `{ current }`、`useMemo` 直接執行 factory、effect 都是 no-op、
`useContext` 回一個假的 zustand store 好讓 `useFrame` 訂閱得下去）。動畫 callback 永遠不會被
執行，所以量到的是模型的**靜止姿勢** —— 那本來就是該量的東西（鞦韆的碰撞體積應該是它靜止時的
樣子，不是盪到最高點時的樣子）。

代價是它用到 React 的私有欄位。這是 build-time 的稽核而不是出貨的程式碼，而替代方案 ——
要求每個會動的模型把幾何拆成第二個沒有 hook 的元件、再維護一張對照表 —— 是「一個模型是什麼」
的第二份事實來源，正好是 `constants/furnitureModels.ts` 存在要終結的那一類 bug。

### 尺寸從畫出來的東西量，不從表格裡讀

碰撞體積、站立高度、擺放判定全部是從模型量出來的（`lib/furniturePlacement.ts`）。所以：

- **改模型會自動改碰撞體積**，不需要同步任何表格。這是好事。
- **但也代表放大一件東西會讓玩家更難在它旁邊擺東西**。椰子樹第一版的葉子做到 1.23 全長，
  量出來的擺放外框是 3.68×3.38 —— 比房子還寬，而草地半徑只有 5.7，整座島放得下三棵。
  改葉子長度前先想這件事，然後跑 `npm run audit:colliders` 看外框。
- 有幾個尺寸是**被別的地方釘死的**，改之前要一起改：
  - 木製平台的甲板頂面必須維持 `y = 0.30`（它是 `standable`，那個高度就是玩家站立的高度）
  - 吊床織帶在 `x = -0.835` 處的高度必須維持 `0.5237`（`items.ts` 的 `surfaceY: 0.69`
    除以 BUILDING 的 1.3175 倍率）

## 三之二、效能：這次改版實際花了多少

`npm run audit:outdoor` 每次都會把細節換算成 draw call 印出來，因為那才是掉不掉幀的那個數字：

```
  室外 26 種各放一件                346 draw calls
  典型一座島（24 件擺設）             319 draw calls
  再加上房屋（56–129，只有一棟）     375–448 draw calls
```

改版前的同一座島大約是 **180–240**，所以這一輪把室外的 draw call 加了將近一倍。

**這是可以接受的，而且是有意識花的**：一座擺滿的島 450 個 draw call，對 WebGL 場景來說仍在
舒服的範圍（真正要開始擔心是四位數），而島上同一時間只有一棟房子、二三十件擺設，不像室內
有多個房間可以疊加。真正擋住失控的是級距上限（`SIZE_CLASSES` 的 `maxMeshes`），它會在任何一件
東西膨脹到離譜之前先失敗。

三件刻意沒有做的事：

- **沒有做 instancing 或 mesh merge。** 那是一次架構改動（要把所有模型從宣告式 JSX 換成合併
  幾何），會讓「碰撞體積從模型量出來」這條保證更難維持，而現在的數字還沒有需要它。
- **沒有共用 `THREE.Material` 實例。** R3F 對「用 prop 傳進來的 material」與「自己建立的
  material」在卸載時的處置不同，為了省下來的那點材質數去賭生命週期不划算。共用的是**色盤**
  （`outdoorPalette.ts`），所以相同設定的材質會共用同一支 shader program，狀態切換仍然便宜。
- **火焰與光效不算進結構預算。** 它們本來就不是零件，稽核會把 `visible={false}` 或關掉
  `depthWrite` 的 mesh 排除 —— 跟碰撞系統對「畫上去的光」的處理同一個判準。

## 四、怎麼跑

```bash
npm run audit:outdoor
```

它會逐件列出室外每一件可擺放物與七棟房子的級距、尺寸、mesh 數、顏色數，任何一件低於它那一級的
下限、超出上限、或兩棟房子撞了同一組屋頂／外牆配對就失敗。

同時該跑的（這一輪都被這些擋下過真正的錯）：

```bash
npm run audit:colliders    # 碰撞體積是不是模型自己的形狀，外框有沒有暴增
npm run audit:placements   # 含同一個模型內部的共平面偵測
npm run audit:zfighting    # 兩個相距太近又互相遮蓋的朝上面
npm run audit:interactions # 坐點、躺點有沒有落在自己的家具上
npm run audit:ground       # 腳底有沒有踩在該踩的面上
```

## 五、這一輪實際改了什麼

**重建（原本 2–4 個 primitive）**：椰子樹、噴泉、木製平台、吊床、火把

**補上次級結構**：木製鞦韆（繫樑、封頭、三片座板、托條、繩結）、溫馨營火（七顆大小不一的石頭、
灰燼盤、餘燼、三根架起來的柴）、黃銅望遠鏡（三根撐條、目鏡、對焦鈕、尋星鏡、兩道銅箍）、
手作鳥屋（地樁盤、斜撐、底板、雙斜面屋頂、屋脊壓條、洞口木邊、棲木）、許願井（兩層砌石、井緣、
青苔、捲軸與搖把、雙斜面屋頂）

**補到下限**：戶外寵物窩、藤編狗籃、帆布帳篷窩、圓形貓窩、毛線貓屋、海風拱門、戶外陶甕、
戶外展台雕塑

**房屋**：六種屋頂全部重寫或新增（gable 從三角錐改成真正的三角柱、新增 gambrel 與 cottage）、
五種外牆（新增 log，其餘從「只描邊角」改成「牆面上看得到材質」）、每一棟都加了門階、兩側窗、
正面窗、門的板材與滴水簷；新增門廊、百葉窗、雨水桶、門燈四種特色

**沒有改**：室內家具（不在這次委託範圍）、圖騰石柱與風動雕塑（本來就達標）、白色柵欄與其餘六件
寵物窩（本來就達標）
