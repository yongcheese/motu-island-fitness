# 判定門檻實測報告：專業教練示範影片

**目的**：為 v2 企劃書 §3.4 的 I／II 類門檻補上實測依據。該節流程圖第 ① 步「蒐集標準」與第 ④ 步「以資料驗證」原本都是空的，本報告填第 ① 步。
**方法**：抓取 YouTube 上的專業示範影片，用**本系統自己的模型與參數**抽骨架，量出教練實際做到的角度分佈。
**日期**：2026-08-23

---

## 一、為什麼要做這件事

企劃書 §3.4 把每個門檻分成三類，其中 I 類宣稱「對應該運動領域公認的標準」。但 2026-08-22 的引用複查發現：

- 深蹲的「平行蹲」定義**掛錯出處**（歸給 Schoenfeld 2010，實為健力競賽規則）
- 伏地挺身只寫「體適能檢測通用」，**沒有指名任何檢測**

出處已於當日修正。但更根本的問題是：**這些門檻從未與任何真實影像比對過**。114 項自動化測試用的是本團隊自製的合成骨架，而該合成器把「髖低於膝」寫死——測試在結構上不可能失敗。

本報告用「不是我們生成的資料」量一次，看門檻站在哪裡。

---

## 二、方法

### 2.1 為什麼不用 Python 版 MediaPipe

刻意使用專案自己的 `vendor/models/pose_landmarker_full.task` 與 `app/core/pose.js` 的完整設定（含 One-Euro 平滑、信心門檻），在瀏覽器中執行。

理由：量出來的數字要能拿來標定本系統的門檻，就必須跟本系統實際判定時「看到」的骨架同源。換一套函式庫或參數，數字就不可比。

### 2.2 量什麼

每個動作量的算式與 `app/core/exercises/*.js` 中實際判定用的完全相同：

| 動作 | 量測值 | 算式 |
|---|---|---|
| 深蹲 | `depth` | (髖y − 膝y) / 腿長，值越大越深 |
| 深蹲 | `torsoLean` | 肩髖連線與鉛垂線夾角 |
| 伏地挺身 | `elbow` | 左右肘角平均 |
| 高抬腿 | `kneeRise` | (髖y − 膝y) / 軀幹長，正值＝膝高於髖 |
| 開合跳 | `legSpread` | 兩踝距 / 肩寬 |

### 2.3 流程

1. `yt-dlp` 取回 480p 影片
2. `ffmpeg` 抽成 5 fps 影格（**不用 `<video>` 逐幀 seek**——實測 yt-dlp 取回的 DASH 分離流沒有可靠索引，`currentTime` 設了不動）
   ⚠️ 5 fps 是**工程取捨**，非經驗證的充分取樣率：提高取樣率會等比增加推論時間，降低則可能錯過動作最深處。本報告未測試不同取樣率對峰值的影響，此為已知限制。
3. 逐幀餵入 PoseLandmarker，計算上表各值
4. 峰值偵測：局部極值且相鄰峰至少間隔 0.6 秒
   ⚠️ 0.6 秒同為**工程參數**，目的是避免把訊號抖動當成兩下，**不是**任何文獻認定的人類動作節奏下限。先前版本曾如此描述，該說法無依據，已更正。

### 2.4 樣本

| 動作 | 影片數 | 有效幀 | 峰值樣本 |
|---|---|---|---|
| 深蹲 | 7 | 991 | 52 |
| 高抬腿 | 3 | 498 | 53 |
| 開合跳 | 2 | 222 | 30 |
| 伏地挺身 | 2 | 163 | 11 |
| **合計** | **14** | **1,864** | **146** |

已剔除：前蹲舉與背蹲舉（負重，動作型態不同）、牆上伏地挺身、引體向上（搜尋誤帶）、世界紀錄競速（動作必然變形）。

## 三、結果

### 3.1 ⚠️ 最重要的發現：深蹲深度對機位極度敏感

七支同樣標榜「標準深蹲示範」的影片，量出的**最深值**如下：

| 影片 | 最深 `depth` | 全片達門檻(−0.10)的幀比例 |
|---|---:|---:|
| How To Squat Properly: Squat Deep | **+0.534** | 34% |
| Air Squats | +0.044 | 11% |
| Bodyweight Squat Tutorial | −0.073 | 1% |
| Exercise Tutorial - Squat | −0.120 | 0% |
| Leg exercise - How to bodyweight squat | −0.129 | 0% |
| How to do a bodyweight squat (Bupa) | −0.196 | 0% |
| CrossFit - Squatting **Below Parallel** | **−0.489** | 0% |

**跨度超過 1.0**，而系統門檻只是一個定值 −0.10。

最刺眼的是最後一列：影片標題明說「蹲到平行以下」，量出來卻是全部樣本中最淺的。這不可能是動作問題，只能是量測條件問題（該片多為遠景與講解畫面，僅 64/416 幀抽得到完整下肢）。

**結論**：`depth` 的變異主要來自**機位與取景**，不是動作本身。在機位不受控的影片上，這個量無法用來標定門檻。

> ⚠️ 這同時代表：**不能**根據本報告去調整深蹲深度門檻。要調必須用機位受控的自拍樣本。

### 3.2 深蹲軀幹前傾：45° 門檻有充分餘裕

| 統計量 | 值 |
|---|---:|
| 中位數 | 4.4° |
| p75 | 15.6° |
| p90 | 25.2° |
| 最大 | 75.3°（異常值，應為非深蹲動作段） |

**對照**：系統門檻 45°，合成器產生的正常深蹲恆為 **0°**。

真人（即使是教練）前傾的 p90 是 25.2°，離 45° 還有約 20° 餘裕。這支持現行門檻不會誤殺標準動作——但也證實合成器的 0° 完全不真實，先前註解宣稱「真人自然前傾常達 40°+」同樣沒有依據（實測 p90 僅 25°）。

### 3.3 伏地挺身肘角：系統門檻確實遠比標準寬鬆

| 統計量 | 值 |
|---|---:|
| 最深 | 41.9° |
| p25 | 53.3° |
| 中位數 | **65.6°** |
| p75 | 90.8° |
| 最淺 | 106.5° |

**對照**：體適能檢測標準 90°；系統觸發計次時肘角約 **117.5°**。

教練實際下壓到 65.6°（比檢測標準還深 24°），而系統在 117.5° 就給過——**兩者相差約 52°**。這具體證實了 v2 §3.4 已主動揭露的「比標準寬鬆」，並首次給出量化差距。

### 3.4 高抬腿膝高：同樣寬鬆

| 統計量 | 值 |
|---|---:|
| p25 | −0.005 |
| 中位數 | **+0.113** |
| p75 | +0.222 |

正值代表膝**高於**髖。教練中位數是膝高於髖 0.113 個軀幹長，而系統只要膝在髖下 0.085 就算達標——兩者相差約 0.20。

### 3.5 開合跳腳距：同樣寬鬆

腳距中位數 **1.705 × 肩寬**（p25 為 0.413，該低值來自併攏相位）。系統門檻為 1.0–1.2 × 肩寬。

## 四、對企劃書的具體修正建議

| 章節 | 現況 | 建議 |
|---|---|---|
| §3.4 I 類（伏地挺身） | 只說「比標準寬鬆」 | 補實測：教練中位 65.6°，系統 117.5°，差約 52° |
| §3.4 II 類（高抬腿） | 只寫慣例「膝抬至髖高」 | 補實測：教練中位為膝高於髖 0.113 軀幹長 |
| §3.4 II 類（開合跳） | 只寫「腳超肩寬」 | 補實測：教練中位 1.705 × 肩寬 |
| §3.4 III 類（軀幹 45°） | 附合成邊界值 | 補真人分佈：p90 = 25.2°，門檻餘裕約 20° |
| §3.6 | 三階段驗證計畫 | 新增「階段零：示範影片標準蒐集」，即本報告 |

**深蹲深度不建議寫入企劃書**，理由見 3.1——樣本間變異過大，寫進去會被問倒。

## 五、已知限制（必須一併揭露）

1. **樣本小且不平均**：伏地挺身僅 11 個峰值樣本，統計意義薄弱。
2. **機位完全未受控**：這是 3.1 那個發現的來源，也是本報告最大的方法論弱點。
3. **教練 ≠ 一般使用者**：示範者的動作品質高於目標族群，這批資料只能界定「標準動作長什麼樣」，不能用來估計真實使用者的通過率。
4. **僅供內部量測**：影片版權屬原作者。本報告只使用「量出來的統計數值」，**不重製影片、不放入作品或簡報**。若需示範影片，一律使用團隊自拍素材。
5. **不能取代真人測試**：本報告回答的是「標準在哪裡」，不是「系統判得準不準」。後者仍須自蒐真人樣本（現狀盤點 B-3）。

## 六、對真人測試的行動含義（重要）

3.1 的發現直接改變真人測試的拍攝規格。原本《真人測試執行手冊》第五節寫「要故意拍差」（低角度、距離不一），目的是測真實條件下的韌性。這仍然正確，但**不夠**：

> 機位不受控的資料**無法用來校準門檻**，只能用來測韌性。

因此拍攝要分成兩批：

| 批次 | 機位 | 用途 |
|---|---|---|
| **校準批** | 嚴格固定：鏡頭高度、距離、角度全部記錄並保持一致 | 標定門檻（尤其深蹲 depth） |
| **韌性批** | 故意拍差：低角度、距離不一、一般燈光 | 測真實條件下的表現 |

若只拍一批，兩個目的都達不到。執行手冊已據此更新。
