# Cloudflare Workers 後端複驗可行性測試報告

- 測試日期：2026-09-26
- 測試程式：`spikes/workers-verify/`（尚未 commit）
- 測試環境：Cloudflare Workers 免費方案（線上實測）＋本機 wrangler 4.140（workerd）
- 線上測試端點：`https://workers-verify-spike.yongcheesezhang.workers.dev`（僅做計算、不存資料；刪除需使用者執行 `npx wrangler delete`）

## 一、結論

**可以落地實作，但必須採用「分段上傳複驗」：每約 5 秒（150 幀）上傳一段，由 Workers 接續複驗。**
整場練完才一次上傳的做法，在免費方案每次 10ms 的 CPU 上限下不可行。

| 問題 | 結果 |
|---|---|
| 同一套判定引擎能否在 Workers 執行 | ✅ 可以，前端 `app/core` 原封不動匯入，打包 51KB |
| 後端結果是否與前端一致 | ✅ 一致（前提：前端先量化座標再判定） |
| 整場一次上傳（60 秒 50 下） | ❌ 線上 CPU 中位 24–52ms，持續超時後被 Cloudflare 強制中止 |
| 分段上傳（每段 5 秒） | ✅ 線上 60 次請求全部成功，CPU 中位 3ms、第 90 百分位 8ms |
| 分段結果是否等於整段 | ✅ 18,720 組比對 0 不一致（本機）；線上 5 種訓練 0 不一致 |
| 存檔被竄改／亂序重送 | ✅ 全部擋下（HTTP 403） |
| 費用 | ✅ 全程免費方案 |

## 二、測試方法

1. **資料**：使用專案內建的合成器（`app/core/synth.js`）產生骨架座標，涵蓋深蹲、開合跳、高抬腿、伏地挺身 4 種動作與 13 種動作變體（標準、半蹲、前傾、膝內夾、塌腰等），加入座標雜訊、時間戳抖動，以及隨機的遮擋／出框片段。
2. **CPU 時間**：線上環境的計時器在計算中不會前進（Cloudflare 官方文件說明之資安設計），因此線上 CPU 時間一律取自 `wrangler tail` 回報的 `cpuTime`，不採用程式自行計時。
3. **一致性**：以「前端整段一次判定」的結果為基準，逐項比對有效次數、無效次數、嘗試次數、錯誤類型統計與提醒統計，並逐幀比對次數變化。

## 三、測試結果

### 1. 整場一次上傳（不可行）

60 秒 50 下（1,806 幀）：

| 上傳格式 | 大小（gzip） | 本機 CPU | 線上 CPU 中位 |
|---|---|---|---|
| 原始 JSON | 2.6MB（1MB） | 5–9ms | 52ms |
| JSON 小數 4 位 | 1.2MB（250KB） | 4–6ms | 39ms |
| 二進位 | 473KB（200KB） | 2–3ms | 24ms |

- 線上 CPU 約為本機的 8–10 倍。
- 連續超時後 Cloudflare 啟動強制中止：共 127 次「Worker exceeded CPU time limit」，HTTP 503。

### 2. 座標量化的影響與解法

- 二進位與小數 4 位格式會把座標精度降到萬分之一。3,120 組比對中有 23 組結果改變，原因是訊號剛好落在門檻邊緣（例：高抬腿訊號 0.7809 與 0.7808，門檻 0.80）。
- **解法：前端先量化座標再判定**，前後端吃到完全相同的資料。實測 468 組前端 vs Worker，0 不一致。

### 3. 分段上傳複驗（可行）

做法：判定引擎加入「存檔／讀檔」。每段複驗完，Workers 把引擎狀態連同 HMAC 簽章交還前端；下一段上傳時帶回，Workers 驗章後接續判定。存檔約 2KB。

**正確性（本機）**：4 動作 × 13 變體 × 3 雜訊 × 20 種子 × 有／無遮擋 × 3 種切段長度（150／90／37 幀，37 幀刻意讓切點落在動作中段），共 18,720 組，**0 不一致**。
另以「故意漏存某項狀態」驗證測試有效：漏存取景視窗、中斷計時、漏看計數時，分別抓到 3,650、1,824、852 組不一致。

**線上 CPU（每段 150 幀，二進位，逐段間隔 1.5 秒）**：

| 訓練 | 段數 | CPU 中位 | 最大 |
|---|---|---|---|
| 深蹲（標準 50 下＋膝內夾 30 下） | 21 | 3ms | 18ms |
| 開合跳 50 下 | 13 | 3ms | 7ms |
| 高抬腿（前傾）50 下 | 13 | 3ms | 14ms |
| 伏地挺身（未打直）50 下 | 13 | 3ms | 10ms |
| **合計** | **60** | **3ms** | **18ms**（第 90 百分位 8ms） |

- 60 次全部成功（HTTP 200），**0 次被中止**。
- 超過 10ms 的有 3 次，屬官方所述「偶爾超時有彈性」的範圍。
- 5 種訓練的最終複驗結果全部等於整段判定。

**防竄改**：簽章綁定訓練編號與段落序號。竄改存檔（有效次數＋100）、拿舊存檔冒充下一段、換訓練編號重用存檔，三種情況全部回傳 403。

## 四、限制與尚未驗證

1. **測試資料為合成資料**，尚未用真人錄製的骨架序列測試。
2. **線上偶有尖峰**（最大 18ms）。若正式上線後尖峰頻繁，可把每段縮短為 3 秒（本機已驗證 90 幀切段結果正確，線上 CPU 未實測）。
3. **防作弊的邊界**：骨架座標本身可被合成，因此複驗是「大幅提高作弊門檻」而非「無法作弊」；使用者也可能挑選不上傳某些段落，需以段落序號連續性與時間戳檢查補強（尚未實作）。
4. **尚未串接 Firebase**：寫入訓練紀錄與點數需要遊戲組將我們加入 Firebase 專案（待確認第 ⑦ 項）。
5. 測試用簽章金鑰為明碼，正式版需改用 `wrangler secret`。
6. 引擎的存檔／讀檔目前是測試用副本（由腳本從正式引擎自動產生），正式導入時需併入 `app/core/engine.js` 並補測試。

## 五、對企劃書用語的建議

- 「後端以同一套判定邏輯複驗」：**已驗證可行**，可以寫。
- 「後端驗證服務**建置於** Cloudflare Workers」：目前是通過可行性驗證的原型，尚未整合進產品；建議寫「**規劃建置於** Cloudflare Workers，並已完成可行性驗證」。
